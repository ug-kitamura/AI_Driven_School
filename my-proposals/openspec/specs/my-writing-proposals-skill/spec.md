# my-writing-proposals-skill Specification

## Purpose
対話でユーザーの中にある材料（変えたいこと・決裁者・相手の問い・根拠・実際に見た場面と心の声・文体見本）を1問ずつ引き出し、結論ファーストで意思決定者を動かす提案文書を作るスキルを提供する。読み手の頭に絵が浮かぶ具体を根拠側に置き、部のパーパスとの整合を保ったまま、日本語の提案文として出力する。

## Requirements
### Requirement: スキルの起動とトリガー

`my-writing-proposals` スキルは、会社向けの提案文作成を依頼されたときに起動する SKILL.md を提供しなければならない（SHALL）。SKILL.md は frontmatter に `name` と `description` を持ち、`my-proposals/.claude/skills/my-writing-proposals/` に配置されなければならない（SHALL）。

#### Scenario: 提案作成の依頼で起動する

- **WHEN** ユーザーが「提案文を作って」「会社向けの提案を書いて」等と依頼する
- **THEN** スキルが起動し、対話フェーズを開始する

#### Scenario: 配置とメタ情報

- **WHEN** スキルを配置する
- **THEN** `my-proposals/.claude/skills/my-writing-proposals/SKILL.md` に置かれ、frontmatter に `name: my-writing-proposals` と日本語の `description` を持つ

### Requirement: 対話による材料収集

スキルは6材料（①変えたいこと ②決裁者 ③相手の問い ④根拠 ⑤実際に見た場面と心の声 ⑥文体見本）を1問ずつ推奨案つきで収集しなければならない（SHALL）。入力に既にある材料は聞き返さず出力へ進まなければならない（SHALL）。選択肢は基本1案、必要なら2案、最大3案に絞り込まなければならない（SHALL）。固定の質問リストを上から順に埋めてはならず（SHALL NOT）、ユーザーの回答に応じて次に掘る場所を変えなければならない（SHALL）。やりとりの回数を固定してはならない（SHALL NOT）。

材料④（根拠）の収集では、「提案文に要る事実の点検」で定める軸を通し、不足する事実を聞き取らなければならない（SHALL）。

#### Scenario: 既知材料をスキップする

- **WHEN** ユーザーが `my-issue.md` のように材料を最初にまとめて渡す
- **THEN** スキルは埋まっている材料を聞き返さず、不足分だけを1問ずつ確認する

#### Scenario: 選択肢を絞る

- **WHEN** 提案に複数の案が考えられる
- **THEN** スキルは案を最大3案までに絞り、各案を1行で示し推奨を明示する

#### Scenario: 抽象語を具体に戻す

- **WHEN** ユーザーの回答に「非効率」「課題」「改善」のような抽象語が出る
- **THEN** スキルはその裏にある具体的な場面を聞き返す

#### Scenario: ユーザーが打ち切る

- **WHEN** ユーザーが「もう十分」と伝える
- **THEN** スキルはその時点で対話を終え、出力に進む

### Requirement: ストーリーレベルの合意

スキルはストーリーレベルを 0〜3 の4段階で定義しなければならない（SHALL）。レベルは「読み手の頭に絵が浮かぶ箇所の数」で定義しなければならない（SHALL）。Lv0 は0箇所（数字と事実で説得する）、Lv1 は1箇所（1〜2文）、Lv2 は2〜3箇所、Lv3 は全編が場面で駆動する、とする。既定は Lv1 でなければならない（SHALL）。

スキルは材料②（決めるのは誰か）が確定した直後に、ストーリーレベルをユーザーに確認しなければならない（SHALL）。確認より前に材料⑤（実際に見た場面と心の声）を掘ってはならない（SHALL NOT）。

合意したレベルは、材料⑤を掘る深さの上限として扱わなければならない（SHALL）。

#### Scenario: 決裁者の確定後に聞く

- **WHEN** ユーザーが決裁者を答える
- **THEN** スキルはストーリーレベルを 0〜3 で確認し、既定として Lv1 を推奨する

#### Scenario: Lv0 を選んだとき

- **WHEN** ユーザーが Lv0 を選ぶ
- **THEN** スキルは材料⑤を掘らず、数字と事実で提案文を組み立てる

#### Scenario: レベルどおりの分量で書く

- **WHEN** ユーザーが Lv1 に合意している
- **THEN** 出力される提案文に、読み手の頭に絵が浮かぶ箇所は1箇所（1〜2文）だけ置かれる

### Requirement: 提案文に要る事実の点検

スキルは提案文を書く前に、必要な事実を軸で点検しなければならない（SHALL）。軸は規模・期間・判定・次の一手・影響・出所とする。

- **規模**: 何人 / どれくらいの量 / いくら
- **期間**: いつから / いつまで / どれくらい続くか
- **判定**: 終わったとき何をもって成功とするか / 何が起きたら失敗と判断して撤退するか
- **次の一手**: 通ったら誰が何をするか（提案相手 / 提案者 / 対象者の3者に分ける）
- **影響**: 誰が困るか / 何が止まるか / 何をやめることになるか
- **出所**: その数字はどこから来たか（実測 / 推定 / 伝聞）

この一覧は軸であり、提案の種類ごとに該当する行を1つ選ぶ分類表として実装してはならない（SHALL NOT）。全軸が毎回同時に効かなければならない（SHALL）。

スキルは全軸を通さなければならないが（SHALL）、全軸を質問してはならない（SHALL NOT）。軸を落とす基準は「読み手がその問いを持たないとき」でなければならない（SHALL）。すでに分かっている事実を聞き返してはならない（SHALL NOT）。

#### Scenario: 読み手が持たない問いは落とす

- **WHEN** 定例会議の頻度を変える提案で、読み手が撤退条件を気にしない
- **THEN** スキルは判定の軸を聞かずに落とし、規模と影響の軸を聞く

#### Scenario: 投資判断では全軸が通る

- **WHEN** ツール導入のトライアルを提案し、読み手が費用と展開範囲を判断する
- **THEN** スキルは規模・期間・判定・次の一手・影響・出所のすべてを確認する

#### Scenario: 次の一手を3者に分けて聞く

- **WHEN** 提案が通った後の段取りを確認する
- **THEN** スキルは提案相手・提案者・対象者のそれぞれが何をするかを分けて聞く

### Requirement: ぼかしの検出

スキルは、事実が手元にないことを曖昧な語で埋めてはならない（SHALL NOT）。「数名」「希望者」「早めに」「一定の効果」のような語を書こうとしたとき、それを事実の欠落のサインとして扱い、ユーザーに聞かなければならない（SHALL）。

#### Scenario: 曖昧な語を書こうとしたら聞く

- **WHEN** 対象者の人数が分からないまま「他部署の希望者」と書こうとする
- **THEN** スキルは書かずに人数をユーザーに確認する

### Requirement: 事実が得られないときの扱い

スキルは、手元にない事実にぶつかったらユーザーに聞かなければならない（SHALL）。ユーザーが答えられない場合はフェルミ推定で見積もり、ユーザーの合意を得てから使わなければならない（SHALL）。見積もれない場合はその話題に触れてはならない（SHALL NOT）。

フェルミ推定は、推定が可能となるレベルまでユーザーから情報を引き出し、算出結果を提示して違和感がないか確認し、違和感があれば理由を聞いて再計算し、ユーザーが納得するまで繰り返さなければならない（SHALL）。

#### Scenario: 数字を一緒に見積もる

- **WHEN** ユーザーが工数の実測値を持っていない
- **THEN** スキルは推定に必要な情報を聞き出して算出し、結果を提示して違和感がないか確認する

#### Scenario: 納得するまで再計算する

- **WHEN** 提示した推定結果にユーザーが違和感を示す
- **THEN** スキルは理由を聞き、再計算に必要な情報を聞き出して計算し直し、再度提示する

#### Scenario: 見積もれないものには触れない

- **WHEN** 提案が通った後に相手が取る行動をユーザーが答えられず、推定もできない
- **THEN** スキルはその段取りを提案文に書かない

### Requirement: 状況フレーミング（メンツ配慮の汎用化）

スキルは、既存のやり方や過去を否定する提案について、人や過去を責めず、会社の事情・環境変化・状況変化に原因を帰属させる書き方を採用しなければならない（SHALL）。「無駄」「非効率」「間違い」等の否定語を避けなければならない（SHALL）。

#### Scenario: 変化への追従として語る

- **WHEN** 提案が既存の取り組み（例: 既存ツールの推進方針）と衝突しうる
- **THEN** スキルは「新しい環境への変化に追従する」「会社の事情に合わせる」という状況要因として提案を組み立て、過去の担当者や判断を否定しない

### Requirement: 出力形式とテンプレート

スキルは提案文を日本語のみで生成しなければならない（SHALL）。節構成は提案内容に合わせて変えなければならず（SHALL）、固定テンプレートを機械的に埋めてはならない（SHALL NOT）。

SKILL.md は提案文の節構成の例を提示してはならない（SHALL NOT）。節の名前・数・順番は「読み手が何を、どの順で知りたいか」から毎回決めなければならない（SHALL）。骨格は PREP（結論 → 理由 → 具体 → 再結論）とし、結論を最初に言い切らなければならない（SHALL）。

行数・文字数を指定してはならない（SHALL NOT）。分量の調整は、起動時のユーザー指示または出力後の指示で行う。分量を削る必要が生じた場合は「背景説明 → リスク詳細 → 選択肢の説明文」の順に削り、結論・数字・依頼事項は必ず残さなければならない（SHALL）。提案文の中で太字などの markdown 装飾を使ってはならない（SHALL NOT）。

#### Scenario: 節構成の例を持たない

- **WHEN** SKILL.md を読む
- **THEN** 提案文の節構成を示すテンプレートは書かれておらず、節を決める判断基準だけが書かれている

#### Scenario: 内容に応じて節を変える

- **WHEN** 提案に判断材料としての比較が必要である
- **THEN** 比較表や選択肢の節が加わり、要点が1つだけの提案では階層を作らない

#### Scenario: 行数で切らない

- **WHEN** 提案文を生成する
- **THEN** 行数の上限による打ち切りは行われず、必要な内容が書かれる

#### Scenario: 英語版は求められたときだけ

- **WHEN** ユーザーが英語版を必要とする
- **THEN** 出力後に翻訳を依頼する形で対応し、スキルは既定で英語版を生成しない

### Requirement: パーパス整合の扱い

スキルは対話の冒頭で1回だけ、ユーザーのチーム・部署の Purpose / Mission を確認しなければならない（SHALL）。確認は選択肢（`references/purpose.md` を参照する／自分でファイルを選択する／自分で記入する／スキップする）で行わなければならない（SHALL）。Purpose の扱いを読み手によって変えてはならない（SHALL NOT）。提案文への織り込みは1箇所だけとし（SHALL）、Purpose の文言をそのまま引用せず提案の文脈に言い換えなければならない（SHALL）。独立したパーパスセクションを作ってはならない（SHALL NOT）。接点がない場合やくどくなる場合は織り込みを省略しなければならない（SHALL）。

#### Scenario: 冒頭で1回だけ確認する

- **WHEN** 対話を開始する
- **THEN** Purpose / Mission の扱いを選択肢で1回確認し、以降は聞き返さない

#### Scenario: 読み手で扱いを変えない

- **WHEN** 読み手が Purpose を重視しない人物である
- **THEN** スキルは扱いを変えず、同じようにさりげなく1箇所に織り込む

#### Scenario: 接点がなければ省略する

- **WHEN** 提案内容と Purpose に自然な接点がない
- **THEN** 無理に紐づけず、織り込みを省略する

### Requirement: 絵文字の統一

スキルは提案文で絵文字を原則使ってはならない（SHALL NOT）。`【提案】` タグもテキストのみとしなければならない（SHALL）。使う場合はパターンを統一し、見出し1つだけ・本文だけといった混在を禁止しなければならない（SHALL）。

#### Scenario: 原則なし

- **WHEN** 提案文を生成する
- **THEN** 絵文字を使わず、タグはテキストのみで表現する

### Requirement: 模範例の構成と読み方

`references/examples.md` は提案文の例だけを並べたファイルでなければならない（SHALL）。

以下を含めてはならない（SHALL NOT）。

- 例ごとの解説・注釈（「何が効いているか」等）
- 例の通し番号
- 型・ストーリーレベル・媒体などの分類見出しやタグ
- 例の読み方や流用禁止の注記

見出しは提案の内容だけを示さなければならない（SHALL）。例の読み方（品質水準・文体・構成・情報量・説明の深さを読み取る／題材・数字・表・言い回しを流用しない）は SKILL.md に置かなければならない（SHALL）。

`examples.md` は、ユーザーや他のメンバーが良い提案文を追加・修正・削除して育てられる構造でなければならない（SHALL）。既定のストーリーレベル（Lv1）の例を最低1本含まなければならない（SHALL）。

#### Scenario: 例文だけが並ぶ

- **WHEN** `references/examples.md` を開く
- **THEN** 提案内容を示す見出しと提案文本文だけが並び、解説・番号・分類は書かれていない

#### Scenario: 例を1本足す

- **WHEN** ユーザーが良かった提案文を1本追加する
- **THEN** 見出しと本文を貼るだけで済み、分類やレベルの判断を求められない

#### Scenario: 既定レベルの実例がある

- **WHEN** スキルが Lv1 で提案文を書く
- **THEN** `examples.md` に Lv1 相当の例が存在し、品質水準の参照先になる

### Requirement: 事実の創作の禁止

スキルは、ユーザーが語っていないことを事実として書いてはならない（SHALL NOT）。対象は場面・数字・期限・段取り・相手の反応のすべてとする。

材料が不足している場合は、聞く・一緒に見積もって合意する・その話題に触れない、のいずれかを取らなければならない（SHALL）。曖昧な語で埋めてはならない（SHALL NOT）。

たとえ話については、ユーザーの体験ではないためスキルが案を出してよい。複数案を示し、読み手にいちばん近いものをユーザーに選んでもらわなければならない（SHALL）。

#### Scenario: 段取りを創作しない

- **WHEN** 提案が通った後の日程をユーザーから聞いていない
- **THEN** スキルは「今週中にご返信いただければ来月から始められます」のような段取りを書かない

#### Scenario: 場面を創作しない

- **WHEN** 材料⑤が得られていない
- **THEN** スキルは場面を作り出さず、合意したストーリーレベルの範囲で数字と事実により構成する

### Requirement: 読み手が複数のときの焦点

提案の読み手が複数いる場合、スキルは「誰の一言でこの提案が動くか」を対話で確定し、本文はその1人の問いに答える形で構成しなければならない（SHALL）。他の読み手の関心は、懸念の先出しの中で拾わなければならない（SHALL）。読み手ごとに別の提案文を生成してはならない（SHALL NOT）。

#### Scenario: 承認者が二段階にいる

- **WHEN** ユーザーが「まず課長、最終承認は部長」のように複数の読み手を挙げる
- **THEN** スキルはどちらに焦点を合わせるかを確認し、本文はその1人に向けて書き、もう1人の関心は懸念として1行拾う

### Requirement: 媒体の確認

スキルは提案文の媒体（メール／チャット）を、入力から判断できないときにだけ確認しなければならない（SHALL）。入力に媒体の指定がある場合は聞き返してはならない（SHALL NOT）。

#### Scenario: 指定済みなら聞かない

- **WHEN** ユーザーが「メールで提案文を作って」と依頼する
- **THEN** スキルは媒体を聞き返さず、材料の収集に進む

#### Scenario: 無指定なら1問聞く

- **WHEN** 入力に媒体の手がかりがない
- **THEN** スキルはメールかチャットかを1問だけ確認する

### Requirement: 出力先と保存

スキルは完成した提案文を、**入力ファイルと同じフォルダ**に Markdown ファイルとして保存しなければならない（SHALL）。同時にチャットにもコードブロックで出力しなければならない（SHALL）。ファイル名は提案の内容が分かる日本語としなければならない（SHALL）。命名規則を固定してはならない（SHALL NOT）。

#### Scenario: 保存とチャット出力を両方行う

- **WHEN** 提案文が完成する
- **THEN** 入力ファイルと同じフォルダに Markdown ファイルが保存され、チャットにも同じ内容がコードブロックで示される

### Requirement: 品質チェックリスト

スキルは `references/output-quality.md` に、提案文をレビューするための観点を持たなければならない（SHALL）。この観点は、人間およびサブエージェントがレビューに使うものとする。

観点は結論と依頼事項・具体の有無と置き場・ストーリーレベルとの整合・Purpose の織り込み・文章表現・出力形式を含まなければならない（SHALL）。件名を1件に絞る、初出の用語を説明する、といった細目を含んでよい。

スキルは出力前にこのチェックリストの全項目をセルフチェックすることを義務としてはならない（SHALL NOT）。出力は人間が磨く草稿として扱う。

#### Scenario: レビュー観点として使う

- **WHEN** サブエージェントレビューを実施する
- **THEN** `output-quality.md` の観点に沿って提案文が点検される

#### Scenario: 出力前に全項目を確認しない

- **WHEN** 提案文を出力する
- **THEN** スキルは全項目のセルフチェックを行わず、草稿として出力する

### Requirement: 出力後のレビュー

スキルは提案文の出力後に、意思決定者役のサブエージェントに時系列で心の声を出させるレビューを実施するかどうかをユーザーに確認しなければならない（SHALL）。ユーザーが実施を選んだ場合は実行しなければならない（SHALL）。確認せずに実行してはならない（SHALL NOT）。

#### Scenario: 確認してから実行する

- **WHEN** 提案文を出力し終える
- **THEN** スキルはサブエージェントレビューを実施するか確認し、ユーザーが同意した場合に実行する

#### Scenario: 実施しない選択

- **WHEN** ユーザーがレビューを断る
- **THEN** スキルはレビューを実行せずに終了する

### Requirement: 締めの言葉

スキルは提案文を渡し終えたあと、ユーザー自身が文章を磨くよう促す締めの言葉を表示しなければならない（SHALL）。文面は逐語で表示しなければならず（SHALL）、言い換え・要約をしてはならない（SHALL NOT）。

表示のタイミングはサブエージェントレビューの可否が決まった後とする。表示は1セッションにつき1回とし、その後のやりとりで繰り返してはならない（SHALL NOT）。

#### Scenario: レビューを実施したあとに表示する

- **WHEN** サブエージェントレビューを実行し、指摘を提案文へ反映し終える
- **THEN** スキルは締めの言葉を逐語で表示する

#### Scenario: レビューを断られたときも表示する

- **WHEN** ユーザーがサブエージェントレビューを断る
- **THEN** スキルは締めの言葉を逐語で表示する

#### Scenario: 往復が続いても繰り返さない

- **WHEN** 締めの言葉を表示した後、ユーザーが提案文の修正を求める
- **THEN** スキルは修正に応じ、締めの言葉を再度表示しない

- **WHEN** スキルを作成・運用する
