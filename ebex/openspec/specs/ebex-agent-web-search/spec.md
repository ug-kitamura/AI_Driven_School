## Requirements

### Requirement: web_search ツール

システムは `web_search` ツール（入力: `query` / `purpose`）を提供しなければならない（MUST）。検索は EBEX ランタイムがクライアントツールとして実行し、LLM プロバイダのサーバーサイド検索ツールを使用してはならない（MUST NOT）。tool_result にはタイトル・URL・スニペットからなる結果一覧（件数上限あり）のみを返し、ページ本文を含めてはならない（MUST NOT）。

#### Scenario: 検索して結果の要約を返す

- **WHEN** モデルが `web_search` を要求し、ユーザーが確認を許可し、検索バックエンドが成功する
- **THEN** tool_result にタイトル・URL・スニペットの一覧（上限件数以内）が返る

#### Scenario: query 欠落はエラー

- **WHEN** `query` が欠落または空で呼び出される
- **THEN** 検索は実行されず、復旧可能なエラーが tool_result で返り、loop は継続する

### Requirement: 検索の確認ゲート

システムは、検索 API キーが設定されている場合、検索実行前に毎回ユーザー確認を要求しなければならない（MUST）。この確認は `query` が非空である限り、直前の検索失敗によるサーキットブレーカー作動中であっても表示しなければならない（MUST）。確認表示には「『{query}』について web 検索しますが、よろしいですか？」の形式でクエリ全文を含め、`purpose` を補助表示しなければならない（SHALL）。拒否された場合は検索せず、拒否された旨と同じクエリを再要求しない旨の案内を tool_result でモデルへ返さなければならない（SHALL）。検索 API キーが未設定の場合は本ゲート（検索してよいかの確認）を表示してはならず（MUST NOT）、「キー未設定時の人手フォールバック」要件に従わなければならない（SHALL）。

#### Scenario: 確認して検索する

- **WHEN** キー設定済みでモデルが `web_search` を要求し、確認ダイアログでユーザーが許可する
- **THEN** 検索が実行され、結果が返る

#### Scenario: 拒否時は検索しない

- **WHEN** キー設定済みで確認ダイアログでユーザーが拒否する
- **THEN** 検索 API は呼ばれず、拒否された旨と同一クエリを再要求しない案内が tool_result で返り、loop は継続する

#### Scenario: クエリ全文が確認に表示される

- **WHEN** キー設定済みで `web_search` の確認ダイアログが表示される
- **THEN** 外部へ送信されるクエリ全文と目的（purpose）がユーザーに提示される

#### Scenario: サーキットブレーカー作動中でも確認は表示される（キー設定済み）

- **WHEN** キー設定済みで直前の検索が失敗しサーキットブレーカーが作動中の状態で `web_search` が要求される
- **THEN** 確認ダイアログが表示され、承認後にスキップ判定が行われる

#### Scenario: キー未設定時は検索確認を出さない

- **WHEN** 検索 API キーが未設定の状態で `web_search` が要求される
- **THEN** 「検索してよいか」の確認ダイアログは表示されず、人手フォールバックへ移る

### Requirement: SearchProvider アダプタと設定解決

システムは検索バックエンドを `SearchProvider` アダプタの背後に置き、バックエンド種別・API キー・エンドポイントを workspace 設定から解決しなければならない（MUST）。ツール契約（schema・確認 UX・結果の形）はバックエンドに依存してはならない（MUST NOT）。

#### Scenario: 設定からバックエンドを解決する

- **WHEN** workspace 設定に検索 API キーが設定されている
- **THEN** `web_search` は設定されたバックエンドのアダプタで検索を実行する

#### Scenario: キー未設定は確認後に劣化契約で返す

- **WHEN** 検索 API キーが未設定のまま `web_search` が要求され、ユーザーが確認を許可する
- **THEN** 検索は実行されず、モデルへは検索が未設定であり再試行せず検索なしで続行する旨の案内が tool_result で返る。ツール実行ログには「検索APIキーが未設定のためweb検索できません。web検索をスキップします。」を表示する

### Requirement: 劣化契約（graceful degradation）

検索の失敗（到達不可・認証エラー・タイムアウト）・キー未設定時、システムは単なるエラーではなく、「再試行せず、検索なしで続行するか、必要な情報をユーザーに尋ねる」という行動指示を含む tool_result をモデルへ返さなければならない（MUST）。あわせて、ツール実行ログには利用不可の理由を含む「{理由}のためweb検索できません。web検索をスキップします。」を表示しなければならない（SHALL）。理由はケースごとに区別しなければならない（SHALL）: キー未設定は「検索APIキーが未設定」、サーキットブレーカー作動中は「直前の検索が失敗した」、実際の検索リクエスト失敗はエラー内容そのもの。検索の失敗がスキル実行の他の処理を停止させてはならない（MUST NOT）。

#### Scenario: 検索失敗でもスキル実行は続く

- **WHEN** ユーザーが許可した検索がネットワーク到達不可で失敗する
- **THEN** 行動指示付きの案内が tool_result で返り、ツール実行ログにはエラー内容を理由としたスキップ表示が出て、モデルは検索なしで残りの処理を継続できる

#### Scenario: 検索失敗が安全停止に到達しない

- **WHEN** 検索を含むスキルを検索不可の環境で実行する
- **THEN** 同一ツールエラーの連続によるエージェント安全停止は発生せず、検索以外の成果物は生成される

### Requirement: サーキットブレーカー

システムはセッション内で検索が一度失敗した後、以降の `web_search` 呼び出しに対して確認ダイアログは表示しつつ、承認後に実 API（プロバイダ）を再度呼び出してはならない（MUST NOT）。この場合、劣化契約と同文の案内を tool_result でモデルへ返し、ツール実行ログには「直前の検索が失敗したためweb検索できません。web検索をスキップします。」を表示しなければならない（MUST）。フラグのスコープはセッション内とし、新しいセッションでは再試行できなければならない（SHALL）。

#### Scenario: 2 回目以降は確認後に実 API を呼ばずスキップする

- **WHEN** セッション内で検索が一度失敗した後、モデルが再度 `web_search` を要求し、ユーザーが確認を許可する
- **THEN** 検索プロバイダは呼び出されず、利用不可の案内が即座に tool_result で返り、ツール実行ログには「直前の検索が失敗した」旨のスキップ表示が出る

#### Scenario: 新しいセッションでは再試行される

- **WHEN** 検索が失敗したセッションの後、新しいセッションで `web_search` が要求される
- **THEN** 通常どおり確認ダイアログが表示され、検索が試行される

### Requirement: キー未設定時の人手フォールバック

検索 API キーが未設定の状態で `web_search` が要求されたとき、システムは検索可否の確認を出さず、即座に人手フォールバックを提示しなければならない（SHALL）。フォールバックはユーザーに検索クエリ全文を提示し、(1) ユーザー自身が検索した結果とソース URL を入力する導線、(2) 検索をスキップして続行する導線、の双方を含めなければならない（SHALL）。ユーザーが結果を入力した場合はその内容を、スキップした場合は「検索なしで続行する」旨を tool_result としてモデルへ返さなければならない（SHALL）。モデルへ同一クエリでの `web_search` 再要求を促してはならない（MUST NOT）。本要件はキー未設定時において、劣化契約のキー未設定分岐に優先する。

#### Scenario: キー未設定でクエリが提示される

- **WHEN** キー未設定で `web_search` が要求される
- **THEN** 検索クエリ全文がユーザーへ提示され、結果貼付またはスキップを選べる

#### Scenario: 結果を貼付して続行する

- **WHEN** ユーザーが検索結果とソース URL を入力する
- **THEN** その内容が tool_result としてモデルへ返り、モデルは続行できる

#### Scenario: スキップして続行する

- **WHEN** ユーザーが検索をスキップする
- **THEN** 「検索なしで続行する」旨が tool_result で返り、モデルは同一クエリを再要求しない

### Requirement: 人手フォールバックの URL 欄とデータ欄の分離

システムは、キー未設定時の人手フォールバックダイアログにおいて、入力欄を 2 つに分けて提供しなければならない（SHALL）。上部に 1 行の URL 入力欄（`input`）を、その下に複数行のデータ入力欄（`textarea`）を配置しなければならない（SHALL）。URL 入力欄は任意とし、空のままでも続行できなければならない（SHALL。URL 空を理由に続行を妨げてはならない・MUST NOT）。ユーザーが入力した URL とデータは、tool_result としてモデルへ渡す前に結合または構造化されなければならない（SHALL）。スキップの導線は従来どおり維持しなければならない（SHALL）。

#### Scenario: URL 欄とデータ欄が分かれて表示される

- **WHEN** キー未設定で `web_search` が要求され、人手フォールバックが表示される
- **THEN** 上に 1 行の URL 入力欄、その下に複数行のデータ入力欄が表示される

#### Scenario: URL 空でも続行できる

- **WHEN** ユーザーが URL 欄を空のままデータ欄に検索結果を入力して続行する
- **THEN** URL 空を理由に妨げられず、入力内容が tool_result としてモデルへ返る

#### Scenario: スキップは維持される

- **WHEN** ユーザーが検索をスキップする
- **THEN** 従来どおり「検索なしで続行する」旨が tool_result で返る

### Requirement: 検索未成立時の出典抑止

web 検索が成立しなかった場合、システムはモデルへ返す tool_result の案内に、検索していない情報へ出典 URL や出典表記を付けてはならない旨の行動指示を含めなければならない（SHALL）。対象は次の 4 ケースとする（SHALL）: 検索リクエストの失敗、検索 API キーの未設定、ユーザーによる検索の拒否、人手フォールバックでのスキップ。

人手フォールバックでユーザーが検索結果を入力した場合、その結果に基づく出典は正当であるため、本要件の出典抑止を適用してはならない（MUST NOT）。

本要件は案内文の内容に対する要件であり、検索の実行可否・確認ゲート・サーキットブレーカーの挙動を変更してはならない（MUST NOT）。

#### Scenario: 検索失敗時は出典抑止が案内される

- **WHEN** ユーザーが許可した検索がネットワーク到達不可・認証エラー・タイムアウトのいずれかで失敗する
- **THEN** tool_result の案内に、検索なしで続行してよい旨に加えて、検索していない情報に出典を付けない旨の行動指示が含まれる

#### Scenario: キー未設定時は出典抑止が案内される

- **WHEN** 検索 API キーが未設定の状態で `web_search` が実行され、劣化契約の案内が返る
- **THEN** その案内に、検索していない情報に出典を付けない旨の行動指示が含まれる

#### Scenario: 拒否時は出典抑止が案内される

- **WHEN** ユーザーが検索の確認ダイアログで拒否する
- **THEN** 拒否された旨・同一クエリを再要求しない旨に加えて、検索していない情報に出典を付けない旨の行動指示が tool_result で返る

#### Scenario: スキップ時は出典抑止が案内される

- **WHEN** 人手フォールバックでユーザーが検索をスキップする
- **THEN** 検索なしで続行する旨に加えて、検索していない情報に出典を付けない旨の行動指示が tool_result で返る

#### Scenario: 結果を貼付した場合は出典抑止を案内しない

- **WHEN** 人手フォールバックでユーザーが検索結果とソース URL を入力する
- **THEN** tool_result には入力内容とそれを根拠として続行する旨が返り、出典を付けない旨の行動指示は含まれない

#### Scenario: 検索成功時は案内が変わらない

- **WHEN** 検索が成功し、結果一覧が tool_result で返る
- **THEN** 出典抑止の行動指示は含まれず、検索成功時の tool_result の形は変わらない
