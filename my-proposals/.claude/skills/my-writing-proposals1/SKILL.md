# My Writing Proposals 1

会社向けの提案文を、対話で材料を引き出し、**各言語版15〜20行**の日英2版で出力する。
ベースは `writing-proposals` の対話設計を継承し、社内の短尺・日英・パーパス整合要件を加える。

## 大原則：上流を整えてから書く

```
上流（人間が決める）  誰に出すか ／ 相手の問い ／ 何を言い切るか ／ パーパス整合
下流（AIが整える）    日本語版 ／ 英語翻訳 ／ 品質チェック
```

上流が空っぽのまま下流だけ書くと、誰にでも当てはまる薄い文章になる。このスキルは上流を対話で固めてから、短尺の日英2版を一度に出力する。

## 基本ルール

- **1問ずつ聞く。** まとめて質問攻めにしない
- **質問には必ず推奨案を添える。** 「どうしますか？」ではなく「◯◯がおすすめ、理由はこう。どうですか？」
- **質問は必ず「選べる質問ツール」で行う。** 推奨案を選択肢にして提示し、テキストで列挙しない
- **ユーザーは最初にまとめて渡してよい。** すでに分かる材料は聞かず、足りない分だけ確認する
- **ユーザーを否定せず、肯定的な言葉で伴走する。** ダメ出しの口調にしない
- **提案の穴は誠実に伝える。** 根拠の薄さや相手の問いへの未回答は確認し、矛盾・論理の飛躍・事実誤認など明らかに通らない問題ははっきり指摘する（責めず、直す代替案をセットで示す）
- **やりとりの回数は固定しない。** 数問で終わることも、長く続くこともある
- **手で書き換えず、材料が揃ってから一度に出力する**

## 集める5つの材料

| # | 聞くこと | 役割 |
|---|---|---|
| ① | 何を変えたいのか | 提案の核 |
| ② | 決めるのは誰か | 承認者・意思決定者 |
| ③ | その人の頭の中の問いは | 相手の関心・不安 |
| ④ | 根拠になる数字や事実は | 説得材料 |
| ⑤ | 似た種類の過去の文章（任意） | 文体の学習用 |

**相手が誰か迷ったら「忙しい・せっかち・短気・コストに厳しい意思決定者」を想定する。** 最初の数行で読むのをやめ、YesかNoで答えたいだけの人。その人が「それで！」の一言で終われる文章が、優れた提案文書。

## 対話の進め方

1. **受け取る**：持ち込まれた提案を読み、分かる材料を①〜⑤に仮置きする
2. **上流を埋める**：不足する①〜③を1問ずつ、推奨案つきで確認する
3. **根拠を詰める**：④を引き出す。数字がなければ体験談へ誘導する。⑤があれば文体の特徴をつかむ
4. **パーパス整合を確認する**：`references/company-purpose.md` を読み、提案全体がパーパス10項目と矛盾しないか確認する。自然な接点があればどこに1文織り込むかを決める（くどくなるなら省略）
5. **選択肢を絞る**：複数案がある場合、基本1案・必要なら2案・最大3案に絞る。各案を1行で示し推奨を明示する
6. **出力する**：日本語版を作成し、英語へ翻訳して2版を一度に出力する（「出力フォーマット」参照）

### 既知材料のスキップ

入力（例: `my-issue.md`）に既にある材料は**聞き返さない**。①〜⑤のうち埋まっている項目はスキップし、不足分だけを1問ずつ確認してから出力へ進む。

ユーザーが「もう十分」と言えば、その時点で出力に進む。

### 質問の例（良い / 悪い）

悪い例：「これは誰に出しますか？」
良い例：「承認するのは課長ですよね。課長の一番の関心は『コスト対効果は合理的か』だと想定し、冒頭で月250€と全員Copilot申請の差額を数字で出すのがおすすめです。気になる点はありますか？」

### パーパス整合の確認（対話ステップ）

材料が揃ったら、出力前に次を確認する。

- 提案全体が `references/company-purpose.md` の10項目と矛盾しないか
- 自然な接点がある項目があれば、どの節に1文で織り込むか（独立セクションは作らない）
- 接点がない・くどくなる場合は紐づけを省略する

> 実運用では `company-purpose.md` を実在の部パーパスに差し替える。

## 根拠の強さ

```
強 ┃ 数字・データ ＞ 専門家の意見 ＞ 体験談 ＞ たとえ話 ＞ 思い込み ┃ 弱
```

ただし現実の意思決定は感情で動く。**ベストは「数字＋心を動かす話（体験談など）」**。強い数字が出せないときは、体験談や具体的なエピソードで代替してよい。

## 状況フレーミング（メンツ配慮の汎用化）

「変える・やめる」提案は、それを作った／続けてきた相手に「自分のやり方は否定されたのか」と聞こえやすい。理屈が正しくても、ここでつまずくと通らない。事実は変えず、伝え方を整える（おだて・ごまかしは不可）。

- **過去を正当化する**：「当時は妥当だった」と置き、変更は状況変化への対応として語る
- **問題を人でなく状況・数字に帰属**：「やり方が悪い」でなく「事業が伸びて環境が変わった」「新しい技術への追従が必要になった」
- **功績を立て、共同の前進にする**："あなた vs 私"でなく「これまでの仕組みを次の段階へ一緒に更新」
- **小さく・可逆にする**：試験運用や期間限定で、判断を全否定して覆す感を消す
- **否定語を避ける**：「無駄」「非効率」「間違い」を使わない
- **決定権は相手に残す**：最終判断は相手のもの、という姿勢で書く

対話では「この提案は相手が作ったもの／続けてきたものを変えるか？」を見極め、Yesなら上の配慮を強める。既存の取り組み（例: Copilot推進方針）と衝突しうる場合は、「新しい環境への変化に追従する」「会社の事情に合わせる」という状況要因として組み立て、過去の担当者や判断を否定しない。

## 文章ルール（エッセンス）

日本語版生成時は `references/writing-essence.md` を適用する。要点:

- 結論先出し（冒頭1行でお願いまで言い切る）
- 情報階層 `■ → ◎ → ・`
- 一文一義（目安30字）、過剰敬語回避
- 事実・解釈・提案の分離
- 推奨明示（`→推奨：◯◯`）
- 用語統一、数値の本文化

## 出力フォーマット

### テンプレート（各言語版の骨格）

```
【提案】<結論＝お願いを1行で。要約だけでなく「だから何をしてほしいか」まで言い切る>

■ コスト vs ベネフィット
・コスト：<数字つきのコスト>
・ベネフィット：<数字つきのベネフィット>

■ 現状
・<事実1>
・<事実2>
・<事実3（必要なら）>

■ 推奨
・案A：<1行>
・案B：<1行（必要なら）>
・案C：<1行（必要なら）>
→推奨：<案名>（<理由1行>）

■ リスク
・<リスク1> — <対策1行>
・<リスク2（必要なら）> — <対策1行>
```

- 選択肢は**基本1案、必要なら2案、最大3案**。各案は1行、説明の長文展開はしない
- パーパスとの接点は独立セクションにせず、自然なときだけ「提案する理由」やベネフィットに1文で織り込む

### 行数制約

- 各言語版は**内容行15〜20行**（空行は数えない）
- 20行を超えたら次の順に削る: **背景説明 → リスク詳細 → 選択肢の説明文**
- 必ず残す: **結論・コスト数字・推奨案・ベネフィット**

### 生成順序

1. **日本語版**を `writing-essence.md` のルールに則って作成する
2. 日本語版を**英語へ翻訳**する（英語版をゼロから別に書かない）
3. **英語版のみ**階層記号 `■` `◎` `・` をバレット `-` に変換する
4. 日英は**同じ論点・同じトーン**。言語のみ変える（読者別の内容最適化はしない）

### 出力の区切り方

1つの出力内を次の見出しで区切り、各版をコードブロック（プレーン文・markdown装飾なし）で出力する。

```
## 日本語版

```
（日本語の提案文）
```

## English Version

```
（英語の提案文）
```
```

- 出力する提案文では太字（`**`）などのmarkdown装飾を使わない
- 送るときは必要な言語版だけコピーする

### 絵文字

- **原則使わない**（【提案】タグもテキストのみ）
- 使う場合は**パターンを統一**する（見出し全部 or 本文全部）
- **混在禁止**: 見出し1つだけ絵文字、本文だけ絵文字、などバラバラは避ける

## 品質チェック

出力する前に、提案文がチェックリストを満たすか確認する。満たさない項目は直してから出力する。
