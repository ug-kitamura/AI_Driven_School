# レッスン原稿レビュースキル

`contents/` に着地した原稿を読み、**直さずに指摘する**。何を反映するかは人が決める。

## 責任範囲

| やる | やらない |
|---|---|
| 原稿の整合と品質の点検 | **原稿の修正**——指摘だけを出す |
| 指摘ファイルの書き出し | 構成の決め直し・レッスンの追加削除（`dx-training-plan` の担当） |
| リリース可否の判定材料の提示 | リリース判断そのもの |
| 受講順の現状に照らした検査 | `.meta.json` の書き換え・シリーズ間の辺の張り替え |
| 出典リンクが生きているかの確認 | **ファクトチェック**——`dx-training-create` が執筆時に済ませている |

## 依存

- `contents/` — 検査対象。レッスン本文と各階層の `.meta.json`
- `contents-plan/plans/` — 計画書。曼陀羅の**意図**の参考であって正ではない（→ 受講順の正本）
- `dx-training-create/references/design-principles.md` — 内容品質と、書いてはいけないものの基準
- `dx-training-create/references/lesson-template.md` — frontmatter・空欄・画像・出典の**形式**の基準
- `dx-training-create/references/model-answer/` — トンマナの基準。**無くてよい**（→ `references/quality-checks.md`）
- `contracts/image-slot-contract.md` — 画像コメントの書式
- `contracts/agent-write-contract.md` — run ディレクトリの作法
- `lib/schema.ts` / `lib/lesson-frontmatter.ts` / `lib/lesson-tags.ts` — frontmatter と meta の正本

## 進め方

このチェックリストを写して進捗を管理する。

- [ ] フェーズ1: 範囲と深さを確認する
- [ ] フェーズ2: 受講順の現状を読む
- [ ] フェーズ3: 整合チェック
- [ ] フェーズ4: 公開前レビュー（選ばれたときだけ）
- [ ] フェーズ5: 指摘をまとめ、リリース可否を出す

## フェーズ1: 範囲と深さを確認する

**聞くのは冒頭の1回だけ。** 対象シリーズ（複数可）と深さをまとめて確認し、以後は聞き直さない。実行中に判断の分かれる箇所が出ても、その場で質問せず advisory の指摘として記録して続ける。

深さは次の2つだけを出す。**検査項目を並べたメニューを見せない**——選択肢が増えるほど人は選べなくなる。

```
どこまでレビューしますか？

  1. 整合チェック（推奨・短時間）
     名前・受講順・「次のレッスンで」等の参照・画像や空欄の残りなど、
     構成をいじると壊れやすい箇所を点検します。
     → コースの追加・並び替え・改名のあとの確認に

  2. 公開前レビュー（時間がかかります）
     整合チェックに加えて、誤字・文章の品質・トンマナの統一・
     受講者目線での通し読みまで行います。
     → 受講者にリリースする前の総点検に
```

- **既定は 1。** 迷ったらこれを勧める。回す頻度が高いのはこちらで、軽いから習慣にできる
- ユーザーが「公開前に」と言っている文脈なら 2 を勧めてよい。**選択は妨げない**
- 「層」「第1層」のような**内部の呼び名を対話に出さない**。ユーザーが選ぶ材料は、どんな場面で使うものかだけ

## フェーズ2: 受講順の現状を読む

対象シリーズの各階層の `.meta.json` を読み、コースとレッスンの並び、シリーズ間の接続を把握する。以降の検査はすべてこの現状を基準にする。

### 受講順の正本

**正は `.meta.json`。計画書ではない。** シリーズ間の辺は create の実行後に人が Studio 上で張り、コースを足すたびに張り替えられる。計画書は張られる前の意図を書いたものなので、**ずれていても `.meta.json` を誤りと断定しない**。ずれは advisory の指摘として報告し、判断を人に渡す。

## フェーズ3: 整合チェック

手順は [`references/integrity-checks.md`](references/integrity-checks.md)。**深さの選択に関わらず必ず通る。**

## フェーズ4: 公開前レビュー

フェーズ1で公開前レビューが選ばれたときだけ実行する。手順は [`references/quality-checks.md`](references/quality-checks.md)。

## フェーズ5: 指摘をまとめる

指摘を run ディレクトリへ書き出し、リリース可否を1行で示す（→ 出力規約）。**チャットに流して終わらせない。** 指摘は後工程の作業リストであり、残らなければ届かない。

---

## 出力規約

出力先は run ディレクトリ（`contents-plan/runs/<yyyymmdd>-review/`）。作法は [`contracts/agent-write-contract.md`](../../../contracts/agent-write-contract.md) に従う。**`contents/` には何も書かない。**

| 置くもの | 中身 |
|---|---|
| `summary.md` | リリース可否の1行、blocking の件数、分類ごとの内訳 |
| `findings/<レッスン名>.md` | そのレッスンに閉じた指摘 |
| `findings/横断.md` | 複数のレッスンにまたがる指摘（参照の整合・受講順・ストーリー・メタファー） |

レッスンが増えれば指摘ファイルも増えるので、`findings/` に畳む。同じ日に2回目を回すときは、既存ファイルに連番を足さず**別の run ディレクトリを作る**。

指摘1件に持たせるもの:

| 項目 | 中身 |
|---|---|
| 対象 | ファイルと位置（見出しか行） |
| 分類 | **コードと名称を併記する**（「G: 次・前参照の整合」）。コードだけの表記はしない。コードの定義は references |
| 指摘 | 何がどうずれているか。**そう判断した根拠を書く**——人が検証できないと採否を決められない |
| 修正案 | どう直すかの案。直すのは人 |
| 重さ | blocking / advisory |

**blocking は「受講者に届いたら実害が出る」ものだけ。** 名前や参照の食い違い、埋まっていない空欄、出典の形式違反など。判断に幅があるもの、好みに寄るもの、外部要因で揺れるもの（リンクの到達失敗など）は advisory にする。

サマリには **blocking の件数とリリース可否**を1行で書く。blocking が0件なら通過。

## 制約

- **`contents/` を変更しない。** 原稿・`.meta.json` とも読むだけ
- **計画書・`contracts/`・他スキルを変更しない**
- **修正案を本文へ反映しない。** 「ついでに直しました」をやらない——採否の判断が人から奪われる
- **根本的な作り直しを提案しない。** 指摘は直せる粒度で出す
- **「問題なし」は完璧を意味しない**
- 出力は日本語
- 理想環境（Claude Code・強いモデル）を前提にする。Studio の Pane4 Agent では動かない
