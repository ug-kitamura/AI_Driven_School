# レッスンの型

`contents.md` 1本の**形式**を決める。何を書けば良い草稿になるかという**質**の判断材料は [design-principles.md](design-principles.md) にある。両方を使う。

## frontmatter

キーの集合と並び順の正本は `lib/lesson-frontmatter.ts` の `serializeLessonDocument`。ここで決めるのは**値の選び方**だけ。

| キー | 値の決め方 |
|---|---|
| `series` / `course` | 出力先のディレクトリ名と一致させる。ずれてもエラーにはならないが、Studio が読み書きするたびにディレクトリ名で上書きされる（正本は `lib/lesson-frontmatter.ts` の `normalizeLessonMeta`）。ディスク上のファイルは古い値のまま残るので、自分で合わせる |
| `lesson` | レッスンのディレクトリ名と一致させる。ずれるとディスク側の名前で上書きされる |
| `status` | `in_progress`。本文を書いた時点で未着手ではない。完成後に `done` へ上げるのは人がやる |
| `description` | 1行で書く。改行を含めない（パーサが行単位で読む） |
| `tags` | 小文字英数とハイフンのみ。正本は `lib/lesson-tags.ts` の `TAG_PATTERN`。弾かれた値は黙って捨てられる |
| `estimated_minutes` | 計画書の時間をそのまま入れる |
| `author` | この run の執筆者名（聞く手順は `SKILL.md`）。**空にしない** |

`id` は書かない（表示名から導出される）。`content` も書かない（ファイル本文そのもの）。

## 受講者の前提

読者は**社内の業務環境で学ぶ社員**。この前提から外れる書き方をしない。

| やらない | なぜ |
|---|---|
| 私物 PC・社外の共有フォルダ・個人所有の資料を代替手段として出す | 業務環境以外は使わない。演習の代替案も業務環境の中で完結させる |
| 「英語の文言を読める必要はまだありません」のような断り | 基礎的な英語は読める。短い画面表示やメッセージは、断りを置かず意味を説明する |

## 章立て

見出しは `##`。冒頭に `# <レッスン名>` を1本置く。章の並びと「やってみる」を全レッスンに置くことは計画書の既定方針で、**章を足したり順を変えたりしない**。

| 章 | 役割 | 目安 |
|---|---|---|
| 学習目標 | なぜこれを学ぶかを、読者が経験している場面で受け取らせる | 3〜5行 |
| 本文 | `###` で節に割る。1節につき読者の問いを1つ解く | 全体の6〜7割 |
| やってみる | 5分以内で手が動く課題を1つ。やること・前提・考えなくてよいことを書く | 課題1つ＋解答例 |
| まとめ | 持ち帰る骨を数で名指しする（「この3つだけ」） | 3〜4行 |
| 確認問題 | 自分の言葉で言い換えさせる・学んだ概念で分類させる。**本文を読み返せば自分で確かめられる問いに限る**（解答は付けない）。計算や複数選択のように解答が無いと正誤の分からない問いは出さない | 1〜2問 |

分量は `estimated_minutes` から逆算する。読了は400字≒1分（換算の正本は `lib/lesson-frontmatter.ts` の `estimateDraftMinutes`）。手を動かす時間がその外側に乗るので、本文を時間いっぱいまで書かない。

解答例は `<details>` に畳んで**1行**に収める。完成コード一式を置いてよいのはハンズオンのレッスンだけ。

## 本文の書き方

### 前後のレッスンへの参照

**記述的に書く。**「前のレッスンで」「三大エリアのレッスンで」。`L06` のようなレッスン番号を読者向け本文に書かない——読者に番号は見えておらず、順序が変われば嘘になる。

### 表

項目と属性が対応づく情報は**表で示す**。コマンドと役割の一覧、複数手段の比較、利点と欠点。箇条書きに畳むと対応関係が読み取れなくなる。

### アラート

補足・注意は GitHub アラートで示してよい。多用しない——本文の流れで書けるものは本文で書き、**読み飛ばされると困る一点**にだけ使う。

| 記法 | 使いどころ |
|---|---|
| `> [!NOTE]` | 知っておいてほしい補足 |
| `> [!TIP]` | よりうまくやるコツ |
| `> [!IMPORTANT]` | 成功に必要な重要事項 |
| `> [!WARNING]` | すぐ対応が要る、危険を伴いうる内容 |
| `> [!CAUTION]` | 実行すると悪影響・リスクがある内容 |

### コードブロック

フェンスには**必ず言語を指定する**（``` ```bash ``` / ``` ```python ``` 等）。変更前後を見せる場面は ``` ```diff ``` を使い、`+` と `-` で示す。

### コマンドの出力

**コマンドを実行できる環境なら、実際に実行して出力を確認してから書く。** 実行できない環境では、推測した出力を断定形で書かない。

出力を短くして載せるときは「要点だけを抜き出しています」と**その場で断る**。省略を黙ってやると、読者は自分の画面との差分を自分のミスだと思う。

## 穴の記法

設計メモの3段梯子（DB 検索 → 一括問合せ → 穴。手順は `SKILL.md`）で解決できなかったものは、blockquote で穴として残す。**プレビューに残るので埋め忘れが見える。**

| 記法 | 何の穴か | 埋める場所 |
|---|---|---|
| `> **社内**:` | 社内固有のテキスト（手順・呼称・ルール・窓口） | 後工程の穴埋め作業 |
| `> **社内画像**:` | 社内画面の撮影・録画（計画書の `【撮】` `【録】` に対応） | 後工程の穴埋め作業 |
| `> **素材**:` | 社内ではないが人手が要る画像 | どこでも |

- **`社内` の穴は中身を書かず、答えるべき問いを箇条書きにする。** 期待する形式と分量も指定する（「番号付き手順3〜5ステップ / 200〜300字」のように）。穴は DB に無く、ユーザーもその場で出せなかった情報である。後工程の作業者がこの実行の文脈なしで埋められるよう、**穴は誰にも聞かずに自己完結している必要がある**
- **`社内画像` の穴は撮影指示を具体的に書く。** 何の画面を、どの状態で撮り、どこをマスクするか。中身を知らなくてもここは具体化できる——テキストと画像で「具体的」の意味が違う
- **穴の周囲に一般論を書かない。** 導入文と次への接続文だけを書く。一般論は埋め忘れたときそのまま公開され、文章として自然に読めるためレビューでも穴と認識されない
- 穴は後工程の穴埋め作業で、AI の支援を受けて埋められる。**AI への指示として読める粒度**で書く

## 画像

AI 生成で埋まる図は HTML コメントで枠を置く。書式は `contracts/image-slot-contract.md` に従い、**印や接頭辞を足さない**。Studio はコメント本文をそのまま生成プロンプト欄へ送るため、印を付けるとプロンプトに混入する。

素材を待たずに済む図は**アスキーアート**で書く。穴を1つ減らせる。

図を置いたら、どこを見てほしいかを本文で指定する。

### 実在アプリの画面を求めるとき

VSCode や GitHub のような**実在するアプリの画面**を頼むスロットには、代替手段の断りをプロンプトの末尾に1行足す。

```
実際の画面との一致が重要な図。生成品質が悪い場合はスクリーンショットで代用すること。
```

生成の難しさを事前に見積もって書き分けない——生成は人がその場で回すので、出来を見てから判断できる。**概念図やイメージには足さない**（代替手段が要らない）。

## 出典

Web で調べた事実には出典を添える。**斜体1行**を、本文の該当箇所の直後に置く。脚注や巻末の参考文献リストは作らない。

**URL を裸で書かない。タイトル文字列にリンクを埋め込む。** 長い URL（日本語をパーセントエンコードしたものは特に）が本文に露出すると読む線が切れる。

```markdown
*出典: [Pro Git 日本語版「使い始める - Gitの基本」](https://git-scm.com/book/ja/v2/...)（2026年8月取得）*
```

社内コンテキスト DB のアイテムを本文素材に使った箇所にも、同じ形式で出典を添える。リンク先はアイテムの `source_url`。日付は取得日ではなく**ソース最終更新日**を「YYYY年M月D日更新」で書く。最終更新日が無いアイテムは括弧ごと省略する。

```markdown
*出典: [NMS Git ブランチ運用ルール](https://intra.example.com/git-rules)（2026年8月1日更新）*
```

## 書き終えたら

本文を通しで1度読み、次の2点を見る。

- **誤字と表記ゆれ** — 同じものを2つの呼び方で書いていないか（`最終版_2` と `最終版2`、frontmatter の `description` と本文の食い違い）、半角スペースが紛れていないか
- **単純化した箇所に断りがあるか** — 判断と落とし方は [design-principles.md](design-principles.md) の「単純化していることを明示する」

設計メモとの突き合わせは執筆フェーズの手順にある（`SKILL.md`）。
