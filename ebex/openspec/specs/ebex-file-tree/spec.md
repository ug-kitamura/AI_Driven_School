## Requirements
### Requirement: 表示対象

Pane 1 は `workspace/` 直下の各プロジェクトフォルダと、その配下の **全階層** のサブフォルダ・ファイルを再帰ツリーとして表示しなければならない（SHALL）。`session.json` は Pane 1 に表示してはならない（MUST NOT）。⚠ サブフォルダ警告アイコンは表示してはならない（MUST NOT）。

#### Scenario: ネストしたフォルダとファイルが表示される

- **WHEN** `workspace/20260706-demo/sub/` に `deep.md` が存在する
- **THEN** Pane 1 に `20260706-demo` → `sub` → `deep.md` の階層が表示される

#### Scenario: session.json が非表示

- **WHEN** プロジェクトフォルダに `session.json` が存在する
- **THEN** Pane 1 のファイル一覧に `session.json` は表示されない

#### Scenario: サブフォルダ警告がない

- **WHEN** プロジェクトフォルダ内にサブフォルダが存在する
- **THEN** 警告アイコンは表示されずサブフォルダがツリーに表示される

### Requirement: Pane 1 ヘッダーロゴ

Pane 1 ヘッダーの「EBEX」テキスト左に `images/logo_small.png` を表示しなければならない（SHALL）。

#### Scenario: ロゴとタイトルが並ぶ

- **WHEN** ワークスペースが表示される
- **THEN** Pane 1 ヘッダーにロゴ画像と「EBEX」が左から順に表示される

### Requirement: 検索 UI

Pane 1 の検索行に下方向の区切り線（`border-b`）を表示してはならない（MUST NOT）。検索文字列が空でないとき、検索入力のクリアボタンが提供されなければならない（SHALL）。クリアボタンをクリックしても他の UI 要素の位置がずれてはならない（MUST NOT）。クリアボタンは短押し・長押しのいずれの操作でも確実に検索文字列を空にしなければならない（SHALL）。検索ボックスの右端は、Pane 1 ヘッダー右端の「フォルダ追加」ボタンの右端に揃えられなければならない（SHALL）。

#### Scenario: 検索下に横線がない

- **WHEN** ワークスペースが表示される
- **THEN** 検索バー直下に水平区切り線が存在しない

#### Scenario: 検索クリア

- **WHEN** ユーザーが検索ボックスに文字を入力する
- **THEN** クリアボタンが表示され、クリックで検索文字列が空になる

#### Scenario: クリアボタンの位置が安定している

- **WHEN** ユーザーが検索ボックスに文字を入力してからクリアボタンをクリックする
- **THEN** クリアボタンや検索入力の表示位置はクリック前後で変化しない

#### Scenario: 長押しでもクリアされる

- **WHEN** ユーザーがクリアボタンを長押しする
- **THEN** 検索文字列が空になる

#### Scenario: 検索ボックス幅がヘッダーボタンに揃う

- **WHEN** ワークスペースが表示される
- **THEN** 検索ボックスの右端は Pane 1 ヘッダーの「フォルダ追加」ボタンの右端と同じ横位置になる

### Requirement: 右クリックコンテキストメニュー

フォルダ行の右クリックメニュー項目は、表示順を **add folder → add file → rename → copy（該当時）→ paste（該当時）→ delete** とし、**delete は常に最後**でなければならない（SHALL）。プロジェクトフォルダ（`folderPath` に `/` を含まない）の場合は「add folder」「add file」「rename」「paste」「delete」としなければならない（SHALL）。サブフォルダ行の場合は「add folder」「add file」「rename」「copy」「paste」「delete」としなければならない（SHALL）。ファイル行のメニュー項目は「rename」「copy」「paste」、**add to chat**、**add favorite または remove favorite（状態に応じて排他）**、「delete」の順としなければならない（SHALL）。`(no file)` 行のメニュー項目は「add folder」「add file」「paste」としなければならない（SHALL）。メニュー項目の表示言語は英語でなければならない（SHALL）。「add folder」「add file」「rename」「copy」「paste」「add to chat」「add favorite」「remove favorite」の hover 背景色・文字色は、ツリー行の選択・強調時と同じグレー系トークンでなければならない（SHALL）。「delete」項目の hover 配色は destructive（赤系）のまま維持しなければならない（SHALL）。クリップボードが空のとき paste は無効（disabled）でなければならない（SHALL）。各メニュー項目はラベルテキストの前に、項目に対応する lucide アイコンを表示しなければならない（SHALL）：add folder は `FolderPlus`、add file は `FilePlus`、rename は `Pencil`、copy は `Copy`、paste は `ClipboardPaste`、delete は `Trash2`、add to chat は `MessageSquarePlus`、add favorite は `Star`（アウトライン）、remove favorite は `StarOff`。アイコンの色は個別指定してはならず（MUST NOT）、`ContextMenuItem` の `variant` に連動した既存の自動配色（muted はグレー系、destructive は赤系）に従わなければならない（SHALL）。

#### Scenario: サブフォルダ行の右クリックメニュー

- **WHEN** ユーザーが `demo/sub` フォルダ行を右クリックする
- **THEN** add folder、add file、rename、copy、paste、delete の順で、それぞれ対応するアイコン付きの英語メニューが表示される

#### Scenario: プロジェクトフォルダ行の右クリックメニュー

- **WHEN** ユーザーが `demo` プロジェクトフォルダ行を右クリックする
- **THEN** add folder、add file、rename、paste、delete の順で、それぞれ対応するアイコン付きの英語メニューが表示され、copy は含まれない

#### Scenario: ネストファイルの右クリックメニュー

- **WHEN** ユーザーが `sub/deep.md` ファイル行を右クリックする
- **THEN** rename、copy、paste、add to chat、add favorite または remove favorite、delete の順で、それぞれ対応するアイコン付きの英語メニューが表示される

#### Scenario: add to chat の位置とアイコン

- **WHEN** ユーザーがファイル行を右クリックする
- **THEN** `MessageSquarePlus` アイコン付きの add to chat が paste と favorite 項目の間に表示される

#### Scenario: 別プロジェクトのファイルでは add to chat が無効

- **WHEN** Agent チャットの対象プロジェクトが `demo` の状態で、ユーザーが別プロジェクト `other` 内のファイル行を右クリックする
- **THEN** add to chat は無効（disabled、グレー表示）であり、クリックしても添付は追加されない

#### Scenario: フォルダ行に add to chat がない

- **WHEN** ユーザーがプロジェクトフォルダまたはサブフォルダ行を右クリックする
- **THEN** add to chat は表示されない

#### Scenario: no file 行の右クリックメニュー

- **WHEN** ユーザーが `no file` 行を右クリックする
- **THEN** add folder、add file、paste の順で、それぞれ対応するアイコン付きの英語メニューが表示される

#### Scenario: 通常項目の hover はグレー

- **WHEN** ユーザーが右クリックメニューの rename 項目にマウスを重ねる
- **THEN** アイコンを含む背景色・文字色は青系ではなくグレー系トークンで表示される

#### Scenario: 削除項目の hover は赤系のまま

- **WHEN** ユーザーが右クリックメニューの delete 項目にマウスを重ねる
- **THEN** `Trash2` アイコンを含む背景色・文字色は destructive（赤系）で表示される

#### Scenario: favorite 項目のアイコンが状態に応じて切り替わる

- **WHEN** ユーザーがお気に入り未登録のファイル行を右クリックする
- **THEN** `Star`（アウトライン）アイコン付きの add favorite が表示される
- **WHEN** ユーザーがお気に入り登録済みのファイル行を右クリックする
- **THEN** `StarOff` アイコン付きの remove favorite が表示される

### Requirement: ツリー行の視覚フィードバック

ファイルまたは `no file` が選択されているとき、当該選択行のテキストのみ太字（`font-semibold`）でなければならない（SHALL）。フォルダ行は、いかなる状態でも太字にしてはならない（MUST NOT）。太字の表示は選択状態にのみ依存し、カーソル位置（フォーカス）や右クリック中かどうかによって変化してはならない（MUST NOT）。行の背景色（`--workspace-tree-row` トークン、グレー系）は、当該行が現在カーソル位置である場合、右クリックでコンテキストメニューが開いている場合、またはマウスオーバーされている場合にのみ表示されなければならない（SHALL）。選択中のファイル行または `no file` 行であっても、カーソル位置がその行から他行へ移動した場合は、背景色を通常時（非カーソル・非ホバー）と同じ状態に戻さなければならない（SHALL）。青系（`accent` 等）のトークンを行背景およびフォーカスリングに用いてはならない（MUST NOT）。いずれの行背景色も、Pane 1 の通常時の背景色と同一であってはならない（MUST NOT）。選択中のファイル行または `no file` 行にマウスオーバーしても、背景色は選択時と同じ濃さのままで変化してはならない（MUST NOT）。祖先フォルダ行を、選択中ファイルの強調のために `--workspace-tree-row` の行背景色でハイライトしてはならない（MUST NOT）。選択中プロジェクトフォルダの強調は、行・ブロックの背景色を変えず左辺の縦アクセントレールで行うものとし、別要件「選択中プロジェクトフォルダの強調」で定義する。

#### Scenario: ファイル選択時の太字

- **WHEN** ユーザーが `20260707-demo/sub/notes.md` を選択する
- **THEN** `notes.md` 行のみ太字で表示される

#### Scenario: no file 選択時の太字

- **WHEN** ユーザーが空フォルダの `no file` 行を選択する
- **THEN** 当該 `no file` 行のみ太字で表示される

#### Scenario: フォルダ行は選択時に背景色が変わらない

- **WHEN** ユーザーが `20260707-demo/sub/notes.md` を選択する
- **THEN** `20260707-demo` 行と `sub` 行に `--workspace-tree-row` の行背景色は付かない

#### Scenario: フォルダ行はホバー時のみ背景色が変わる

- **WHEN** ユーザーが選択されていないフォルダ行にマウスを重ねる
- **THEN** その行の背景色が `--workspace-tree-row` のグレー系で表示される

#### Scenario: ファイル行のホバーと選択の背景色が同一

- **WHEN** ユーザーがファイル行を選択する、または選択されていないファイル行にマウスを重ねる
- **THEN** 背景色はいずれも同一の `--workspace-tree-row` グレー系で表示される

#### Scenario: 選択中ファイル行のホバーで背景色が変わらない

- **WHEN** ユーザーが選択中のファイル行にマウスを重ねる
- **THEN** 背景色は選択時と同じ濃さのままであり、ホバーによって変化しない

#### Scenario: カーソルが選択行から離れると背景色が元に戻る

- **WHEN** ユーザーがファイルを選択した状態で `↓` キーを押しカーソル位置を別の行へ移動する
- **THEN** 選択されたファイル行は太字のままだが背景色は非カーソル・非ホバー時と同じ状態に戻り、新たにカーソル位置となった行のみ背景色がグレーになる

#### Scenario: レールによる強調は祖先行のグレー背景を付けない

- **WHEN** ユーザーが `20260707-demo/sub/notes.md` を選択し、`20260707-demo` が選択中プロジェクトフォルダとして左辺レールで強調される
- **THEN** `20260707-demo` 行と `sub` 行には `--workspace-tree-row` のグレー行背景は付かず、左辺のアクセントレールのみが適用される

#### Scenario: 行内のボタン要素にフォーカスリングが表示されない

- **WHEN** ユーザーがファイル名やフォルダの chevron をクリックする
- **THEN** クリックされた要素にブラウザ既定の青いフォーカスアウトラインは表示されない

### Requirement: フォルダ行の開閉と選択

フォルダツリーの展開・折りたたみは、フォルダ行左端の chevron ボタンのクリック、またはプロジェクトフォルダ行・サブフォルダ行のシングルクリック（フォルダ名を含む行本体の1回クリック）で操作できなければならない（SHALL）。フォルダ行をシングルクリックしたとき、システムは当該フォルダの展開状態を切り替え、カーソル位置を当該フォルダ行に設定しなければならない（SHALL）。フォルダ行のシングルクリックで、現在選択中のファイル選択を変更してはならない（MUST NOT）。フォルダ行のシングルクリックで、フォルダ内の先頭ファイルを自動選択してはならない（MUST NOT）。コンテキストメニュー操作直後のポインター開閉抑止は、フォルダ行のシングルクリックに対して chevron ボタンと同一の条件で適用されなければならない（SHALL）。chevron ボタンのクリックによる展開・折りたたみおよびフォーカス挙動は、本変更以前と同等でなければならない（SHALL）。フォルダ行のダブルクリックに対して、開閉のための専用の処理を行ってはならない（MUST NOT）。

#### Scenario: chevron で展開・折りたたみ

- **WHEN** ユーザーがフォルダ行の chevron ボタンをクリックする
- **THEN** 当該フォルダの子要素の表示が展開または折りたたみされる

#### Scenario: フォルダ行シングルクリックで展開する

- **WHEN** ユーザーが折りたたまれたプロジェクトフォルダまたはサブフォルダの行をシングルクリックする
- **THEN** 当該フォルダが展開され、カーソル位置は当該フォルダ行になり、Pane 2 の選択中ファイルは変化しない

#### Scenario: フォルダ行シングルクリックで折りたたむ

- **WHEN** ユーザーが展開済みのプロジェクトフォルダまたはサブフォルダの行をシングルクリックする
- **THEN** 当該フォルダが折りたたまれ、カーソル位置は当該フォルダ行になり、Pane 2 の選択中ファイルは変化しない

#### Scenario: フォルダ行シングルクリックではファイル選択を維持

- **WHEN** ユーザーが `20260707-demo/sub/notes.md` を選択した状態で、別のフォルダ行をシングルクリックする
- **THEN** 選択中のファイルは `notes.md` のままであり、エディタの表示対象も変わらない

#### Scenario: フォルダ行ダブルクリックでは元の展開状態に戻る

- **WHEN** ユーザーが折りたたまれたフォルダ行をダブルクリックする
- **THEN** 2回のクリックで展開と折りたたみが順に行われ、最終的な展開状態はクリック前と同じ折りたたみ状態になる

#### Scenario: chevron クリックで二重に開閉しない

- **WHEN** ユーザーがフォルダ行の chevron ボタンを1回クリックする
- **THEN** 展開状態は1回だけ切り替わり、行本体のシングルクリック処理は実行されない

### Requirement: 検索フィルタ

Pane 1 上部に検索ボックスが提供されなければならない（SHALL）。キーワードにマッチするフォルダ名・ファイル名、またはそれらを含む祖先パスを持つノードのみが表示されなければならない（SHALL）。検索行の下に区切り線を表示してはならない（MUST NOT）。

#### Scenario: ネストファイル名でフィルタ

- **WHEN** ユーザーが検索ボックスに「deep」と入力する
- **THEN** `deep.md` を含むパスとその祖先フォルダのみが表示される

#### Scenario: フォルダ名でフィルタ

- **WHEN** ユーザーが検索ボックスに「sub」と入力する
- **THEN** 名前に `sub` を含むフォルダとその祖先・子孫のマッチが表示される

### Requirement: フォルダ追加

Pane 1 ヘッダー右上のフォルダ追加ボタンからモーダルが開かれなければならない（SHALL）。モーダルフッターには左からキャンセル・自動入力・確定の順でボタンが配置されなければならない（SHALL）。自動入力ボタンは入力欄に名前をセットするのみとし、モーダルを閉じてはならない（MUST NOT）。フォルダ作成は確定ボタンでのみ実行されなければならない（SHALL）。自動入力時の名前は `{YYYYMMDD}-untitled{N}` とし、N は同日の既存フォルダ名 `^{YYYYMMDD}-untitled(\d+)$` の最大値 + 1、存在しない場合は 1 としなければならない（SHALL）。作成された新規フォルダ自身は既定で折りたたみ状態（展開しない）でなければならず、作成に伴う選択変更によって自動展開されてはならない（MUST NOT）。フォルダ作成成功後、システムはカーソル位置を新規フォルダの行に設定し、当該フォルダの `no file` を選択状態にしなければならない（SHALL）。

#### Scenario: 自動入力で名前がセットされる

- **WHEN** ユーザーがフォルダ追加モーダルで「自動入力」をクリックする
- **THEN** 入力欄に `20260707-untitled1` 形式の名前がセットされ、モーダルは開いたままである

#### Scenario: 通し番号のインクリメント

- **WHEN** `20260707-untitled1` と `20260707-untitled3` が既に存在し自動入力を実行する
- **THEN** 入力欄に `20260707-untitled4` がセットされる

#### Scenario: 確定でフォルダ作成

- **WHEN** ユーザーが自動入力後に「確定」をクリックする
- **THEN** 入力欄の名前で `workspace/` 配下にフォルダが作成される

#### Scenario: 新規フォルダは折りたたみのまま no file が選択される

- **WHEN** ユーザーがフォルダ追加を確定する
- **THEN** 新規フォルダは折りたたみ状態のまま表示され、カーソル位置は新規フォルダの行になり、Pane 2 はヘッダー `no file`・本文「ファイルが存在しません」の表示になる

### Requirement: フォルダリネーム

プロジェクトフォルダ（`workspace/` 直下、`folderPath` に `/` を含まない）の名前変更時のみ、モーダルフッターに「AI 自動入力」が表示されなければならない（SHALL）。サブフォルダの名前変更には AI 自動入力を表示してはならない（MUST NOT）。フォルダリネームダイアログの入力欄には、対象フォルダのパスから最終セグメント（フォルダ名）のみを表示しなければならない（SHALL）。確定時、システムは親パスと入力されたフォルダ名を結合して API の `toPath` を生成しなければならない（SHALL）。リネーム成功後、ツリー再読み込み（`onRefresh`）は選択状態の更新より先に完了しなければならない（SHALL）。

#### Scenario: サブフォルダリネームに AI 自動入力がない

- **WHEN** ユーザーが `20260707-demo/sub` の名前変更モーダルを開く
- **THEN** AI 自動入力ボタンは表示されない

#### Scenario: サブフォルダのリネーム入力はフォルダ名のみ

- **WHEN** ユーザーがパス `20260707-demo/sub` のフォルダをリネームし、入力欄に `sub-renamed` と入力して確定する
- **THEN** システムは API に `toPath: "20260707-demo/sub-renamed"` を送信する

### Requirement: フォルダ削除

### Requirement: Pane 1 共通エラーのメッセージボックス表示

Pane 1 の共通エラー（DnD 失敗、copy/paste 失敗、移動拒否等。モーダル内エラーは対象外）は、検索バーとツリー表示領域の間にメッセージボックスとして表示されなければならない（SHALL）。メッセージボックスは角丸（`rounded-lg`）のコンパクトな枠とし、帯状にペイン全幅へ横断してはならない（MUST NOT）。背景は `bg-destructive/10`、枠線は `border-destructive/20` 等の destructive 系トークンで視認性を確保しなければならない（SHALL）。左に警告アイコン（`AlertCircle`、`text-destructive`）、中央にエラーメッセージ（`text-sm text-destructive`）、右に dismiss 用の ✕ ボタンを配置しなければならない（SHALL）。✕ ボタンのアイコン色は警告アイコンと同じ `text-destructive` でなければならない（SHALL）。✕ ボタンはメッセージボックス内で警告アイコンおよびテキストと**垂直方向に中央揃え**でなければならない（SHALL）。✕ ボタンのクリックでエラー表示を消去できなければならない（SHALL）。ユーザーが Pane 1 上で別の操作（行クリック、キーボード操作、ファイル選択、フォルダ開閉、ダイアログを開く、検索文字列変更、copy/paste/delete 操作開始、DnD 開始等）を開始した場合、表示中のエラーは消去されなければならない（SHALL）。マウスホバーのみではエラーを消去してはならない（MUST NOT）。新しいエラーが発生した場合は直前のエラーを置き換えなければならない（SHALL）。タイマーによる自動消去を設けてはならない（MUST NOT）。

#### Scenario: エラーがメッセージボックスで表示される

- **WHEN** ユーザーが DnD 操作を実行し失敗する
- **THEN** 検索バーとツリーの間に角丸のメッセージボックスが表示され、警告アイコンとエラーメッセージが含まれる

#### Scenario: ✕ ボタンで消去

- **WHEN** ユーザーがエラーメッセージボックスの ✕ ボタンをクリックする
- **THEN** メッセージボックスが消える

#### Scenario: 別操作開始でエラーが消える

- **WHEN** エラーメッセージが表示されている状態で、ユーザーが別のファイル行をクリックする
- **THEN** メッセージボックスが消える

#### Scenario: ホバーだけではエラーが消えない

- **WHEN** エラーメッセージが表示されている状態で、ユーザーが別行にマウスを移動する（クリックしない）
- **THEN** メッセージボックスは表示されたままである

#### Scenario: 新しいエラーで置き換え

- **WHEN** エラー A が表示されている状態で、別の操作がエラー B を発生させる
- **THEN** メッセージボックスの内容はエラー B に置き換わる

#### Scenario: モーダル内エラーは対象外

- **THEN** エラーはダイアログ内にのみ表示され、Pane 1 のメッセージボックスは表示されない

### Requirement: ツリーカーソル位置

Pane 1 のツリーは、キーボード操作およびクリックによって移動する**カーソル位置**（現在行）を 1 行のみ保持しなければならない（SHALL）。カーソル位置は `--workspace-tree-row` 背景色で表示しなければならない（SHALL）。マウスホバーはカーソル位置を変更してはならない（MUST NOT）。ホバー時の背景色は CSS `:hover` による一時表示とし、カーソル位置の状態とは独立でなければならない（SHALL）。Pane 2 のファイル選択（太字表示）とカーソル位置は別概念であり、カーソル移動だけでは Pane 2 を変更してはならない（MUST NOT）。カーソル位置の表示に DOM focus ring（青系 `ring` / `outline`）を用いてはならない（MUST NOT）。

#### Scenario: ホバーだけではカーソルが動かない

- **WHEN** ユーザーがキーボードで `git-series-spec.md` 行をカーソル位置とした後、マウスを `notes.md` 行へ移動する（クリックしない）

### Requirement: paste/DnD 時の同名自動リネーム

paste および DnD（ペイン1 内移動、OS からのファイル/フォルダ追加）において、配置先に同名のファイルまたはフォルダが存在する場合、システムはエラーで停止せず、名前の末尾に `-{通し番号}` を付与した一意名で作成または移動しなければならない（SHALL）。ファイルの場合、拡張子の直前に `-{通し番号}` を挿入しなければならない（SHALL）（例: `test.md` → `test-2.md`）。フォルダの場合、フォルダ名末尾に `-{通し番号}` を付与しなければならない（SHALL）（例: `folder` → `folder-2`）。通し番号は、同一配置先における `{基底名}-{N}` パターン（ファイルは拡張子除く基底名）の **最大 N に 1 を加えた値** とし、N は 2 から開始しなければならない（SHALL）。`test.md` のみ存在する場合の最初の衝突名は `test-2.md` でなければならない（SHALL）。ダイアログ経由の追加・リネームにおける同名エラーは従来どおりモーダル内エラーとし、本自動リネームの対象外でなければならない（MUST NOT）。

#### Scenario: 同名ファイルを paste すると -2 が付く

- **WHEN** ユーザーが `test.md` を copy し、既に `test.md` が存在するフォルダへ paste する
- **THEN** `test-2.md` が作成される

#### Scenario: -2 存在時は -3 が付く

- **WHEN** 配置先に `test.md` と `test-2.md` が存在し、ユーザーが `test.md` を paste する
- **THEN** `test-3.md` が作成される

#### Scenario: DnD 同名衝突も自動リネーム

- **WHEN** ユーザーが外部から `report.md` をドロップし、配置先に既に `report.md` が存在する
- **THEN** `report-2.md` として作成される

#### Scenario: ダイアログ追加の同名は従来どおりエラー

- **WHEN** ユーザーが add file ダイアログで既存ファイルと同名を入力して確定する
- **THEN** モーダル内にエラーが表示され、自動リネームは行われない

### Requirement: 操作後のカーソル位置追従

Pane 1 上でフォルダ・ファイルの追加、リネーム、削除、paste、ペイン内ドラッグ&ドロップによる移動、または OS からのドラッグ&ドロップインポートが成功した場合、システムはカーソル位置（`focusedRowId`）を操作の結果に応じた行へ設定しなければならない（SHALL）。フォルダ追加・サブフォルダ追加・ファイル追加・フォルダリネーム・ファイルリネーム・paste・ペイン内移動の場合、カーソル位置は操作対象（結果）の行でなければならない（SHALL）。**カーソル位置の設定は、ツリー再読み込み（`onRefresh`）完了後に行われなければならない（SHALL）。** ファイル追加成功時は、Pane 2 で当該ファイルを開き（選択状態にし）、カーソル位置も当該ファイル行に設定しなければならない（SHALL）。OS からのドラッグ&ドロップインポートの場合、カーソル位置はドロップ先フォルダの行でなければならない（SHALL）。削除の場合、カーソル位置は削除対象の親フォルダの行でなければならない（SHALL）。削除対象に親フォルダが存在しない場合（プロジェクトフォルダ自体を削除した場合等）、カーソル位置は現在開いているファイルの行でなければならない（SHALL）。開いているファイルも存在しない場合、カーソル位置は設定しなくてよい（MAY）。

#### Scenario: フォルダリネーム後にカーソルが新しい行へ移動する

- **WHEN** ユーザーがフォルダ `demo/sub` を `demo/sub-renamed` にリネームする
- **THEN** カーソル位置は `demo/sub-renamed` の行になる

#### Scenario: ファイル追加後に Pane 2 で開きカーソルがファイル行になる

- **WHEN** ユーザーが `demo/sub` に `new.md` を add file で追加する
- **THEN** `onRefresh` 完了後、Pane 2 で `new.md` が開かれ、カーソル位置は `new.md` の行になる

#### Scenario: サブフォルダ追加後にカーソルが新フォルダ行になる

- **WHEN** ユーザーが `demo` にサブフォルダ `inner` を add folder で追加する
- **THEN** `onRefresh` 完了後、カーソル位置は `demo/inner` のフォルダ行になる

#### Scenario: ファイル削除後にカーソルが親フォルダへ移動する

- **WHEN** ユーザーが `demo/sub/notes.md` を削除する
- **THEN** カーソル位置は `demo/sub` フォルダの行になる

#### Scenario: プロジェクトフォルダ削除後にカーソルが開いているファイルへ移動する

- **WHEN** ユーザーが空のプロジェクトフォルダ `demo-empty` を削除し、別のプロジェクトフォルダ内で `notes.md` が開かれている
- **THEN** カーソル位置は `notes.md` の行になる

#### Scenario: paste 後にカーソルが貼り付け結果の行へ移動する

- **WHEN** ユーザーが `notes.md` をコピーし、同名ファイルが存在する `sub` フォルダへ貼り付ける（自動リネームが行われる）
- **THEN** カーソル位置は自動リネームされた新しいファイル名の行になる

#### Scenario: OS からのインポート後にカーソルがドロップ先フォルダへ移動する

- **WHEN** ユーザーが OS からフォルダ構造を `demo` フォルダへドロップする
- **THEN** カーソル位置は `demo` フォルダの行になる

### Requirement: お気に入り

Pane 1 はファイル行に対するお気に入り登録・解除を提供しなければならない（SHALL）。お気に入りの対象は**ファイルのみ**とし、フォルダ行および `no file` 行ではお気に入り操作を提供してはならない（MUST NOT）。ファイル行の右クリックメニューには、delete の直上に **add favorite** または **remove favorite** のいずれか 1 項目のみを表示しなければならない（SHALL）。お気に入り未登録のファイルでは **add favorite**、登録済みでは **remove favorite** を表示しなければならない（SHALL）。お気に入り登録済みのファイル行の右端には黄色の ☆ アイコン（lucide `Star`、fill あり）を表示しなければならない（SHALL）。未登録ファイルでは ☆ アイコンを表示してはならない（MUST NOT）。お気に入りデータは workspace ルートの `.ebex-favorites.json` に `{ folderPath, fileName }` の配列として永続化されなければならない（SHALL）。EBEX 内でのファイルリネーム・ファイル削除・フォルダ削除・フォルダリネーム成功時は、お気に入り内の該当キーを更新または除去しなければならない（SHALL）。次回読み込み時、実在しないファイルを指すお気に入りエントリは表示から除外しなければならない（SHALL）。

#### Scenario: 未登録ファイルで add favorite を表示する

- **THEN** メニューに remove favorite が表示され、add favorite は表示されない

#### Scenario: お気に入り登録で ☆ が表示される

- **THEN** `notes.md` 行の右端に黄色 ☆ アイコンが表示される

#### Scenario: フォルダ行にお気に入りメニューがない

### Requirement: お気に入りのみ表示トグル

Pane 1 の検索行右端（検索ボックスとヘッダーボタンの間）に、お気に入りのみ表示の ☆ トグルボタンを提供しなければならない（SHALL）。トグル ON 時は、お気に入り登録済みのファイルとその祖先フォルダのみを表示しなければならない（SHALL）。トグル OFF 時はお気に入りフィルタを適用してはならない（MUST NOT）。お気に入りフィルタと名前検索・内容検索は **AND 条件** で合成されなければならない（SHALL）。

### Requirement: ファイル内容検索

Pane 1 の検索文字列の先頭が **`?`** のとき、システムはファイル名フィルタの代わりに**内容検索モード**に切り替えなければならない（SHALL）。内容検索モードでは、先頭の `?` を除いた残りの文字列をクエリとし、300ms デバウンス後にサーバー API で workspace 内のテキストファイルを再帰検索しなければならない（SHALL）。検索文字列が `?` のみ、または `?` 以降が空白のみの場合、内容検索は実行せず全件表示（他フィルタのみ適用）としなければならない（SHALL）。内容検索の対象は UTF-8 テキストとして読める主要拡張子（`.md`, `.txt`, `.json`, `.yml`, `.yaml`, `.ts`, `.tsx`, `.js`, `.jsx`, `.html`, `.htm`, `.css`, `.xml`）とし、`node_modules`、`.next`、バイナリファイルは除外しなければならない（SHALL）。マッチ判定は大文字小文字を区別せず、部分一致としなければならない（SHALL）。検索実行中はツリー上部または検索行付近に「検索中…」等の待機表示を示さなければならない（SHALL）。内容検索結果にマッチするファイルとその祖先フォルダのみを表示しなければならない（SHALL）。先頭が `?` でない検索文字列は、従来どおりクライアント側のファイル名・フォルダ名フィルタとして即時適用されなければならない（SHALL）。

#### Scenario: ? プレフィックスで内容検索モードになる

- **WHEN** ユーザーが検索ボックスに `?TODO` と入力する
- **THEN** 300ms 後に内容検索 API が呼び出され、ファイル本文に `TODO` を含むファイルのみが表示される

#### Scenario: 通常検索は即時ファイル名フィルタ

- **WHEN** ユーザーが検索ボックスに `notes` と入力する（先頭に `?` なし）
- **THEN** API を呼び出さず、ファイル名・フォルダ名に `notes` を含むノードのみが即時表示される

#### Scenario: 内容検索中の待機表示

- **WHEN** ユーザーが `?keyword` を入力し API 応答を待っている
- **THEN** 「検索中…」等の待機表示がツリー領域に示される

#### Scenario: 内容検索とお気に入りの AND

- **WHEN** ユーザーが ☆ トグルを ON にし、検索ボックスに `?meeting` と入力する
- **THEN** お気に入り登録済みかつ本文に `meeting` を含むファイルのみが表示される

### Requirement: 非空プロジェクトフォルダ削除のワーニング

プロジェクトフォルダ（`folderPath` に `/` を含まない）の削除操作において、ツリー上の当該ノードに表示上の子フォルダまたはファイル（`session.json` を除く）が 1 つでも存在する場合、システムは削除確認ダイアログを開いてはならない（MUST NOT）。代わりに、削除がブロックされる理由を説明する**ワーニングモーダル**（OK ボタンのみ、削除ボタンなし）を表示しなければならない（SHALL）。ワーニングモーダルには、プロジェクトフォルダは空の場合のみ削除可能である旨を明示しなければならない（SHALL）。表示上空（子フォルダ・ファイルなし、`session.json` のみまたは完全空）のプロジェクトフォルダの削除は、従来どおり削除確認ダイアログを表示しなければならない（SHALL）。

#### Scenario: 中身ありプロジェクトフォルダでワーニングモーダル

- **WHEN** ユーザーがサブフォルダまたはファイルを含むプロジェクトフォルダ `demo` の delete を実行する
- **THEN** 削除確認ダイアログではなく、理由を説明するワーニングモーダルが表示され、削除は実行されない

#### Scenario: 空プロジェクトフォルダは従来どおり確認ダイアログ

- **WHEN** ユーザーが表示上空のプロジェクトフォルダ `demo-empty` の delete を実行する
- **THEN** 削除確認ダイアログが表示され、確認後に削除できる

### Requirement: Agent 実行中プロジェクトフォルダの rename/delete ブロック

Agent がストリーミング実行中のプロジェクトフォルダ（およびそのプロジェクト配下として扱うパスの親プロジェクト）に対し、EBEX の File Tree からの rename および delete を実行してはならない（MUST NOT）。ユーザーが当該操作を試みた場合、実行中であるため操作できない旨を表示しなければならない（SHALL）。実行中でない他のプロジェクトフォルダ、および実行対象プロジェクト内のファイル単体の rename/delete は、本要件により制限してはならない（MUST NOT）— ただし既存の非空フォルダ削除ワーニング等の別要件は維持する。可能であれば rename/delete API も同条件で拒否しなければならない（SHALL）。

#### Scenario: 実行中フォルダのリネームを拒否する

- **WHEN** プロジェクトフォルダ A で Agent 実行中に、ユーザーが A の rename を試みる
- **THEN** リネームは行われず、実行中のため操作できない旨が表示される

#### Scenario: 実行中フォルダの削除を拒否する

- **WHEN** プロジェクトフォルダ A で Agent 実行中に、ユーザーが A の delete を試みる
- **THEN** 削除は行われず、実行中のため操作できない旨が表示される

#### Scenario: 他フォルダは操作できる

- **WHEN** プロジェクトフォルダ A で Agent 実行中に、ユーザーが別プロジェクトフォルダ B を rename する
- **THEN** B のリネームは従来どおり実行できる

### Requirement: お気に入りファイルの削除ブロック

#### Scenario: お気に入りファイルの delete がブロックされる

- **THEN** ワーニングモーダルが表示され、削除は実行されない

#### Scenario: お気に入りを含むサブフォルダの削除がブロックされる

### Requirement: no file 行の選択

システムは、空フォルダの `no file` 行を Pane 2 の選択対象として開けなければならない（SHALL）。選択値は親フォルダの `folderPath` とセンチネル `fileName` 文字列 `no file`（UI ラベルと同一）でなければならない（SHALL）。ユーザーが `no file` 行をクリックしたとき、または当該行にフォーカスがある状態で Enter を押したとき、システムは当該選択を適用しなければならない（SHALL）。選択中の `no file` 行のラベルは太字（`font-semibold`）でなければならない（SHALL）。ラベルの文字色は通常の `no file` 行と同様に muted 系のままでなければならず、選択のために色を変えてはならない（MUST NOT）。`no file` 行の選択はフォルダ行のシングルクリックによる選択変更禁止要件を変更してはならない（MUST NOT）。

#### Scenario: no file 行クリックで選択する

- **WHEN** ユーザーが空フォルダ内の `no file` 行をクリックする
- **THEN** 当該フォルダの `no file` が選択され、Pane 2 の表示対象が `no file` になる

#### Scenario: Enter で no file を開く

- **THEN** 当該フォルダの `no file` が選択され、Pane 2 の表示対象が `no file` になる

### Requirement: no file 選択の永続化と復元

システムは `no file` 選択を通常のファイル選択と同様に localStorage へ記憶しなければならない（SHALL）。次回起動時、記憶された選択の `fileName` がセンチネル `no file` であり、かつ対象 `folderPath` がツリー上に存在し子フォルダおよびファイルがともに空である場合、システムは当該 `no file` 選択を復元しなければならない（SHALL）。対象フォルダが存在しない、または空でなくなった場合は `no file` 選択を復元してはならない（MUST NOT）。同一フォルダに実ファイル名 `no file` が存在する場合は、通常のファイル選択として扱わなければならない（SHALL）。

#### Scenario: no file 選択をリロード後に復元する

- **THEN** システムは当該 `no file` 選択を復元しない

### Requirement: 選択中プロジェクトフォルダの強調

現在選択中のファイルまたは `no file`（`selectedFolderPath`）を配下に持つトップレベルプロジェクトフォルダ（`getProjectRoot(selectedFolderPath)`）を、その行および展開中の子孫を含むブロックの左辺に沿った縦のアクセントレールで恒常的に強調しなければならない（SHALL）。レールは `primary` トークンの色とし、太さ 3px でブロック左辺から 2px 外側に配置しなければならない（SHALL）。この強調は当該プロジェクトフォルダの展開・折りたたみ状態に依存してはならない（MUST NOT）。折りたたみ時はプロジェクトフォルダ行の左辺のみにレールが表示され、展開時は配下の子孫を含むブロック全体の左辺に沿ってレールが伸びなければならない（SHALL）。強調は行・ブロックの背景色を変更してはならず（MUST NOT）、枠線（`ring` / `border`）で全体を囲んではならない（MUST NOT）。レールはレイアウト幅を占有してはならず（MUST NOT）、選択プロジェクトと非選択プロジェクトの間で各行要素（特に左右）の表示位置がずれてはならない（MUST NOT）。当該プロジェクトが DnD ドロップ対象になっている間はレールを表示せず、青枠（`ring-2 ring-primary`）を優先しなければならない（SHALL）。`selectedFolderPath` が空（選択なし）の場合、いずれのプロジェクトフォルダにもレールを表示してはならない（MUST NOT）。レールはライト／ダーク両テーマで視認できなければならない（SHALL）。

#### Scenario: 折りたたみ時はプロジェクト行の左辺のみにレールが出る

- **WHEN** `demo` が折りたたまれた状態で、配下ファイルが選択されている
- **THEN** `demo` プロジェクトフォルダ行の左辺のみにアクセントレールが表示される

#### Scenario: 展開時はブロック全体の左辺にレールが伸びる

#### Scenario: 別プロジェクト選択でレールが移動する
