# EBEX スキル契約（制約と誓約）

EBEX 向けにスキルを書く／直すときに従う契約。**このファイルはスキル作者向けの正本**であり、これ単体で読んで従える（実装の内部仕様には依存しない）。

スキルは EBEX 以外（Cursor・Claude Code 等）でも動かす前提で書く。**EBEX の都合でスキルの機能を落とさない。** EBEX で使えない機能はホストが検出して代替へ倒すので、その機能を用いる手順を書いてよい。作者が負うのは「倒されても手順が破綻しない形にすること」だけである。

制約は 2 群に分かれる。どちらの群かで、作者がすることが変わる。

| | 群 | 作者がすること |
| --- | --- | --- |
| **A** | ホストが吸収する制約 | その機能を書いてよい。**落とされても手順が破綻しない形にする** |
| **B** | どのホストでも守る作法 | **必ず守る**。守っても他ホストで失うものはない |

## 用語

- **作業フォルダ** — 成果物を置く場所。EBEX 内部ではプロジェクトフォルダ（`workspace/<project>/`）を指すが、スキル本文では物理パスを書かず「作業フォルダ」と役割で呼ぶ。
- **スキル同梱ファイル** — `SKILL.md` と同じフォルダ配下（例: `references/`、`assets/`、`scripts/`）のファイル。スキル相対パスで参照する。

## A. ホストが吸収する制約（書いてよい）

### サブエージェント

- **EBEX では**: 起動できない。本文から検出してユーザーへ通知し、同一セッションでの順次実行へ倒す。
- **書く時**: 並列であることに依存した制御（複数の子を同時に走らせて結果を待ち合わせる、子同士を比較する）を前提にしない。順に 1 つずつ実行しても同じ成果物になる手順にする。

### web 検索

- **EBEX では**: 検索キーは既定で未設定。未設定のときは人手フォールバック（検索ワードを提示し、ユーザーが結果とソース URL を貼る）へ倒す。
- **書く時**: 検索結果が得られない場合に手順が止まらないようにする。ユーザーが結果を貼る経路、またはスキップして続行する経路を用意する。

### 画像・マルチモーダル

- **EBEX では**: 生成・読取とも非対応。本文から検出してユーザーへ通知し、「スキップして継続 / 中止」を選ばせる。
- **書く時**: 画像処理が飛ばされても成果物が成立する主線を持つ。画像から得る情報が必須なら、テキストでの代替入力を受け取れるようにする。

### ファイル削除

- **EBEX では**: 削除ツールを提供しない。
- **書く時**: 「一時ファイルを作って後で消す」を完了条件にしない。中間ファイルは残っても無害な場所（`_work/`。後述）に置く。

### MCP・外部コネクタ

- **EBEX では**: 利用できない。専用のフォールバックは無く、当該ステップは実行できないまま残る。
- **書く時**: コネクタからしか得られない情報を必須にしない。作業フォルダ内の資料か人手入力で代替できる経路を必ず併記する。

## B. どのホストでも守る作法（必ず守る）

### プレースホルダー

- 短スロットは `{{XXX}}`、可変長ブロックは `<!-- XXX_START -->`〜`<!-- XXX_END -->`。大文字スネークケースで書く。
- 挿入位置をモデルの判断に委ねない。決定的に埋められる形（変数置換・区間差し込み）だけで完結させる。
- 額縁内の自由記述コメントは書かない。指示は `SKILL.md` 側へ置く。
- 残留（`{{` や空の区間）があるうちは「完了」にならない。完了前に確認する手順を持つ。

### 区間名の一意性

- 区間マーカー名は**ファイル内で一意**にする。同名の `_START` / `_END` の組を 1 つのファイルに複数置かない。
- 複数の差し込み区間があるなら、役割を表す別々の名前を付ける（`AGENDA_LIST` / `ACTION_PLAN` など）。
- 区間端トークンと同じ字面を、マーカー以外の位置（ガイド文・説明・サンプル）に書かない。同じ字面が二重にあると、差し込みが誤った位置を拾う。

### テンプレートの自己完結

- CSS はインライン。ロゴ等の小さな画像は base64 で埋め込み済みにする。
- 実行時に外部ファイルを組み立てる前提にしない。

### 大きな成果物

- 巨大な本文を 1 回のツール引数に載せない（サイズ上限がある）。
- 額縁（テンプレート）があるなら作業フォルダにコピーしてから断片を差し込む。創作長文は分割生成して差し込む。大量レコードはスクリプトで変換する。
- 成果物の形に応じて経路を 1 つ選んで書く（「◯◯が失敗したら△△」というフォールバック列を並べない）。

### 作業フォルダの境界

- 入出力は作業フォルダ内で完結させる。必要なファイルは事前に作業フォルダへ用意する前提で書く。
- 作業フォルダ外のパスに触れる手順を書かない。

### 中間ファイル

- 中間ファイル（partial 等）は**作業フォルダ直下の `_work/`** に置き、成果物本体と混ぜない。
- 成果物フォルダの位置が変わっても中間ファイルの置き場は変えない。

### スクリプト実行とネットワーク

- その場のスクリプトに `fetch` 等の通信を書かない（ブロックされる）。外部データ取得が必要なら、審査済みのスキル同梱スクリプト（`scripts/` 配下）に置く。
- 読取はスキル同梱ファイル基準、書込は作業フォルダ基準の相対パスで書く。
- npm / npx やシェルコマンドの実行を前提にしない。必要な処理は同梱スクリプト（依存なしで動くもの）にするか、素材を事前に用意しておく。

## スキルの自動発火はできない

- **できない**: 説明文やトリガーワードからスキルが自動で起動すること。ユーザーが `/` で明示指定したときだけ起動する。
- **代わり**: 続きが必要なら、ユーザーが次のスキルを明示指定する。
- **書く時**: スキルから別スキルを呼ぶ連鎖を前提に手順を切らない。1 スキルで完結させ、必要な材料は自スキル同梱に持つ。

## 後処理はユーザーに可否を尋ねる

英語版の生成・成果物のレビュー・CSS やアイコンのインライン化など、主成果物ができた後の工程に入る前に、**実施するかスキップするかをユーザーに尋ねる**。同意が得られた場合のみ実行する。1 つのメッセージで複数の後処理をまとめて尋ねない。

## パスと場所の書き方（ポータブル規約）

スキルを EBEX 以外でも動かすため、場所は**物理パスでなく役割**で書く。

- **コピー元** = スキル相対パス（`references/base.html` など）。`.claude/skills/…` や `workspace/…` と書かない。
- **コピー先・出力先** = 「作業フォルダ」等の役割語。物理パスを固定しない。作業フォルダ内のサブフォルダ（`output/` 等）をスキルが指定するのは構わない。
- **操作** = 意図の動詞（「コピーする」「埋める」「差し込む」）。ツール名（`copy_file` 等）を本文に書かない。ホストが実行時に適切なツールへ翻訳する。
- **「なぜ先にコピーするか」は書かない** — その必要性はホスト（EBEX）が実行時に補う。

### 例

推奨:

```
Step1: 額縁 references/base.html を作業フォルダにコピーする
Step2: コピーした額縁のプレースホルダー {{TITLE}} 等を埋める
```

避ける（ホスト依存で他環境で壊れる）:

```
Step1: references/base.html を workspace/<project>/output/ にコピー
Step2: copy_file で配置し replace_between で差し込む
```
