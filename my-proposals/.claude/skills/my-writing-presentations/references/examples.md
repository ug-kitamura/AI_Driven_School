# プレゼン原稿の模範例

「定例会議を減らす」を題材に、対話で具体を引き出し、心が動く原稿に変わるまでの一周。会議の議題の1つとして話す、約2分の短いプレゼンの例（数十秒でも、自分の意見を伝えて通す場面はプレゼンに含む）。

## 目次

- 元原稿（説明だけの発表）
- 対話の流れ（例）
- 完成した原稿（具体を渡した後）
- 何が変わったか（Before / After の対応表）
- たとえをAIが出す（体験がない場合の例）
- レベルの対比：openspec を紹介する（Lv1）
- レベルの対比：openspec を紹介する（Lv2）

---

## 元原稿（説明だけの発表）

提案スキルで作った、ビジネスライティングとしては十分な発表原稿。結論も先、数字の根拠もある。だが心は動かない。

```
定例会議の進め方について、提案があります。
結論から言います。報告中心の定例3本を、隔週の開催に、変えたいです。
いまの定例は週7本、あわせて週12時間。
うち、報告だけの3本が、週3時間を占めています。
隔週にすれば、月に6時間、年で約70時間が空きます。
報告は、前日に資料を共有すれば、読み上げなくても回ります。
まず、この3本から、隔週に。ご承認いただけないでしょうか。
```

全部正しい。だが全部「説明」で、どこの会社にも貼れる＝誰のプレゼンでもない。ここに足りないのは、絵・賭け金・弱さ・原体験。

## 対話の流れ（例）

元原稿から結論・数字は流用できるので聞き直さない。足りない具体だけを1問ずつ掘る。

> AI：この提案、誰に、どんな場で、何分くらい話しますか？ 定例の見直しなら、週次の全体会議で、議題の1つとして話す形が多いですが、どうでしょう？
> ユーザー：そうです。会議のみんなの前で、議題の1つとして。2分くらいです
> AI：2分ですね。問いを開いて絵で閉じる波は1〜2回、山場の絵は1つに絞ります。今の困りで、実際に見た場面はありますか？ 直近の定例を、スローモーションで思い出してみてください
> ユーザー：先週の定例。30分のうち、25分が資料の読み上げ。7人いて、口を開いたのは、2人だけでした
> AI：その場面、強い絵になります。このまま何もしなければ、何を失いますか？
> ユーザー：報告を聞くだけの時間が、年150時間。1ヶ月分です
> AI：あなた自身の、正直な気持ちはどうでしたか？ 半信半疑だったこと、当たり前だと思っていたことがあれば
> ユーザー：私も長いこと、この会議を当たり前だと思って、疑うことすらなかった。先週、ふと周りを見たら、全員が同じ顔をしていて
> AI：そもそも、なぜ変えたいと思ったんですか？
> ユーザー：その時間で、本当はやりたい仕事が、あったからです
> AI：材料が揃いました。原稿を作ります

## 完成した原稿（具体を渡した後）

```
先週の定例会議。30分のうち、25分が、資料の読み上げでした。
7人いて、口を開いたのは、2人。
──報告だけの定例3本を、隔週にしませんか。
あの読み上げを聞くだけの時間が、1年で150時間。
まるまる1ヶ月分が、毎年、消えています。
正直に言うと、私も長い間、この会議を当たり前だと思って、
疑うことすら、ありませんでした。でも先週、ふと周りを見て、
全員が同じ顔をしているのに、気づいたんです。
やり方は、シンプルです。報告の3本を隔週にして、
資料は前日に共有する。それだけ。
それだけで、年に70時間ちかく──消えた時間の半分が、戻ります。
ずっと後回しにしてきた、やりたかった仕事に、手がつけられます。
まず、報告の3本だけ。1ヶ月、試させてもらえませんか。
```

## 何が変わったか（Before / After の対応表）

企画の中身は同じ（定例3本を隔週に）。変わったのは、渡した具体だけ。

| 6ステップ | 元原稿 | 完成した原稿 |
|---|---|---|
| ① フック | なし（いきなり本題） | 沈黙の場面の絵（7人中2人） |
| ② 結論 | 先にある | 先にある（維持） |
| ③ なぜ | 数字のみ | 絵 ＋ 賭け金（年150時間＝1ヶ月分が消え続ける） |
| ④ どうやって | ある | 短く維持 |
| ⑤ どうなる | 数字のみ（年70時間） | 数字 ＋ 原体験（やりたかった仕事に手がつく） |
| ⑥ お願い | ある | 小さく・試しやすく（まず3本だけ、1ヶ月） |
| 弱さ | なし | 「私も当たり前だと思っていた」（ひと言・穏やかに） |

注意点：

- 原稿に出てくる絵は、すべてユーザーがインタビューで渡したもの。AIが場面を足していない
- 賭け金は150時間、回収は「半分＝70時間」と正直に。盛っていない
- 弱さは「内職していました」のような告白ではなく、堅い場でも出せる穏やかな自己開示にしている
- 分量は約400字＝渡された尺（2分）に収まる。尺が5分、10分と長い場合も6ステップは同じで、「問いを開いて、絵で閉じる」波の数を増やして分量を設計する。山場の絵は1つのまま増やさない

## たとえをAIが出す（体験がない場合の例）

自分が実際に見た場面がないときは、聞き手に身近なたとえで補う。たとえの案出しはAIの得意技。

> ユーザー：その現場には行ったことがなくて、見た場面がないんです
> AI：では、身近なたとえで絵にしましょう。「会議の資料の読み上げを聞いている時間」を、誰でも知っている場面にたとえると、こんな案があります。
> ・朝礼で、長い校長先生の話を聞いている時間
> ・機内で、毎回同じ安全ビデオを見せられる時間
> ・説明書を音読されるのを、隣で聞いている時間
> 聞き手にいちばん近いのは、どれですか？
> ユーザー：校長先生の話が、いちばん伝わりそう

選ぶのは必ずユーザー。聞き手を知っているのはユーザーだけ。

# レベルの対比：openspec を紹介する

同じ題材・同じ場・同じ話し手で、ストーリーレベルだけが違う2本。差は「絵で閉じる箇所」の数だけ。上の定例会議の例が承認型・2分なのに対し、こちらは紹介型・10分超で、⑥が依頼ではなく誘いで着地する。

実際に使われたのは Lv1 のほう。原稿の質はどちらも高い。レベルは質の高低ではなく、話し手と場に合うかで選ぶ。

## Lv1 の原稿

- 場：社内のチーム内勉強会（カジュアル・上長も同席）
- 尺：本編 約5分 ＋ デモ
- 聞き手：AI・プログラムに詳しいメンバー。ただし openspec は知らない
- 絵で閉じる箇所：**1つ**（⑥のみ。たとえ・変化の絵・弱さが締めに集まっている）

①の「みなさんも、心当たりがあるんじゃないでしょうか」は、そのあとに絵が続かないので**つなぎ**。数えない。

```
# プレゼン原稿：openspec の紹介

## ① フック ＋ ③ なぜ

まず、openspec が解決する課題なのですが。

AI と何度もやり取りを繰り返して、ようやくうまくいった、と思っても。
そのやり取りは記録されなくて、後から再利用することができないんですよね。
なぜこの仕様にしたのかも、忘れてしまう。
そういう問題が、あると思います。

みなさんも、心当たりがあるんじゃないでしょうか。

## ② 結論

openspec を一言でいうと、仕様駆動開発を支援するツールです。

AI とのやり取りを仕様として文書化して、その仕様をもとに実装してくれます。
作った仕様は保存されて、次のやり取りで参照されます。
このサイクルを回せば回すほど、仕様が磨かれていって、
アウトプットの品質が上がっていきます。

1サイクル回すのに時間はかかるんですけど、手戻りが減るので、
トータルでは効率的だと思います。

## ④ どうやって — セットアップ

セットアップは3つです。

まず、Node.js を入れます。
社内システムから NodeJS Selector を入れてください。無料です。
インストーラーを動かすと、Node.js のバージョンを選ぶ画面が出ます。
色々なバージョンが表示されますけど、
私は v24 シリーズの最新版をお勧めします。

次に、`npm install -g @fission-ai/openspec@latest` を実行します。
これで openspec が入ります。

最後に、作業フォルダで `openspec init` を実行します。
環境の選択画面が出るので、Claude Code を選びます。
これで `.claude/skills/` の下に、openspec のスキルが置かれます。

## ④ どうやって — 使い方

使うときは、スキルを4つ、順番に呼びます。

1つめが Explore です。
plan モードのような感じで、アイデアや企画を言語化していきます。
この時点では、ファイルは何も作りません。

2つめが Proposal。
仕様が文書になって、`openspec/changes/` に置かれます。
中身は4つで、proposal.md に「なぜ・何を作るか」、
design.md に「どう作るか・何がゴールか」、
spec.md に仕様そのもの、tasks.md にやるタスクが入ります。

3つめが Apply。
仕様に基づいて実装します。
終わったタスクは tasks.md に記録されていきます。

4つめが Archive。
仕様が `openspec/archive/` に保存されます。
これまでに作成した仕様に、変更分が継ぎ足されていきます。

## デモ

ここで実際に動かしてみます。
Next.js で作ったアプリに、ピンクモードを追加してみましょう。

## ⑤ どうなる ＋ ⑥ 誘い

openspec のおかげで、最近はほとんどプログラムを書かなくなりました。
そのかわりに、超絶優秀なメンバーを1人マネジメントしている感覚です。
コードを書く人から、何を作るか決める人に、変わりました。

openspec はちょっと使い方にクセがありますけど、
私はこれのおかげで、大分助かっています。
良かったら是非、使ってみてください。
```

## Lv2 の原稿

- 場：社内のチーム内勉強会（カジュアル・上長も同席）
- 尺：本編 約11分 ＋ デモ 2〜3分
- 聞き手：AI・プログラムのエキスパート。ただし openspec は知らない
- 絵で閉じる箇所：**4つ**（①AI ガチャ／③こたえました／⑤役割が変わった＝山場／⑥聞き手の心の声）

①の「こんなことはないでしょうか」は、直後に場面が続いて閉じているので**波として数える**。Lv1 の同型の問いかけとは扱いが違う。山場は⑤の1つに絞られている。

```
# プレゼン原稿：openspec の紹介

## ① フック（約1分）

AI を使っていて、こんなことはないでしょうか。

指示を出す。出てきたものが、ちょっと違う。直してもらう。また違う。何往復かして、ようやく「お、いいのが出た」となる。

私はこれを、勝手に「AI ガチャ」と呼んでいます。当たりが出るまで、回し続ける。便利なんですけど、正直しんどい。

で、しんどいのは、そこじゃないんです。

せっかく当たりを引いたのに、次の日、別のところで同じことをやると、また一から回している。昨日の当たりが、手元に残っていないんですよね。

## ② 結論（約30秒）

今日は、その「残らない」を解決するツールを紹介します。

openspec といいます。一言でいうと、**仕様駆動開発を支援するツール**です。

AI とのやり取りを仕様として文書に残して、その仕様をもとに実装してもらう。ガチャを回し続けるのをやめて、先に仕様を決めてしまう、という道具です。

無料で、npm で入ります。

## ③ なぜ（約2分30秒）

なぜこれが要るのか。私が困っていたことは、3つでした。

1つめ、**再現性がない。** 良いものが出たとしても、なぜ良いものが出たのかが分からない。同じように頼んでも、同じものは返ってきません。

2つめ、**なぜこの仕様にしたか、忘れる。** やり取りの最中は、けっこう細かいところまで詰めているんです。この条件のときはこうする、この方式は採らない、といった判断を。でもそれは、チャットの履歴の中に流れていってしまう。3日後の自分は、もう思い出せません。

3つめ、これが一番大きいんですが、**自分の土台となる考えが、引き継がれない。** 前回のやり取りで固めたはずの前提が、次のやり取りには渡らない。AI は毎回、まっさらな状態から始めます。

つまり、回した回数だけ賢くなっていくはずのものが、毎回ふりだしに戻っている、ということです。

そのぶんは、手戻りとして返ってきます。私の場合、実装が終わってから「そもそも、この前提が違った」と気づく。あれが一番、こたえました。

## ④ どうやって（約3分30秒）

では、openspec が何をしてくれるのか。使い方を順番に見ていきます。

まずセットアップ。3つだけです。

1つめ、Node.js を入れます。社内システムから NodeJS Selector を入れれば、無料で入ります。インストーラーを動かすとバージョンを選ぶ画面が出るので、v24 シリーズの最新を選んでください。

2つめ、`npm install -g @fission-ai/openspec@latest` を実行します。これで openspec 本体が入ります。

3つめ、作業フォルダで `openspec init` を実行します。環境を聞かれるので Claude Code を選んでください。`.claude/skills/` の下に、openspec のスキルが置かれます。

ここまでで、5分もかかりません。

使うときは、スキルを4つ、順番に呼ぶだけです。

1つめ、**Explore**。plan モードのような感じで、アイデアや企画を言語化していきます。この時点では、ファイルは何も作りません。まだ考えている段階です。

2つめ、**Proposal**。ここで仕様が文書になって、`openspec/changes/` に置かれます。中身は4つ。proposal.md に「なぜ・何を作るか」。design.md に「どう作るか・何がゴールか」。spec.md に、仕様そのもの。tasks.md に、やることのリスト。

3つめ、**Apply**。ここでようやく実装です。仕様に沿って実装が進んで、終わったタスクは tasks.md に記録されていきます。

4つめ、**Archive**。仕様が `openspec/archive/` に保存されます。ここが大事で、**これまでの仕様に、今回の変更分が継ぎ足される**んです。前回決めたことの上に、今回決めたことが積まれる。次のサイクルでは、それが最初から参照されます。

回せば回すほど仕様が磨かれて、アウトプットの質が上がっていく。そういう構造になっています。

## デモ（2〜3分・時間が無ければ省略）

> 事前に Proposal まで進めた状態を用意しておき、Apply を実行するところだけを見せる。
> 題材：Next.js で作ったアプリに、新しいテーマを追加する。
>
> 話すこと：「これが、Proposal まで回した状態です。tasks.md を見てください。ここに書いてあることを、Apply でそのまま実装させます」

## ⑤ どうなる（約3分）

ここまで聞いて、たぶん一番気になっているのは、これだと思います。

**「それ、1サイクル回すのに時間かかるでしょ」**

かかります。正直に言います。私の場合、軽いもので30分。じっくりやると、2時間かかることもあります。実装を始めるまでに、2時間です。

それでも私が使い続けているのは、**手戻りが、そのぶん減るから**です。前は、実装が終わってから前提の間違いに気づいて、作り直していました。今は、その時間を先に払っている、という感覚です。トータルでは、こちらのほうが早い。

それと、これは使ってみて初めて分かったことなんですが、**一度決めてしまえば、あとは実装するだけ**、という状態が、すごく楽なんです。悩む時間と、手を動かす時間が、きれいに分かれます。

その結果どうなったかというと、**私は、プログラムをほとんど書かなくなりました。**

いま何をやっているかというと、仕様を詰めて、渡して、上がってきたものを見る。感覚としては、超絶優秀な部下を1人、マネジメントしているような感じです。コードを書く人から、何を作るかを決める人に、役割が変わりました。

## ⑥ お願い（約1分）

openspec は、正直、ちょっと使い方にクセがあります。最初は「なんで、いちいち文書にするんだ」と思うかもしれません。

それでも、私はこれのおかげで、大分助かっています。ツールそのものというより、**仕様駆動開発という考え方**を、皆さんにも一度、試してみてほしいと思っています。

なので、お願いはひとつだけです。

次に何か小さいものを作るとき、その1個だけでいいので、openspec で一周、回してみてもらえないでしょうか。セットアップが5分、一周が30分です。

それで合わなければ、やめてもらって構いません。ただ、一周してみないと、この良さは分からないと思うので。

ぜひ、試してみてください。
```

注意点：

- Lv1 は、話し手がマインドマップに書いた見出しから読み上げ原稿に起こしたもの。実際の発話をすべて逐語で記録したものではない
- どちらも場面・数字・感情はすべて話し手が渡したもの。AIが足していない
- Lv1 の①に問いかけを足しても Lv1 のまま。絵で閉じていなければレベルは動かない
