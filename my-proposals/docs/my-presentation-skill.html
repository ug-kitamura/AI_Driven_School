課題概要 — 自分自身のプレゼン作成スキルを作る

今回の課題は、汎用のスキルをそのまま使うのではなく、自分の発表の型に合わせて育てたスキルを1本つくるというものです。スキルとは、Claude Code に「こういう手順で、こういう質問をして、こういう形式で出力して」と教え込んだ作業マニュアルのようなもの。作ったスキルで実際にプレゼン原稿を1本仕上げ、その過程を報告するところまでが課題です。

この場の特徴を、原稿の書き方に効く順に3つ挙げます。聞き手が全員テクノロジーとAIに詳しいこと。カジュアルで、かしこまっていないこと。そして承認をもらう場ではないこと。この3つが、原稿のトーンと締め方をほぼ決めてしまいます。

2 openspec のメリットと使い方を、その場で試せる粒度まで落として伝える
3 ツールの紹介にとどめず、仕様駆動開発という進め方そのものを広めたい

題材 — openspec とは何か

原稿の中身を見る前に、題材そのものを押さえておきます。openspec は、AIコーディング支援ツール向けの「仕様駆動開発（SDD＝Spec-Driven Development）」のフレームワークです。コードを書き始める前に、AIと人間が「何を作るか」で合意し、その合意を仕様ファイルとして残しながら進める、という考え方でできています。

BEFORE — いわゆる「AIガチャ」
  • 指示を出す → ちょっと違う → 直す。何往復もして、ようやく当たりが出る
  • 当たりを引いても、翌日には手元に残っていない
  • やり取りが記録されず、なぜその仕様にしたのかを忘れる
毎回ゼロから引き直し。学習が積み上がらない。
AFTER — openspec を挟む
  • やり取りが仕様として文書化され、その仕様をもとに実装される
  • 作った仕様は保存され、次のやり取りで参照される
  • 回すほど仕様が磨かれ、アウトプットの品質が上がる
1サイクルは重いが、手戻りが減る分トータルで速い。

使い方は、AIとのチャットの中で4つのスキル（スラッシュコマンド）を順番に呼ぶだけです。原稿でも、この4ステップを軸に説明しています。

作成したプレゼン原稿

スキルは、引き出した材料を6ステップの弧に流して原稿に組みます。「問いを開いて、絵で閉じる」を短く刻むための型です。今回の原稿がどの型に乗っているかを、まず地図として見てください。

① フック 15〜30秒

「AIガチャを回しているみたいで、正直けっこう疲れる」──聞き手が全員うなずける困りから入る。

② 結論

「その"残らない"を解決するツールを紹介します。openspec といいます」──結論は隠さず先に渡す。

③ なぜ 賭け金

「昨日の当たりが、手元に残っていない」──放置すると何を失うかを具体で見せる。今回は①と一体化。

「超絶優秀な部下を1人、マネジメントしているような感じ」──唯一の山場。ここに絵を1つだけ置いた。

⑥ 誘い

承認を求める場ではないので、依頼ではなく「良かったら、ぜひ使ってみてください」という誘いで着地。

# プレゼン原稿：openspec の紹介

- 場：社内チームの技術共有会（2時間・持ち回り発表の1枠）
- 尺：10〜15分
- 聞き手：5〜10名、全員テクノロジー・AIに詳しい。課長も同席（課長が一番詳しい）。他部署の人も参加。若手が多い。カジュアルな雰囲気
- ストーリーレベル：Lv1（絵で閉じる箇所は⑤どうなる、の1箇所）

---

## ① フック ＋ ③ なぜ

最近、AIを使っていると、こんなことがよくあります。

指示を出す。出てきたものが、ちょっと違う。直してもらう。また違う。何往復かして、ようやく「お、いいのが出た」となる。まるでAIガチャを回しているみたいで、出力が安定しないので、正直けっこう疲れるんですよね。

しんどいのは、そこだけじゃなくて。せっかく当たりを引いても、次の日、別のところで同じような作業をすると、また一からガチャを回している。昨日の当たりが、手元に残っていないんです。

AIとのやり取りが記録されなくて、後から再利用できない。なぜこの仕様にしたのかも、忘れてしまう。そういう問題が、あると思います。みなさんも、心当たりがあるんじゃないでしょうか。

## ② 結論

今日は、その「残らない」を解決してくれるツールを紹介します。openspecといいます。

一言でいうと、**仕様駆動開発**を支援するツールです。

AIとのやり取りを仕様として文書化して、その仕様をもとに実装してくれます。作った仕様は保存されて、次のやり取りで参照される。このサイクルを回せば回すほど、仕様が磨かれていって、アウトプットの品質が上がっていきます。

ここで、先に言っておきたいんですけど。1サイクル回すのに、時間はかかります。それでも、手戻りが減るので、トータルで見ると効率的だと思っています。

## ④ どうやって — セットアップ

セットアップは3ステップです。

まず、Node.js を入れます。社内システムから `NodeJS Selector` をインストールしてください。無料です。インストーラーを動かすと、Node.js のバージョンを選ぶ画面が出るので、v24シリーズの最新版を選びます。

次に、`npm install -g @fission-ai/openspec@latest` を実行します。これで openspec 本体が入ります。

最後に、作業フォルダで `openspec init` を実行します。環境の選択画面が出るので、Claude Code を選んでください。これで `.claude/skills/` の下に、openspec のスキルが配置されます。

## ④ どうやって — 使い方

使うときは、スキルを4つ、順番に呼びます。

1つめが Explore（`openspec-explore`）です。plan モードみたいな感じで、アイデアや企画を言語化していきます。この時点では、ファイルは何も作りません。

2つめが Proposal（`openspec-proposal`）。ここで仕様が文書になって、`openspec/changes/` フォルダに置かれます。中身は4つで、`proposal.md` に「なぜ・何を作るか」、`design.md` に「どう作るか・何がゴールか」、`spec.md` に仕様そのもの、`tasks.md` にやることのリストが入ります。

3つめが Apply（`openspec-apply-change`）。仕様に基づいて実装します。終わったタスクは `tasks.md` に記録されていきます。

4つめが Archive（`openspec-archive-change`）。仕様が `openspec/archive/` フォルダに保存されます。ここでこれまでに作った仕様に、今回の変更分が継ぎ足されます。

## ⑤ どうなる ＋ ⑥ 誘い

openspec を使うようになってから、私、最近はほとんどプログラムを書かなくなりました。

いま何をやっているかというと、仕様を詰めて、渡して、上がってきたものを見る。感覚としては、超絶優秀な部下を1人、マネジメントしているような感じなんです。コードを書く人から、何を作るかを決める人に、役割が変わりました。

openspec、ちょっと使い方にクセはあるんですけど、私はこれのおかげで、大分助かっています。良かったら、ぜひ使ってみてください。

ここがポイント — 「絵」は1箇所だけ

原稿の中で、聞き手の頭に絵が浮かぶ箇所は「超絶優秀な部下を1人、マネジメントしているような感じ」の1つだけです。全部を山にすると、全部が平らになる。だから山場は1つに絞り、それ以外は淡々と手順を伝えています。10〜15分のカジュアルな共有会では、これがちょうどいい配分でした。

どのようにチューニングしたか

チューニングの手口は、前回の my-writing-proposals で効果が確認できたものを、そのまま持ち込みました。大きく2つです。

01

模範回答を自分で作って参照させた

「良い原稿とはこういうものだ」をルールで書き並べるのではなく、自分の手で書いた模範原稿をスキルに同梱し、生成時に必ず読ませる。文体・テンポ・言い回しが、指示文よりはるかに正確に伝わります。

02

ストーリー成分の量を最初に選べるようにした

場によって、感情に訴えていい度合いは変わります。そこで「絵で閉じる箇所を何箇所置くか」を Lv0〜Lv3 の4段階にして、書き始める前にユーザーと合意するようにしました。

模範回答を先に読ませる仕組みは、図にするとこうなります。スキルは指示書だけを渡すのではなく、「完成品の実物」を先に見せてから書かせるようになっています。

模範回答を挟むと、何が変わるか

指示文だけを渡す
「話し言葉で、テンポよく書いて」
世界中の文章の平均に寄る。
間違ってはいないが、誰の言葉でもない。
模範回答も一緒に渡す
自分で書いた原稿の実物を先に読ませる
文体・間の取り方・語尾が寄る。
「自分が書いたっぽい」原稿になる。

もう1つのチューニング、ストーリーレベル。原稿を書き始める前に「今回はどのくらい感情に寄せますか？」と聞き、合意した段階が、そのまま材料を掘る深さの上限にもなります。Lv0 なら場面や心の声は掘りません。

ストーリーレベル — 絵で閉じる箇所をいくつ置くか

数えるのは「絵で閉じた箇所」。問いかけやチラ見せは開き手であって、閉じ手ではない

Lv0
0箇所
ビジネスライティング

構成・話し言葉・懸念の先出しだけを整える。数字と手順で伝わる場に。絵はゼロでも、構成は整える。

Lv1
1箇所
既定 ／ 今回採用

さりげなくストーリー成分を挿入。締めに絵を1つ置く。今回の openspec 原稿はこれ。

Lv2
2〜4箇所
数か所にちりばめる

締めに加えて、フックや「なぜ」にも絵を置く。それでも山場は1つのまま。

Lv3
全編
感情に訴える

最初から最後まで波を刻む。長尺向けで、通常の社内発表ではほぼ使わない。

なぜ「最初に選ばせる」のか

原稿を書いてから「もっと熱く」「もっと淡々と」と直すと、全体を作り直すことになります。レベルを先に決めておけば、質問の量も、掘る深さも、そこで決まる。合意した箇所数が埋まらなければ、埋まった分だけで書く──場面をでっちあげない、という歯止めにもなっています。

苦戦したポイント

提案文のときと決定的に違ったのが、プレゼン原稿は「読んで良い」だけでは足りず、「声に出して良い」必要があるという点でした。画面で読むぶんには自然な文章が、実際に口に出すと急に他人行儀になる。ここに一番時間を使いました。

読み上げてみると、言い回しに違和感が出る

目で読む分には通るのに、口に出すと引っかかる箇所が必ず出てきます。息継ぎの位置、語尾の重なり、漢字の多い塊。声に出して初めて見つかる不具合なので、画面を見ているだけでは潰せませんでした。

プレゼンのスタイルによって、言い回しごと変える必要がある

カジュアルな共有会と、承認をもらう報告会とでは、同じ内容でも語り口がまるで変わります。1つの型で全部をまかなおうとすると、どの場でも少し浮く。ストーリーレベルを選べるようにしたのは、この振れ幅への対処でもありました。

「自分の言葉」に寄せるチューニングが、いちばん難しい

AIは世界中の文章の平均から書くので、放っておくと誰にでも当てはまる説明に寄ります。模範回答を読ませて文体を近づけても、最後の数％は自分で直すしかない。そこを埋める作業に、いちばん時間がかかりました。

スキルが、原稿を渡したあとに必ず表示する言葉

本番の前に、必ず声に出して読み、あなた自身の言葉に直してください。

本スキルは便利ですが、あくまで発表の準備を支援するためのものです。

発表がうまくいくことをお祈りします。

苦戦したポイントは、そのままスキルの仕様になりました。「AIの出力は完成品ではなく、下書きである」ことを、スキル自身に毎回言わせています。

まとめ — 覚えておきたい3つのこと

01

AIに書かせるのではなく、引き出させる

心を動かす具体は、本人の中にしかありません。スキルの役割は文章を生成することではなく、実際に見た場面とその時の心の声を、1問ずつ掘り出すことです。

02

模範回答とレベル選択が、チューニングの二本柱

ルールを書き足すより、完成品の実物を1つ見せるほうが速い。そして、感情の量は書き始める前に決めておく。この2つは提案スキルでも今回でも、同じように効きました。

03

最後の仕上げは、声に出した本人にしかできない

出力された原稿は、あくまで下書き。読み上げて引っかかった箇所を自分の言葉に直すところまでが、原稿づくりです。スキルはその手前まで連れていく道具でした。

説明するな、体験させろ。

「定例会議は非効率です」では、頭には届いても心は動かない。「30分のうち25分が資料の読み上げで、7人いて口を開いたのは2人だけでした」なら、聞き手が自分で頷く。その差を毎回つくるための道具が、このスキルです。
