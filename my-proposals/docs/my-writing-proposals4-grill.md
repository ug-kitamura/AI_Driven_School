# my-writing-proposals4 グリル結果

`writing-proposals` をベースに自分専用の提案スキルを作るための、決定事項のまとめ。

## 背景

3つの出力を読み比べた結果が出発点。

| 出力 | 元スキル | 印象 | 見立て |
|---|---|---|---|
| ads-proposal-original.md | writing-proposals | やや長い | 構造は正しい。案A/B/Cの説明が厚く、読む前に量で怯む |
| my-proposal-2.md | my-writing-proposals | 短くそっけない | 長さの問題ではない。全行が「説明」で、絵が1つもない |
| EBEX導入提案メール.md | my-writing-proposals2 | 筋が良い・やや長い | 依頼事項の明示と比較表が効いている。ただし絵はゼロ |

`my-proposal-2.md` のそっけなさは行数制約の結果に見えるが、行数を伸ばしても増えるのは説明の箇条書きだけ。原因は**説明しかないこと**。

## 決まったこと

### 土台と作り方

- オリジナル `.claude/skills/writing-proposals` をコピーし、**差分だけ足す**。例1,2,3 は一字も変えない
- 作成時は `.claude/skills/creating-skills` に従う。**SSoT 原則を守る**（参照先の情報をスキル内に書かない、SKILL.md と references の間・references 同士で情報を重複させない）
- 置き場は `my-proposals/.claude/skills/my-writing-proposals4`
- `my-writing-proposals` / `my-writing-proposals2` / `my-writing-proposals3` は残す。1本化は後で手動、今回のスコープ外

### 書き方

- 2つの型を定義する。**ビジネスライティング型**（例1,2,3）と**ビジネス＋ストーリーライティング型**（例4）
- 既定はストーリー型。骨格は PREP。結論を最初に言い切り、絵は根拠・背景側にくどくない程度で差し込む
- 絵が引き出せなければビジネスライティング型に縮退する。**縮退するときは「ストーリーを盛り込まずに作る」とユーザーに伝える**
- 分量・テンプレの縛りは置かない。分量は起動時か事後にユーザーが指示する
- 出力は日本語のみ。英語が要るときは後から頼む

### 対話

- 6材料 = 既存5（①変えたいこと ②決める人 ③相手の問い ④根拠 ⑥文体見本）＋ **⑤見た場面と心の声**
- 材料⑥は残す。他の人が使う場合と、特定のメールを参考にさせたい場合に効く
- 絵は角度を変えて2〜3回試す。回数は目安で固定しない。「もう十分」で即終了
- 読み手が複数なら**1人に焦点**を合わせ、他の読み手の関心は懸念の先出しで1行拾う
- 媒体（メール／チャット）は**入力から分からないときだけ**聞く
- Purpose / Mission は冒頭で1回だけ聞く（reference を使う／ファイル指定／その場で記入／スキップ）。reference にファイルがあるときだけ先頭の選択肢を出す
- Purpose は読み手で扱いを変えない。**1箇所だけ**、言葉を借りずに言い換えて溶かす。独立セクションにしない。接点がなければ入れない

### reference

- `examples.md` に**例4**として EBEX 提案メールの磨き版を追加。今後 例5, 6 と足したり削ったりして育てる
- 例4は「ビジネス＋ストーリーライティング型」、例1,2,3 は「ビジネスライティング型」と明記する
- 文章ルールのエッセンスと品質チェックリストを持たせる
- Purpose 置き場を1本置く。**ステートメントと個別項目の中身をファイルに直接書き込む**（`ebex/contracts/ebe-purpose.md` を参照させない）。各自が差し替える前提であることをファイル内に明記する
  - SSoT の意図的な例外。各自が差し替える自分用ファイルであり、他プロジェクトを参照させると他部署の人が使えず壊れやすくなるため

### 出力

- 作業フォルダに Markdown で保存し、チャットにもコードブロックで出す
- 最後に「意思決定者役のサブエージェントで、時系列に心の声を出すレビュー」を**1行だけ案内**する。自動実行はしない

## 未決

- **`writing-presentations` への橋渡し** — 提案文ができた後にプレゼン化を案内するか。サブエージェントレビューと同じ「1行だけ案内」で揃えるのが自然だが未確認
- **例4が例1,2,3 の約4倍の長さになる点** — 型が違うので当然だが、AI がどちらを標準の長さと受け取るかは回してみないと分からない
- **文章ルールと品質チェックの重複** — オリジナルの `output-quality.md` には既に文章表現の点検項目（一文一義・用語一貫・過剰敬語・数値の本文化・期限・MECE）が入っている。ここに文章ルールのエッセンスを別ファイルで足すと内容が重複し、SSoT 監査に引っかかる。「オリジナルを削らない」と「重複させない」の両立をどう解くか、実装時の判断が要る
- **評価シナリオ** — 3つ以上のお題で回して、3 と 4 を比べる
