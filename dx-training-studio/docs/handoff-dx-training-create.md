### 2.1 原稿側の改善点（レビューで繰り返し見つかったパターン）

6本のレビューで指摘は合計32件（高1・中十数件・低多数、ほぼ全採用）。**1本だけの問題ではなく、複数レッスンで同種の指摘が出たもの**を優先度高く記録する。次回実行時、執筆フェーズの自己チェックに組み込む価値がある。

| パターン | 具体例 | 対応の方向 |

### 2.2 スキル側の改善点（次回の change 候補）

原稿側の改善はスキルを直さなくても執筆時の注意で対応できるが、次のものは**スキルへの明文化**で再発を防げる可能性が高い。

- **`lesson-template.md` に「前のレッスンへの参照は記述的に行う」ルールを追記する。** 生のレッスン番号（`L06` 等）を読者向け本文に書かないことを明示する。今回は誰も指示していないのに前半5本が自然とこの作法を守り、6本目だけ崩れた——書かれていないルールは崩れうる、という実例になった
- **設計メモを「書いて終わり」ではなく「執筆中の生きたチェックリスト」として使う運用を、`SKILL.md` フェーズ5に一言足す。** 用語表・穴の一覧・画像計画のいずれも、今回は執筆後のレビューで初めてズレに気づいた。書いた直後に自分で見比べる一手間があれば、レビューに回す前に減らせた指摘が複数あった
- **手順型レッスン（コマンドの実行結果を書くもの）では、可能な範囲でコマンドを実際に実行して出力を確認することを `lesson-template.md` か `design-principles.md` に一言添える。** 今回は Claude Code 環境だったため Bash でいつでも実機確認できたが、そのことをスキル側は前提にも明記もしていない。ペイン4（agent 実行環境）ではコマンド実行ツールが無いため、この推奨は**環境によって実行可否が変わる**ことも併記する必要がある

いずれも「本体 spec を書き換える change」を要するほどの大きさではなく、`references/` の追記で足りる規模（`creating-skills` の SSoT 作法に従う）。

### 2.3 レビュー運用は機能した（変更不要）

**per-lesson独立レビュー・指摘のみ・本文の順に初学者反応を書かせる・採否を執筆側が判断してファイルに残す**、という `dx-training-create` スキルのフェーズ6設計は、今回そのまま機能した。特に「コマンドを実機で検証する」という執筆側が指示していなかった振る舞いをレビュー側が自発的に行い、最重要の指摘（diff 出力の欠落）を拾った点は、レビューを「文章として自然かどうか」だけでなく「技術的に正しいか」も見る場として機能させられることを示した。**この設計自体への変更提案はない。**

## 3. 模範解答の設計（検討結果）

「模範解答から型やトンマナを抽出する記述をスキルに含める」「模範解答でスキルをスリムにする」という案について。**前者は賛成。後者は条件付き。**

### 3.1 模範解答に担わせるもの

模範解答が**散文の指示より強いのは、規則で書けないもの**に限る。

| 担わせる | なぜ |
|---|---|
| **トンマナ** — 文体、読者への語りかけ方、断定の強さ、専門語を出す間合い | 「親しみやすく」と書いても伝わらない。実物なら1本で伝わる |

初回のトンマナは `docs/work6.md`（主）と `ads-lecture/`（従）から取る（→ 2.1）。**模範解答ができた時点で、その役割は模範解答に移る。** 外部文書を毎回読ませる運用にはしない。

**マークダウンの運用**（太字の当て方、箇条書きの使い分け、コラムの出し方、完了条件の置き方）も模範解答が運ぶ。これらは規則で書くと窮屈になり、実例なら1本で伝わる典型。
| **密度** — 1節あたりの分量、図と文の比率、たとえの長さ | 数値で指定すると機械的になる。実例のほうが速い |
| **穴の書きぶり** — 「答えるべき問い」の具体度 | 抽象的な指示では粒度がばらつく。実例が最も効く |

### 3.2 担わせてはいけないもの

| 担わせない | なぜ |
|---|---|
| **フェーズとゲート** | AI は手順を平気で飛ばす。実例からは「順序を守れ」が読み取れない |
| **出力規約**（パス・`.meta.json`・命名） | 1本の実例からは一般則が導けない。特に `/` を含むレッスン名のような例外は伝わらない |
| **制約**（既存を変更しない等） | 実例には「やらなかったこと」が写らない |

**つまりスリム化できるのは `lesson-template.md` の一部だけ。** 章の役割や分量の目安は模範解答が語れるので削れる。`SKILL.md` のフェーズ・出力規約・制約は削らない——**むしろここを削ると初回実行で観察した「飛ばし」が悪化する。**

### 3.3 昇格基準（提案・まだ実地で使われていない）

⚠ **2026-08-12 追記**: 初回実行（Gitシリーズ6本）で模範解答への昇格をユーザーが見送ったため、下記4項目はまだ実際の判定に使われていない。次回実行時、この基準で本当に判定できるか（4項目のどれかが曖昧で判断に迷わないか）も合わせて観測すること。

**次の4つを全て満たす1本**を昇格させる。

1. 人の手直しが**段落単位で発生していない**（語句の修正だけで済んだ）
2. 社内の穴が、**中身を知らない人でも何を書けばいいか分かる**粒度になっている
3. 「やってみる」が**学習目標を検証している**（演習をこなすこと自体が到達確認になる）
4. 読み返して**冒頭で詰まらない**（時系列レビューで冒頭に指摘が出ていない）

⚠ **「さらっと眺めるといい感じに見える」現象に注意。** 大量の出力は全部それなりに見える。1本ずつ、上の4項目で明示的に判定する。

### 3.4 何本置くか

**まず1本。** ただし**将来2本目が要る可能性が高い**ことを見込んでおく。

29レッスンには構造の異なる型が少なくとも2つある。

| 型 | 例 | 特徴 |
|---|---|---|
| 概念型 | L05・L06・L11・L18 | 穴が少なく、たとえと図で運ぶ |
| 手順型 | L02・L07・L12・L19 | **申請 → 承認待ち → 承認後の実作業**の3段。穴が主役 |

1本目は概念型になる（2.1 の推奨がそこだから）。手順型の出来が悪ければ2本目を足す。**最初から2本作ろうとしない** — 昇格に値するものが2本同時に出る保証がない。

### 3.5 置き場所と形式

```
references/model-answer/
  <レッスン名>.md      ← contents.md をそのままコピー（frontmatter 込み）
  README.md            ← なぜ模範か・どこを写しどこを写さないか（短く）
```

- **本文に注釈を書き込まない。** 注釈を入れると、それ自体が「レッスンの形」として写る
- 写してよいもの／写してはいけないもの（＝内容そのもの）の区別は `README.md` 側に置く
- `model-answer/` が**無い状態は今も正常**（spec で保証済み）。増えても、無い場合の経路を壊さない

シリーズ名・コース名は第5章の表（`はじめに / DX入門`、`Git / 概念`）。**第2章の全体構造ツリーにある「〜シリーズ」「〜コース」は装飾なので使わない。** レッスン名は第6章の表から取り、`L05` の ID・`【撮】`『【録】』の印・`☆` は落とす。

### 4.2 レッスン名に `/` が含まれるものが2本ある

L13「リポジトリを作る / clone」と L25「ファイル読み書き（CSV / JSON）」。ディレクトリ名では `_` に置換される（`lib/content-filename.ts` の `sanitizeFilename`）。**frontmatter の `lesson` はディレクトリ名のほうに合わせる** — ずれるとディスク側の名前で上書きされる。

### 4.3 `id` は loader が自動で書き足す（実挙動で確認済み）

`order` と `target` だけ書いた `.meta.json` に、Studio が起動していると `id` が追記される。既存キーは保たれ、`cross_series_prev/next` は追加されない。**スキルが `id` を書かないのは正しい。**

### 4.4 新しいシリーズを作ると `contents/.meta.json` が書き換わる

loader が `order` の末尾に新シリーズ名を追記する。**草稿を破棄したときは、このファイルの差分も戻すこと**（`git checkout -- dx-training-studio/contents/.meta.json`）。

### 4.5 `order` は後から直す必要がある

`order` には実在するディレクトリだけを書く。後からコースやレッスンを足したら、**親の `.meta.json` の `order` を計画書の順に直す**。直さないと末尾に追加されて並びが崩れる。

⚠ **2026-08-11 追記: ペイン4 の agent は `.meta.json` を書けない**（`contents-write-gate` でアプリ管理ファイルとして保護された）。ペイン4 経由で回す場合、並べ替えは**ペイン1・2 のドラッグで人がやる**。Claude Code で回す場合は従来どおり直接編集できる。

## 5. 守るべき作法

### 5.1 OpenSpec

- planning home は **`dx-training-studio/`**（リポジトリルートではない）。ルートから叩くと `No OpenSpec changes directory found`
- `openspec validate <change> --strict` は**リポジトリルートからだと `Unknown item` になる**。planning home に入ってから叩く
- **`openspec-sync-specs` スキルはこの環境に無い。** archive 時の同期は手作業。本体 spec を直接書き、`npx openspec validate --specs` が通ることを確認する。**件数は change ごとに増える**（前版の「42件」は古い。2026-08-11 時点で 54 件）ので、数を暗記せず実行時の出力で見る
- ⚠ **手作業同期した change は `openspec archive` が使えない。** delta を spec へ再適用しようとして、RENAMED の元見出しが無いと `Aborted. No files were changed.` で止まる。`openspec/changes/archive/<yyyy-mm-dd>-<change名>/` へ**ディレクトリ移動でアーカイブする**
- delta 側の要件見出しは必ず `### Requirement: <名前>`。**要件内の小見出しに level-3 を使わない** — 同期すると要件がシナリオから切り離され、`validate --specs` が「scenario が無い」で落ちる（2026-08-11 に踏んだ）。太字段落にする
- `openspec/changes/` は `.gitignore` されている。**コミットされるのは `openspec/specs/` だけ** — 設計の記録はそこにしか残らない
- アーティファクトは日本語で書く

### 5.2 スキルの SSoT 作法

スキルの作成・更新には **`creating-skills` スキルを使う**。SSoT 監査とハードコード・不整合レビューがゲートになっている。

- `SKILL.md` は 200行が目安・500行が上限。`references/` は各300行以内、100行超なら目次
- **同じ内容を2箇所に書かない。** 特に `SKILL.md` に references の本文を写さない（spec の要件でもある）
- 外部ファイル（`lib/schema.ts` 等）の内容をスキルに写さない。参照先を示す

### 5.3 その他

- 出力は日本語
- `npm run lint` は既存エラーが残っている。増やしていないかだけ見る
