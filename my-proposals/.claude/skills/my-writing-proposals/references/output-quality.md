# レビューの観点

完成した提案文書を読み直すときの観点。人間のレビューと、意思決定者役のサブエージェントレビューで使う。

出力前にAIが全項目をセルフチェックするためのものではない。出力は人間が磨く草稿として渡す。

## 結論と構造

- [ ] 1行目が結論（＝相手へのお願い）になっている。要約で終わらず「だから何をしてほしいか」まで言い切っている
- [ ] 全体像 → 詳細の順になっている
- [ ] 事実・解釈・提案が混ざらず分かれている
- [ ] 情報が階層構造（◎ → ・）で整理され、同じ階層に同じ粒度の情報だけが入っている
- [ ] 選択肢を示す場合、主要な案を網羅したうえで推奨案を明示している
- [ ] 節構成が提案の中身から決まっている。例の節構成をそのまま当てはめた形になっていない

## 件名と冒頭

- [ ] 件名が1件に絞られている。括弧で補足を足していない
- [ ] 「〜について」「〜の件」で逃げず、具体的なお願いになっている

## 具体と数字

- [ ] 人数・期間・金額が具体的に書かれている。「数名」「希望者」「早めに」でぼかしていない
- [ ] 終わったときに何をもって成功とするかが書かれている
- [ ] 撤退・中止の基準が必要な提案なら、それが書かれている
- [ ] 通ったあと誰が何をするかが書かれている
- [ ] その数字・期限・段取りが、ユーザーの言葉に基づいている。AIが作ったものがない
- [ ] 推定を使った場合、計算の根拠が読み手に見える
- [ ] 「品質」「早急に」など解釈の分かれる言葉に具体的な定義がある
- [ ] 重要な数値や根拠が本文に書かれている（リンク頼みにしない）

## 読み手への配慮

- [ ] 読み手が知らない固有名詞・専門用語が、初出で説明されている
- [ ] 読み手の頭に浮かぶ懸念が、指摘される前に自分から出されている
- [ ] 読み手が複数いる場合、1人に焦点が合っている。他の読み手の関心は懸念で拾っている
- [ ] スコープ外の話が、否定形の断りではなく肯定形で次に回されている
- [ ] 過去を否定する書き方になっていない（変える提案の場合）

## ストーリー

- [ ] 合意したストーリーレベルの箇所数に収まっている
- [ ] 絵で書き始めていない。結論が先に来ている
- [ ] Lv1 以上なら、実際に見た場面が入っている。抽象語（非効率・重要・課題・改善）で済ませていない
- [ ] その場面はユーザーが語った事実で、AIが作ったものではない
- [ ] 山場の絵が1つに絞られている。全部が山になっていない

## 文章表現

- [ ] 一文が長すぎない（一文一義）。ただし削りすぎて意味が抜けていない
- [ ] 同じ意味の言葉の表記揺れがない（用語が一貫している）
- [ ] 過剰な敬語で冗長になっていない
- [ ] 箇条書きはMECE（漏れなく重複なく）で、語尾が統一されている
- [ ] 期限があるなら日時まで具体的（例：2026/07/01 17:00）。「予定」ではなく確定表現になっている
- [ ] 要点が1つだけの短い内容を、無理に階層化していない
- [ ] 意味の区切りで改行され、視覚的に読みやすい

## Purpose

- [ ] 織り込むなら1箇所だけ。繰り返していない
- [ ] 独立したセクションになっていない
- [ ] Purpose の言葉をそのまま引用せず、提案の文脈に言い換えている
- [ ] 接点がないのに無理に入れていない

## 出力形式

- [ ] 作業フォルダの `output/` フォルダに Markdown で保存した
- [ ] チャットにもコードブロックで出力した
- [ ] ファイル名から提案の内容が分かる
- [ ] 提案文書の中に太字などの markdown 装飾が入っていない
- [ ] 日本語で書かれている
- [ ] サブエージェントレビューを実施するかユーザーに確認した
