# Claude API チャットツール 設計メモ（ファイル生成方式）

Next.js ベースで Claude Code のようにスキルを動かすチャットツールの設計たたき台。
大きいファイル出力とストリーム不可の2つの制約への対処をまとめる。

---

## 1. 現状と課題

- Next.js 製ツールを `npm run dev` で起動し、Windows の localhost で使用。
- Docker は使えない。Blob / データベースは未使用。
- Markdown の出力はできるが、**HTML のようにサイズの大きいファイルを JSON で受け取ろうとすると失敗する**。
- 実際の社内利用では **ストリーム出力が使えず**、応答を待ってまとめてデータを受け取る形にならざるを得ない。

---

## 2. 根本原因

JSON で大きい HTML を受け取る方式には二重の弱点がある。

1. HTML 全文が出力トークンに乗るため `max_tokens` で切れる。
2. 切れた瞬間に JSON として壊れ、パース不能になる。

さらに、長い応答を単一の HTTP リクエストで待つと、Nginx やロードバランサ、プロキシのタイムアウトで切れることがある（これが隠れた原因の場合もある）。

結論：**「JSON で成果物本体を受け取る」設計そのものをやめる。**

---

## 3. 基本方針：モデルの仕事とサーバーの仕事を分離する

Claude Code のスキルが大きいファイルを扱えるのは、ファイル内容を LLM の出力トークンに乗せず、**ツール実行（コード実行）でディスクに書く**から。同じ発想を採る。

| 役割 | 内容 |
|---|---|
| モデルの仕事 | ファイルを書く**コード**（Node/Python）を生成する。成果物本体は書かせない。 |
| サーバーの仕事 | そのコードをサンドボックスで実行し、決まったディレクトリに保存する。 |
| チャットへの返却 | 「生成しました」＋ファイルパス／ダウンロードリンクのみ。 |

### なぜ効くか

- モデルの応答は短いコードだけなので `max_tokens` で切れない。
- JSON パース失敗も起きない。
- 実際の HTML は「実行結果」としてディスクに直接書かれる。
- 例：「1000個の div を生成するループ」のような **数KBのコード**を書けば、実行結果は**数十KBの HTML** になる。出力トークンの制約を実行時に迂回できる。

---

## 4. 実装（Windows ローカル / Docker なし版）

コンテナ隔離は諦め、「子プロセス＋書き込み先の固定＋タイムアウト」で現実的な安全性を確保する。生成するコードが自分の指示由来である個人／社内ツールなら、これで十分実用的。

```js
// app/api/generate/route.js
import { execFile } from "node:child_process";
import { writeFile, mkdir } from "node:fs/promises";
import path from "node:path";
import os from "node:os";

const OUTPUT_DIR = path.resolve("C:/tools/output"); // 出力先を固定

export async function POST(req) {
  const { userRequest } = await req.json();

  // 1. モデルにコードだけ生成させる
  const res = await anthropic.messages.create({
    model: "claude-opus-4-8",
    max_tokens: 4096,
    messages: [{
      role: "user",
      content: `${userRequest}\n\nNode.jsスクリプトのみ出力。fs.writeFileSync でカレントディレクトリ配下の相対パスに書くこと。絶対パスや .. は使わない。コードフェンスや説明は不要。`,
    }],
  });

  let code = res.content.filter(b => b.type === "text").map(b => b.text).join("");
  code = code.replace(/```[a-z]*\n?/gi, "").trim(); // 念のためフェンス除去

  // 2. 一時ファイルに書く
  await mkdir(OUTPUT_DIR, { recursive: true });
  const scriptPath = path.join(os.tmpdir(), `gen-${Date.now()}.js`);
  await writeFile(scriptPath, code, "utf8");

  // 3. cwd を出力先に固定して実行（タイムアウト付き）
  const result = await new Promise((resolve) => {
    execFile("node", [scriptPath], {
      cwd: OUTPUT_DIR,
      timeout: 15000,
      windowsHide: true,
    }, (err, stdout, stderr) => {
      resolve({ ok: !err, stdout, stderr: stderr || err?.message });
    });
  });

  return Response.json(result);
}
```

## 5. Windows 固有・実装上の注意点

- **node の解決**：`execFile("node", ...)` は PATH の `node` を使う。`npm run dev` と同じ環境なら通る。解決しない場合は `process.execPath`（今動いている Node 自身のパス）を使うと確実。
- **パス区切り**：`C:/tools/output` のようにフォワードスラッシュでも Node は解釈する。`path.join` / `path.resolve` を通しておけば区切り文字は気にしなくてよい。
- **書き込み先の固定**：`cwd` を出力先にし、プロンプトで「相対パスのみ・`..` 禁止」を指定。モデルが絶対パスを書く可能性はゼロではないので、心配なら実行前にコードを検査し、`writeFileSync` の引数に絶対パス（`C:\` や `/` 始まり）や `..` が現れたら弾くガードを足す。個人ツールなら、まずプロンプト指定だけで運用開始 → 問題が出たら足す、で可。
- **タイムアウト**：無限ループ対策。`15000`（15秒）は目安。生成物の規模に応じて調整。
- **コードフェンス除去**：`.replace(/```[a-z]*\n?/gi, "")` で剥がすか、システムプロンプトで強く指定。

## 6. ストリーム不可への対処（社内利用向け）

`stream: false` のままで問題ないが、長い応答が LB / プロキシのタイムアウトで切れるのを避けるため、**ジョブ化（非同期ポーリング）**を検討する。

1. `POST /api/jobs` → ジョブ ID を即座に返す。
2. サーバー側でバックグラウンド実行（Claude 呼び出し＋ファイル生成）。
3. クライアントは `GET /api/jobs/{id}` を数秒間隔でポーリング。
4. 完了したら結果とダウンロードリンクを返す。

- 状態保存は本来 DB / Redis が定石だが、現状 DB 未使用のため、まずは**ローカルツールなら単一リクエスト同期方式で十分**なことも多い。タイムアウトが問題になったらジョブ化する、という段階導入でよい。
- 進捗表示（「生成中...」）を出せるのがジョブ化の利点。フロントは `useEffect` ＋ `setInterval` でポーリング。

---

## 7. ダウンロード導線

- `OUTPUT_DIR` を `public/output` にすれば `http://localhost:3000/output/xxx.html` で直接開けて手軽。
- ただし dev サーバーが生成ファイルを監視して再読み込みが走ることがある。うるさければ `public` の外に出し、ファイルを返す API ルートを1本立てる。

## 8. 継続生成（参考／非推奨）

どうしてもモデル自身に HTML 全文を書かせる方針を続ける場合は、`stop_reason` を見て継続生成する。ただし境界でズレやすいため、**コード実行方式を強く推奨**。

```js
let full = "";
let messages = [{ role: "user", content: prompt }];
while (true) {
  const res = await anthropic.messages.create({
    model: "claude-opus-4-8",
    max_tokens: 8192,
    messages,
  });
  const text = res.content.filter(b => b.type === "text").map(b => b.text).join("");
  full += text;
  if (res.stop_reason !== "max_tokens") break;
  messages.push({ role: "assistant", content: text });
  messages.push({ role: "user", content: "続きを最初から繰り返さず出力して" });
}
```

## 9. 軽量モデル（GPT-5 nano 等）への対応

今回の方式は軽量モデルと**相性が良い**。モデルに求めるのが「HTML全文」ではなく「ファイルを書く短いコード」なので、出力トークンが少なく、途中で切れて壊れるリスクが構造的に下がる。軽量モデルほどこの分離方式の恩恵が大きい。

ただし軽量モデルは指示への忠実さが落ちるため、**完了率**を守るには入口（プロンプト）と出口（実行前検査・リトライ）の両方で守りを固める。品質劣化は受け入れつつ、動作が確実に終わることを優先する。

### 失敗しやすい3パターンと対策

| 失敗パターン | 対策 |
|---|---|
| コードフェンスや説明文を混ぜる | プロンプトで出力形式を1行目から縛る／実行前にフェンス除去 |
| コードでなくHTML全文を書き始める | 出力の形を具体的に固定（1行目を `const fs = require("fs");` に強制） |
| 生成コードに構文エラー | 実行前に構文チェック → エラーを添えてリトライ |

### プロンプトを狭く・具体的にする

抽象的な禁止より、出力の形を1行目から縛るほうが効く。

```js
const system = `あなたはコード生成器です。出力はNode.jsスクリプトのみ。
1行目は必ず const fs = require("fs"); で始める。
fs.writeFileSync で相対パスに書く。絶対パスと .. は禁止。
説明文・コメント・コードフェンス(\`\`\`)は一切出力しない。`;
```

### 実行前検査＋リトライをループにする

軽量モデルは1回で通らないことがある。「壊れていたら投げ直す」を数回まで許すと完了率が大きく上がる。

```js
async function generateAndRun(userRequest, maxRetries = 3) {
  let lastError = "";
  for (let attempt = 0; attempt < maxRetries; attempt++) {
    const res = await client.messages.create({ /* system + userRequest + lastError */ });
    let code = extractText(res).replace(/```[a-z]*\n?/gi, "").trim();

    // 1. 構文チェック（実行せずに壊れを検出）
    try {
      new Function(code);
    } catch (e) {
      lastError = `前回のコードは構文エラー: ${e.message}。修正して。`;
      continue;
    }

    // 2. 安全ガード（絶対パス・.. を弾く）
    if (/writeFileSync\s*\(\s*["'`](?:[A-Za-z]:[\\/]|\/|.*\.\.)/.test(code)) {
      lastError = "絶対パスや .. は禁止。相対パスで書き直して。";
      continue;
    }

    // 3. 実行
    const result = await runInSandbox(code); // 前述の execFile 方式
    if (result.ok) return result;
    lastError = `前回の実行エラー: ${result.stderr}。修正して。`;
  }
  throw new Error(`${maxRetries}回試行しても完了しませんでした: ${lastError}`);
}
```

- `new Function(code)` で**実行せずに構文だけ検査**できる。壊れを捕まえてエラー内容をモデルに返すと、軽量モデルでも次の試行で直せることが多い。
- 実行時エラー（`stderr`）も同様に投げ直す。この「エラーを添えてリトライ」が、忠実性の低いモデルでも実用的な完了率をもたらす。

### タスクを小さく割る

骨格HTML（テンプレート）はサーバー側のコードに固定で持ち、モデルには「差し込む部分のデータ生成」だけを任せる。失敗の余地が減り、完了率・品質ともに安定する。品質が劣化しても崩壊しにくくなる。

### モデル差を設定で吸収する

`model` / `max_tokens` / リトライ回数をモデルごとに切り替えられるようにしておく。軽量モデルは `max_tokens` を余裕を持たせ（コードが多少長くても切れないように）、リトライ回数を多め（3〜5回）にする。

### API プロバイダの差はアダプタ層で吸収

GPT-5 nano は OpenAI API になるため、レスポンスの取り出し方が変わる（`data.content` ではなく `choices[0].message.content`）。差を吸収する薄いアダプタ層を1枚かませ、`generateAndRun` から下は共通にする。

```js
// アダプタの例
async function extractText(providerResponse) { /* Claude / GPT の差をここで吸収 */ }
```

## 10. この手法をいつ使うか（小さいファイルには常用しない）

この手法は**コストとレイテンシを払って「大きい出力を回避する」ためのもの**。小さいファイルにはその対価が見合わない。常用すべきではない。

### 直接生成のほうがよいケース

数行の Markdown、短い JSON、設定ファイルなど小さい成果物は、**モデルに中身を直接書かせて受け取り、サーバー側で `writeFileSync` する**ほうが速くて単純。コード生成方式だと「書くためのコード生成 → 検査 → 子プロセス起動」と一手間ずつ増え、プロセス起動ぶんレイテンシも余計にかかる。小さい出力ではこのオーバーヘッドが本体より大きくなる。

### 分岐の目安

**「1回のレスポンスに安全に収まるか」**で分ける。

| 条件 | 採る方式 |
|---|---|
| 出力が `max_tokens` に対して十分小さく、切れる心配がない | 直接生成 → `writeFileSync` |
| 切れるリスクがある／ループ・反復で機械的に膨らむ（1000行テーブル、大量要素HTML） | コード生成＋サンドボックス実行 |

### 実装：2ルートを持って振り分ける

- 「短いテキスト成果物 → モデルに直接書かせて `writeFileSync`」
- 「大きい・反復的なもの → コード生成＋サンドボックス実行」

リクエストの種類か想定サイズで選ぶ。ツールの性格上どちらか一方しか出さないなら、片方だけでも構わない。

### 軽量モデルでの逆転に注意

軽量モデルを使う場合、**小さいファイルでもコード生成方式のほうが壊れにくい**ことがある。忠実性の低いモデルに Markdown 本文を直接書かせると余計な説明やフェンスが混ざりやすいのに対し、「短いコードを書け」のほうが形式を縛りやすいため。「小さい＝常に直接生成」とは限らず、**モデルの素直さも見て決める**のが実際的。

### まとめ

この手法は万能の既定ではなく、**大きい出力・反復的な出力・忠実性の低いモデル**という条件で効く道具。小さくて素直に書ける出力には、直接生成のシンプルな経路を残しておく。

## 11. なぜ大きい出力を回避できるのか（データとロジックの分離）

この手法の核心は「**テキスト全文をコードに渡さない**」こと。ここを誤解すると効果がゼロになるので明記する。

### アンチパターン：全文を文字列リテラルに埋める

モデルに HTML 全文をコード内の文字列として書かせる形は**効果がない**。出力トークンは全く節約できていない。

```js
// ❌ アンチパターン：HTML全文がコードに埋まり、出力トークンを消費する
fs.writeFileSync("out.html", "<html>...(数万文字)...</html>");
```

### なぜ効くのか：大きさは「反復」から来る

出力が大きくなる主因は、中身がユニークで情報量が多いからではなく、**構造が反復しているから**。1000行のテーブルは「1000個の異なる事実」ではなく「1行のパターン × 1000」であることが多い。だからモデルは全文でなく**ループ**を書けばよい。可逆圧縮に近く、規則性のあるものほどよく縮む。

```js
// ✅ 数百バイトのコードが、実行時に数万バイトを生成する
const fs = require("fs");
const rows = Array.from({length: 1000}, (_, i) =>
  `<tr><td>${i}</td><td>Item ${i}</td></tr>`).join("");
fs.writeFileSync("table.html", `<table>${rows}</table>`);
```

大きさを生むのは実行時のループであって、モデルの出力ではない。ここが分離のキモ。

### 本質的にユニークで長大な入力が必要な場合

中身が非圧縮的（各行が独立した長文で規則生成できない）なら、**この手法だけでは解けない**。その情報はモデルの外から供給する。扱いは次の三層に整理できる。

| ケース | 扱い | データはどこに乗るか |
|---|---|---|
| 反復的な大きさ | ループ（ロジック）に押し込む | モデル出力にもコードにも乗らない（実行時に生成） |
| 既存のユニークなデータ（CSV/DB/API 由来） | 「読んで整形するコード」を書かせる | 実行時にディスク/APIから読む。モデルにもコードにも乗らない |
| モデルに創作させるユニークな長文 | 分割生成（テンプレート固定＋チャンク追記） | 出力トークンは必ずかかる。安全な単位に割って完了を担保 |

既存データを読むパターンの例：

```js
const data = JSON.parse(fs.readFileSync("input.json")); // 本体はここ。モデル出力に乗らない
const rows = data.map(d => `<tr><td>${d.name}</td></tr>`).join("");
```

### まとめ

コントロールの実体は三層。**反復はロジックに押し込む／既存データは実行時にファイルから読む／モデルが創作するしかない長文だけ分割して少しずつ出す**。「コードに長大なテキストを文字列で埋め込む」形は避けるべきアンチパターンで、正しく設計すればそれ自体が起きない。

---

## 12. まとめ

| 制約 | 対処 |
|---|---|
| HTML が大きすぎて JSON 受信でエラー | ファイルはコード実行でディスクに書き、チャットにはパス／リンクのみ返す |
| ストリーム不可 | まずは同期方式、タイムアウトが問題ならジョブ化＋ポーリング |
| Docker なし / Windows ローカル | 子プロセス＋書き込み先固定＋タイムアウトで実用的な安全性を確保 |
| 軽量モデルで完了させたい | 出力形式を1行目から縛る＋構文チェック＋エラー添えリトライ＋テンプレート固定 |
| 複数プロバイダ対応 | アダプタ層で API 差を吸収し、`generateAndRun` 以下を共通化 |
| 小さいファイルの扱い | 常用しない。切れる心配のない小さい出力は直接生成→`writeFileSync`（ただし軽量モデルでは逆転あり） |
| コードに長大テキストを渡す不安 | 全文を文字列に埋めない。反復はループ／既存データは実行時に読む／創作長文だけ分割生成 |

**設計の肝：「モデルの仕事＝ファイルを書く手順の生成」「サーバーの仕事＝実行と保存」を分離すること。**
