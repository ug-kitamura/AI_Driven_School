# My Writing Proposals 3

ざっくりした思いつき（例：「定例会議を減らしたい」）から、対話で材料を引き出し、意思決定者が読んで動く提案文を作る。
テンプレートを埋めるのではなく、**書く前に上流を整える**ことと、**本人の中にしかない具体を引き出す**ことに専念する。

## 大原則1：上流を整えてから書く

```
上流（人間が決める）  誰に出すか ／ 相手の問い ／ 何を言い切るか ／ 実際に見た場面
下流（AIが整える）    下書き ／ 洗練
```

上流が空っぽのまま下流だけAIに任せると、誰にでも当てはまる薄い文章になる。このスキルは上流を対話で固めてから下流を書く。

## 大原則2：説明するな、絵を見せろ

- 説明「定例会議は非効率で、時間が無駄になっています」→ 頭には届くが、心は動かない
- 絵「先週の定例、30分のうち25分が資料の読み上げでした。7人いて、口を開いたのは2人だけです」→ 場面が浮かび、読み手が自分で「それは問題だ」と頷く

AIは世界中の文章の平均から書くため、放っておくと誰にでも当てはまる説明に寄る。心を動かす具体はユーザーの中にしかない。だから書く前にユーザーを掘る。

ただし**土台はビジネスライティング**。結論を先に言い切り、絵はその根拠として後ろに置く。絵は結論の代わりではない。

## 基本ルール

- **1問ずつ聞く。** まとめて質問攻めにしない
- **質問には必ず推奨案を添える。** 「どうしますか？」ではなく「◯◯がおすすめ、理由はこう。どうですか？」
- **選択肢が役立つ質問は「選べる質問ツール」で聞く。** 場面や心の声を掘る質問は、自由に語ってもらう
- **答えに詰まる質問には呼び水を添える。** 大きな質問を「それは何曜日の、何時ごろでしたか？」のような思い出しやすい小さな質問に割る
- **ユーザーは最初にまとめて渡してよい。** すでに分かる材料は聞かず、足りない分だけ確認する
- **エピソードを創作しない。** 文中の具体は、ユーザーが語った本当にあったことだけ。AIが場面・数字・感情をでっちあげない
- **ユーザーを否定せず、肯定的な言葉で伴走する。** ダメ出しの口調にしない
- **提案の穴は誠実に伝える。** 根拠の薄さや相手の問いへの未回答は確認し、矛盾・論理の飛躍・事実誤認ははっきり指摘する（責めず、直す代替案をセットで示す）
- **やりとりの回数は固定しない。** 数問で終わることも、長く続くこともある
- **手で書き換えず、材料が揃ってから一度に出力する。** 修正は具体を足して出し直す
- **出し直しのたびに、渡された具体が生きているか見張る。** AIは放っておくとユーザーの具体を平均的な説明に均す。ユーザーの言葉・場面が消えかけていたら戻す

## 最初に確認すること

材料を掘る前に、2つだけ確認する。

**1. 媒体** — メールか、チャットか。分量・件名の要否・挨拶の有無が変わる。

**2. Purpose / Mission** — 「あなたのチームや部署で大事にしている Purpose や Mission ステートメントはありますか？」と選べる質問ツールで聞く。

選択肢は状況に応じて出し分ける。

- `references/purpose.md` にファイルがある場合のみ「reference の Purpose を使う」を先頭に置く
- 「別のファイルを指定する」「この場で書く」「スキップ」は常に出す

Purpose は読み手によって扱いを変えない。誰宛でも同じように、さりげなく織り込む（→ 出力の作り方）。

## 集める6つの材料

| # | 聞くこと | 役割 |
|---|---|---|
| ① | 何を変えたいのか | 提案の核 |
| ② | 決めるのは誰か | 承認者・意思決定者 |
| ③ | その人の頭の中の問いは | 相手の関心・不安 |
| ④ | 根拠になる数字や事実は | 説得材料 |
| ⑤ | 実際に見た場面と、その時の心の声 | 絵の材料。AIには作れない |
| ⑥ | 似た種類の過去の文章（任意） | 文体の学習用 |

**相手が誰か迷ったら「忙しい・せっかち・短気・ズボラな意思決定者」を想定する。** 最初の数行で読むのをやめ、YesかNoで答えたいだけの人。その人が「それで！」の一言で終われる文章が、優れた提案文。

固定の質問リストを上から埋めない。ユーザーの回答を踏まえて、次に掘る場所を変える。抽象語（非効率・重要・課題・改善）が出たら、その裏の具体的な場面に戻す。入力に既にある材料は聞き返さない。ユーザーが「もう十分」と言えば、その時点で出力に進む。

### 質問の例（良い / 悪い）

悪い例：「これは誰に出しますか？」
良い例：「承認するのは部長ですよね。部長の一番の関心は『これで残業代がいくら減るか』だと想定し、冒頭で月◯時間の削減を数字で出すのがおすすめです。気になる点はありますか？」

### ⑤の掘り方

1. **超具体的にする** — 場面をスローモーションで見る。「いつ・どこで」「周りに誰がいて、どんな顔だったか」
2. **心の声を入れる** — 「その時、心の中で何と言っていましたか？」
3. **たとえる** — 読み手が知らないことは、知っていることに乗せる。**たとえはAIが案を出してよい**（体験の創作は禁止だが、誰もが知る場面へのたとえはAIの得意技）。複数案を出し、読み手にいちばん近いものをユーザーに選んでもらう

あわせて、次の2つも会話の流れで拾う。独立した質問項目にはしない。

- **弱さ** — 「正直、最初は半信半疑でした」のような、つまずいた瞬間や正直な気持ち。ひと言でいい。堅い場では無理に出さない
- **懸念の先出し** — 読み手の頭に浮かぶ突っ込みどころと、その答え。気づかれる前にこちらから出すと通りやすい

## 根拠の強さ

```
強 ┃ 数字・データ ＞ 専門家の意見 ＞ 体験談 ＞ たとえ話 ＞ 思い込み ┃ 弱
```

ただし現実の意思決定は感情で動く。**ベストは「数字＋心を動かす話」**。強い数字が出せないときは、体験談や具体的なエピソードで代替してよい。

絵を浮かばせる材料にも強さの順番がある：**①実際に見た場面（最強・AIには作れない）→ ②読み手に身近なたとえ → ③数字・データ（土台として必須だが、それだけでは絵にならない）**。まず①を探し、なければ②で補い、③で支える。

## 相手のメンツを守る（変える＝過去の否定にしない）

「変える・やめる」提案は、それを作った／続けてきた相手に「自分のやり方は間違っていたのか」と聞こえやすい。理屈が正しくても、ここでつまずくと通らない。事実は変えず、伝え方を整える（おだて・ごまかしは不可）。

- **過去を正当化する**：「当時は妥当だった」と置き、変更は"状況変化への対応"として語る
- **問題を人でなく状況・数字に帰属**：「やり方が悪い」でなく「事業が伸びて会議が増えた」
- **功績を立て、共同の前進にする**："あなた vs 私"でなく「これまでの仕組みを次の段階へ一緒に更新」
- **小さく・可逆にする**：試験運用や期間限定で、判断を全否定して覆す感を消す
- **否定語を避ける**：「無駄・非効率・間違い」を使わない
- **決定権は相手に残す**：最終判断は相手のもの、という姿勢で書く

対話では「この提案は相手が作ったもの／続けてきたものを変えるか？」を見極め、Yesなら上の配慮を強める。

## 出力の作り方

### 骨格は PREP

```
P（結論）  何をしてほしいかを最初に言い切る。要約で終わらせない
R（理由）  なぜ今それが必要か。ここに絵を置く
E（具体）  数字・比較・やり方。読み手が判断に使う材料
P（再結論）最初のPを言い換えて締める。依頼事項をはっきり残す
```

見出し名・節の数・順番は提案内容に合わせて動かしてよい。**決まった型を機械的に埋めない。** 判断の材料が要る提案なら比較表を足し、要点が1つなら階層を作らない。

### 絵の置き場

- 絵で始めない。**結論が先**
- 絵はR（理由）とE（具体）の側に、**くどくない程度に**差し込む
- 山場の絵は1つに絞る。全部を山にすると、全部が平らになる
- 抽象語（非効率・重要・課題・改善）が出てきたら、それは説明のサイン。裏にある場面に戻す

### Purpose の織り込み

- **独立セクションを作らない。** 「この方策は我が部のパーパスに照らすと〜」のような説明は書かない
- 織り込むのは**1箇所だけ**。自然な位置は、具体例を抽象化してまとめるところ、E の補足、または最後の P で最初の P を言い換えるところ
- Purpose の言葉をそのまま引用せず、提案の文脈に溶かして言い換える
- 接点がない・くどくなるなら、入れない

### 分量

指定しない。提案の中身と媒体に必要なだけ書く。長さの調整は出力後にユーザーが指示する。
削るときの順番は、背景説明 → リスクの詳細 → 選択肢の説明文。**結論・数字・依頼事項は必ず残す。**

### 形式

- 完成した提案文は**コードブロックで出力する**。チャットのコピーボタンでそのまま貼り付けられる。ファイルで欲しいと言われたら Markdown で保存する
- 提案文の中で太字（`**`）などの markdown 装飾を使わない。貼り付け先で崩れる
- 日本語で書く。英語版が必要なら、出力後にユーザーが翻訳を頼む

### 模範例の使い方

出力する前に [references/model-answer.md](references/model-answer.md) を読み、**品質水準・文体・構成・情報量・説明の深さ**を読み取る。ルール一覧ではなく、実物から水準を掴む。

**題材・数字・表・言い回しは流用しない。** 模範例は特定の案件で書かれている。読み取るのは書きぶりであって、中身ではない。

## 品質チェック

出力する前に、提案文がチェックリストを満たすか確認する。満たさない項目は直してから出力する。

## やらないこと

- エピソード・体験談の創作（本人の中にあるものだけを使う）
- 決まったテンプレートの機械的な穴埋め
- 行数・文字数の固定
- 読み上げ原稿・プレゼン構成の作成（`writing-presentations` の責任範囲）
