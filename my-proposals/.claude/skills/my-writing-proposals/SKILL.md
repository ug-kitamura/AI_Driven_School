# My Writing Proposals

ざっくりした思いつき（例：「定例会議を減らしたい」）から、対話を通じて材料を引き出し、意思決定者に刺さる提案文書を作る。
テンプレートを埋めるのではなく、**書く前に上流を整える**ことに専念する。

出力は完成品ではなく、人間が磨くための草稿とする。

## 大原則1：上流を整えてから書く

文章は上流と下流でできている。

```
上流（人間が決める）  誰に出すか ／ 相手の問い ／ 何を言い切るか ／ 実際に見た場面
下流（AIが整える）    下書き ／ 洗練
```

上流が空っぽのまま下流だけAIに任せると、誰にでも当てはまる薄い文章になる。このスキルは上流を対話で固めてから下流を書く。

## 大原則2：説明するな、絵を見せろ

- 説明「定例会議は非効率で、時間が無駄になっています」→ 頭には届くが、心は動かない
- 絵「先週の定例、30分のうち25分が資料の読み上げでした。7人いて、口を開いたのは2人だけです」→ 場面が浮かび、読み手が自分で「それは問題だ」と頷く

AIは世界中の文章の平均から書くため、放っておくと誰にでも当てはまる説明に寄る。心を動かす具体はユーザーの中にしかない。だから書く前にユーザーを掘る。

**ただし絵は結論の代わりではなく、根拠。** 絵だけを並べると「で、何が言いたいの」の作文になる。結論を先に言い切り、絵はその後ろに置く。どちらかを残すなら結論。

## 基本ルール

- **1問ずつ聞く。** まとめて質問攻めにしない
- **質問には通し番号を付ける。**「Q1」「Q2」のように対話の最初から単調に増える番号を毎回添える
- **残り目安を毎質問に添える。** ①〜⑥のうちその時点で未確定の項目数から「あと2〜3問ほど」のような概算を算出し、通し番号と並べて示す。目安は都度再計算し、ユーザーの回答で新たな確認事項が生まれれば増えてもよい（減る一方に固定しない）。あくまで概算であることが伝わる言い回しにする
- **質問には必ず推奨案を添える。** 「どうしますか？」ではなく「◯◯がおすすめ、理由はこう。どうですか？」（特に③相手の問い）
- **質問は必ず「選べる質問ツール」で行う。** 推奨案を選択肢にして提示し、テキストで列挙しない
- **ユーザーは最初にまとめて渡してよい。** すでに分かる材料は聞かず、足りない分だけ確認する
- **固定の質問リストを上から埋めない。** ユーザーの回答を踏まえて、次に掘る場所を変える。抽象語（非効率・重要・課題・改善）が出たら、その裏の具体的な場面に戻す
- **答えに詰まる質問には呼び水を添える。** 大きな質問を「それは何曜日の、何時ごろでしたか？」のような思い出しやすい小さな質問に割る
- **ユーザーが言っていないことを、事実の顔で書かない。** 場面・数字・期限・段取り・相手の反応、すべてが対象。手元にない事実は聞く（→ [references/evidence.md](references/evidence.md)）
- **ユーザーを否定せず、肯定的な言葉で伴走する。** ダメ出しの口調にしない
- **提案の穴は誠実に伝える。** 根拠の薄さや相手の問いへの未回答は確認し、矛盾・論理の飛躍・事実誤認など明らかに通らない問題ははっきり指摘する（責めず、直す代替案をセットで示す）
- **やりとりの回数は固定しない。** 数問で終わることも、長く続くこともある
- **手で書き換えず、材料が揃ってから一度に出力する**
- **出し直しのたびに、渡された具体が生きているか見張る。** AIは放っておくとユーザーの具体を平均的な説明に均す。ユーザーの言葉・場面が消えかけていたら戻す

## 最初に確認すること

材料を掘る前に、2つだけ確認する。

**1. 媒体** — メールか、チャットか。**入力から分かるときは聞かない。**「メールで提案文を作って」と言われたら聞き返さず、手がかりがないときだけ1問聞く。

**2. Purpose / Mission** — 「あなたのチームや部署で大事にしている Purpose や Mission ステートメントはありますか？」と選べる質問ツールで聞く。選択肢は次の4つ。

- `references/purpose.md` を参照する
- 自分でファイルを選択する
- 自分で記入する
- スキップする

Purpose は読み手によって扱いを変えない。誰宛でも同じように、さりげなく1箇所だけ織り込む（→「Purpose の織り込み」）。

## 集める6つの材料

| # | 聞くこと | 役割 |
|---|---|---|
| ① | 何を変えたいのか | 提案の核 |
| ② | 決めるのは誰か | 承認者・意思決定者 |
| ③ | その人の頭の中の問いは | 相手の関心・不安 |
| ④ | 根拠になる数字や事実は | 説得材料 |
| ⑤ | 実際に見た場面と、その時の心の声 | 絵の材料。AIには作れない |
| ⑥ | 似た種類の過去の文章（任意） | 文体の学習用 |

④の集め方 → [references/evidence.md](references/evidence.md)

**相手が誰か迷ったら「忙しい・せっかち・短気・ズボラな意思決定者」を想定する。** 最初の数行で読むのをやめ、YesかNoで答えたいだけの人。その人が「それで！」の一言で終われる文章が、優れた提案文書。

### 読み手が複数いるとき

**「誰の一言でこの提案が動くか」を対話で確定し、本文はその1人の問いに答える。** 他の読み手の関心は、懸念の先出しで1行だけ拾う。読み手ごとに別の提案文書を作らない（転送されたときに食い違いが露見する）。

例：「まず課長、最終承認は部長」なら、どちらに焦点を合わせるかを確認する。課長に絞るなら本文はコスト対効果に答え、部長の関心（方向性との整合）は懸念の節で1行触れる。

## ストーリーレベル

読み手の頭に絵が浮かぶ箇所を、いくつ置くか。**②決めるのは誰かが確定した直後に、ユーザーと合意する。** 相手が誰か分からないうちはレベルを選べないので、それより前には聞かない。

| レベル | 絵の箇所 | 中身 |
|---|---|---|
| 0 | 0箇所 | 数字と事実で説得する。味気ないという意味ではない |
| 1 | 1箇所（1〜2文） | 見た場面を1つだけ置く。**既定** |
| 2 | 2〜3箇所 | 背景と懸念の両方に場面が入る |
| 3 | 全編 | 場面で駆動する。社内提案ではほぼ使わない |

合意したレベルが、⑤を掘る深さの上限になる。Lv0 なら⑤を掘らない。

### ⑤の掘り方

1. **超具体的にする** — 場面をスローモーションで見る。「いつ・どこで」「周りに誰がいて、どんな顔だったか」
2. **心の声を入れる** — 「その時、心の中で何と言っていましたか？」
3. **たとえる** — 読み手が知らないことは、知っていることに乗せる。**たとえはAIが案を出してよい**（体験の創作は禁止だが、誰もが知る場面へのたとえはAIの得意技）。複数案を出し、読み手にいちばん近いものをユーザーに選んでもらう

**1回で出なくても諦めない。** 角度を変えて2〜3回試す（回数は目安であって固定ではない）。合意したレベルの箇所数が埋まらなければ、埋まった分だけで書く。場面を作り出してはならない。

あわせて次の2つも会話の流れで拾う。独立した質問項目にはしない。

- **弱さ** — 「正直、最初は半信半疑でした」のような、つまずいた瞬間や正直な気持ち。ひと言でいい。堅い場では無理に出さない
- **懸念の先出し** — 読み手の頭に浮かぶ突っ込みどころと、その答え。気づかれる前にこちらから出すと通りやすい

### 絵の置き場

絵は理由・具体の側に置く。Lv2 以上でも、山場の絵は1つに絞る。全部を山にすると、全部が平らになる。

## 対話の進め方

1. **受け取る**：持ち込まれた提案を読み、分かる材料を①〜⑥に仮置きする
2. **確認する**：媒体と Purpose を確認する（→「最初に確認すること」）
3. **上流を埋める**：不足する①〜③を1問ずつ、推奨案つきで確認する。読み手が複数なら焦点を1人に絞る
4. **レベルを合意する**：②の直後にストーリーレベルを確認する（→「ストーリーレベル」）
5. **根拠を詰める**：④を引き出す。軸を通して不足する事実を聞く（→ [references/evidence.md](references/evidence.md)）。⑥があれば文体の特徴をつかむ
6. **絵を掘る**：合意したレベルの分だけ⑤を引き出す（→「⑤の掘り方」）
7. **出力する**：結論ファーストの提案文書を生成する（→「出力の組み立て」）

ユーザーが「もう十分」と言えば、その時点で出力に進む。

### 対話の流れ（例）

ユーザーが雑に投げ、AIが1問ずつ推奨案つきで材料を引き出す。特に③相手の問いは答えにくいので、質問するだけでなく推奨案を示す。

> ユーザー：定例会議を減らしたい
> AI：Q1（あと4〜5問ほど）：①は「定例会議を減らす」ですね。②決めるのは誰ですか？ チームの定例なら直属の部長が承認者になりがちです。これでいいですか？
> ユーザー：部長です
> AI：Q2（あと3〜4問ほど）：ストーリーはどのくらい入れますか？ 部長宛の社内提案なら Lv1（見た場面を1箇所だけ）がおすすめです。
> ユーザー：それで
> AI：Q3（あと2〜3問ほど）：③部長の頭の中の問いは「どの会議か／何がよくなるか／自分は何をすればいいか」が刺さります。この3つに答える形でOKですか？
> ユーザー：OK
> AI：Q4（あと2問ほど）：③に答えるなら、冒頭で削減時間を数字で出すのがおすすめです。④根拠になる数字はありますか？
> ユーザー：週7本・12時間、直近は7人中2人しか発言していない
> AI：Q5（あと1問ほど）：減らした後は何本・何時間になりますか？ 見当がつかなければ一緒に見積もります。
> ユーザー：3本減らして週9時間
> AI：Q6（あと1問ほど）：⑤その会議で「これは要らない」と思った場面はありますか？

## 相手のメンツを守る（変える＝過去の否定にしない）

「変える・やめる」提案は、それを作った／続けてきた相手に「自分のやり方は間違っていたのか」と聞こえやすい。理屈が正しくても、ここでつまずくと通らない。事実は変えず、伝え方を整える（おだて・ごまかしは不可）。

- **過去を正当化する**：「当時は妥当だった」と置き、変更は"状況変化への対応"として語る
- **問題を人でなく状況・数字に帰属**：「やり方が悪い」でなく「事業が伸びて会議が増えた」
- **功績を立て、共同の前進にする**："あなた vs 私"でなく「これまでの仕組みを次の段階へ一緒に更新」
- **小さく・可逆にする**：試験運用や期間限定で、判断を全否定して覆す感を消す
- **否定語を避ける**：「無駄・非効率・間違い」を使わない
- **決定権は相手に残す**：最終判断は相手のもの、という姿勢で書く

対話では「この提案は相手が作ったもの／続けてきたものを変えるか？」を見極め、Yesなら上の配慮を強める。

## 出力の組み立て

結論を最初に置き、事実・解釈・提案を分ける。骨格は PREP。

```
P（結論）   何をしてほしいかを最初に言い切る。要約で終わらせない
R（理由）   なぜ今それが必要か
E（具体）   数字・比較・やり方。読み手が判断に使う材料
P（再結論） 最初のPを言い換えて締める。依頼事項をはっきり残す
```

**節の名前・数・順番は、毎回ゼロから決める。** 決め方は「この読み手は、何を、どの順で知りたいか」。集めた材料を、その順に並べ替える。決まった節構成を持たない。

- **出力する提案文書では太字（`**`）などのmarkdown装飾を使わない。** 貼り付け先で崩れるため、プレーンな文章にする
- 下位項目が1つだけなら、見出しを使わず本文に含める
- 文章表現のルール → [references/writing-essence.md](references/writing-essence.md)

### Purpose の織り込み

- **独立セクションを作らない。**「この方策は我が部のパーパスに照らすと〜」のような説明は書かない
- 織り込むのは**1箇所だけ**。自然な位置は、具体例を抽象化してまとめるところ、具体の補足、または最後の P で最初の P を言い換えるところ
- Purpose の言葉をそのまま引用せず、提案の文脈に溶かして言い換える
- 接点がない・くどくなるなら、入れない

### 分量

指定しない。提案の中身と媒体に必要なだけ書く。長さの調整は、起動時のユーザー指示か、出力後の指示で行う。
削る必要が出たら、背景説明 → リスクの詳細 → 選択肢の説明文 の順に削る。**結論・数字・依頼事項は必ず残す。**

### 例の使い方

出力する前に [references/examples.md](references/examples.md) を読み、**品質水準・文体・構成・情報量・説明の深さ**を読み取る。ルール一覧ではなく、実物から水準を掴む。

**題材・数字・表・言い回しは流用しない。節構成もそのまま借りない。** 例は特定の案件で書かれている。読み取るのは書きぶりであって、中身ではない。近い提案なら形を借りてよいが、例の形に寄せるために材料を曲げない。

### 出力先

- 完成した提案文書は、必ず Markdown ファイルとして保存する。入力ファイルの有無を保存条件にしない
- 保存先は**作業フォルダの `output/` フォルダ**とする。`output/` フォルダがなければ作成する
- 現在の会話コンテキストから作業フォルダが一意に特定できない場合は、選べる質問ツールで保存先フォルダをユーザーに確認する。作業フォルダが一意に特定できる場合はこの確認をしない
- ファイル名は提案の内容が分かる日本語にする（規則は固定しない）
- 同時に**チャットにもコードブロックで出力する。** コピーボタンで1クリックで貼り付けられる

### 出力の最後に

サブエージェントレビューを実施するかどうか、ユーザーに確認する。**確認せずに実行しない。**

> 意思決定者役のサブエージェントに、最初から最後まで読んだとして時系列で心の声を出してもらうと、自分では気づけない穴が見つかります。実施しますか？

ユーザーが同意したら実行し、指摘を提案文書に反映する。観点 → [references/output-quality.md](references/output-quality.md)

### 締めの言葉

レビューの可否が決まったら（断られた場合も含む）、次の言葉を**そのまま**表示する。言い換えも要約もしない。

> 提案文書を送る前に、あなた自身で文章を磨き上げてください。
> 本スキルは便利ですが、あくまで提案文書作成を支援するためのものです。
> スキルに頼らず提案文書が書けるようになることを目指してください。
> 提案が通ることをお祈りします。

表示は1セッションに1回。この後さらに修正を頼まれても、応じるだけで再表示はしない。

## やらないこと

- 場面・数字・期限・段取り・相手の反応の創作（本人の中にあるものだけを使う）
- 決まったテンプレートの機械的な穴埋め
- 例の節構成の当てはめ
- 行数・文字数の固定
- 英語版の生成（必要なら出力後に翻訳を頼んでもらう）
- 読み上げ原稿・プレゼン構成の作成（`writing-presentations` の責任範囲）
- 確認なしのサブエージェントレビュー実行
