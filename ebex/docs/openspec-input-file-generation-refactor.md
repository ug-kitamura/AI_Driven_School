# OpenSpec 入力ドラフト：ファイル生成方式のリファクタ

Claude API ベースのスキル駆動チャットツールにおける「大きいファイル出力」の実装方針を刷新する。
このドキュメントは OpenSpec の `explore` → `propose` に渡す前提でまとめたもの。
**新方針の説明だけでなく、廃止する旧方針を名指しで含めている**（既存仕様を正しく置換させるため）。

---

## 0. このドキュメントの使い方（OpenSpec 連携）

1. 実装を触る前に、現状の確定仕様を確認する。
   ```bash
   openspec spec list   # 確定済み capability 一覧
   openspec list        # 進行中の変更（提案）一覧
   ```
2. 下記「廃止対象」が confirmed な `specs/`（capability）に残っていれば、
   今回の `propose` で **modify / remove** する変更として扱う（新規追加だけにしない）。
3. `changes/` 止まりでアーカイブされただけなら確定仕様には染み込んでいないので影響は薄い。
4. このドキュメントを explore の入力に渡し、「既存仕様のどれを置換する提案か」を明示させる。

**注意**：アーカイブそのものが自動で新提案を汚染することは基本ない。効くのは確定済み `specs/` の内容。まずそこを確認する。

---

## 1. 背景と問題

- Next.js 製のスキル駆動チャットツール（`npm run dev` / Windows localhost / Docker なし / DB・Blob 未使用）。
- 大きいファイル（特に HTML 図解）の出力でエラーが継続。
- 試行錯誤の結果、実装が多重フォールバックで複雑化した：
  「スクリプト探索 → 無ければ直接生成にフォールバック → `run_script` に `code` が渡らず失敗」。
- 根本原因は **成果物を JSON 形式で受け取っていること**。JSON は全体が揃って初めて妥当になる形式のため、`max_tokens` で途中で切れると `{` が閉じず、連結・パース不能になる。

---

## 2. 今回の設計判断（結論）

### 2-1. JSON で大きい本体を受け取るのをやめる
- JSON × 分割は相性が最悪。途中で切れると構造が壊れる。
- 大きい成果物は **構造化フォーマットで包まない**。

### 2-2. 成果物の性質で受け取り方・経路を選ぶ（汎用化の核）

| 成果物の性質 | 受け取り方 | 例 |
|---|---|---|
| そのまま連結できる素のテキスト | 生のまま継続生成 → 文字列連結 | HTML, Markdown, CSS, コード, SVG, プレーンテキスト |
| 大量レコードの構造化データ | JSONL（1行1オブジェクト）で継続生成 → 行単位でパース | 1万件のレコード等 |
| 小さい構造化データ（切れる心配なし） | 通常の JSON で一括 | メタ情報等 |
| 反復・既存データで機械的に膨らむ | コード生成＋実行（特殊経路） | 1000行テーブル、CSV整形 |

- **既定は「素のテキスト継続生成」**。JSONL は構造化レコードが成果物のときだけ選ぶ。
- JSONL を汎用の既定にはしない（HTML を JSONL 行に詰めるのは無意味な複雑化。軽量モデルは「毎行を妥当な JSON に閉じる」制約を守り損ねる）。

### 2-3. 区切りはモデルの自己申告でなくサーバ側が握る
- 「1万文字ずつ出力して」等の文字数指示は**不安定**（モデルは自分の文字数を正確に数えられない。軽量モデルは特に苦手）。
- 区切りは `max_tokens` ＋ `stop_reason` で機械的に制御する。
- 完了判定は `stop_reason`（`"max_tokens"` なら途中、それ以外で完了）を主とする。マーカー（`<!--END-->` 等）は従。

### 2-4. 継続生成を主経路にする（コア実装）
- モデルには「続きを書く」しか求めない → スキルの書き方・モデルの賢さに依存しない。
- assistant ロールにこれまでの全文を積み、その続きを書かせると境界が自然につながる。

```js
async function generateLargeFile(client, system, userRequest, opts = {}) {
  const { model = "claude-opus-4-8", maxTokens = 8192, maxRounds = 20 } = opts;
  const messages = [{ role: "user", content: userRequest }];
  let full = "";
  for (let i = 0; i < maxRounds; i++) {
    const res = await client.messages.create({ model, max_tokens: maxTokens, system, messages });
    const chunk = res.content.filter(b => b.type === "text").map(b => b.text).join("");
    full += chunk;
    if (res.stop_reason !== "max_tokens") break;   // 完了
    messages.length = 1;                             // 最初の user だけ残す
    messages.push({ role: "assistant", content: full }); // 全文を積み、続きを書かせる
  }
  return full;
}
```

- `maxRounds` で暴走を止める。
- 注意：assistant 継続は毎ラウンド全文を入力に含めるため入力トークンが累積する（分割数 n に対し概ね n² で増える）。数万文字なら実用上問題ないが、極端に大きい場合は「既存データは実行時にファイルから読む」方式と併用する。

#### `max_tokens` の設定方針

- `max_tokens` は「1回の応答で使える上限」であり「毎回それだけ消費する」ものではない。実際の出力が短ければ課金もそのぶんだけ。設定値そのものがコストを上げるのではなく、**1回でどこまで書かせるか＝分割の粒度**を決めている。
- トレードオフ：値を大きくすると分割数が減り入力累積（n²）が下がる ↔ 一発を長くするほど long-output drift（長い出力で構造・品質が徐々に崩れる）が増える。特に軽量モデルで顕著。
- **まず試す段階では両モデルとも 32000 固定でよい**。方式（継続生成＋連結）が動くかの検証に集中でき、「方式が悪いのか設定値が悪いのか」の切り分けが楽になる。先回りでモデル別に作り込まない。
- 問題が出た箇所だけ後から調整する（後追い最適化）：
  - Sonnet 4.6（最大出力 128k）：32k で十分余裕。多くの図解は 1〜2 回で完結。分割を減らしたければ 64k まで上げる選択肢もある。
  - GPT-5 nano（最大出力 128k だが reasoning トークン込み・長出力で品質劣化しやすい）：32k で品質が崩れるようなら 8k〜16k に下げて短く区切る。逆に 32k で動くなら下げる必要はない。nano は reasoning ぶんで成果物が想定より早く切れることがある点に注意。
- 共通原則：**`max_tokens` は「上限＝既定」にしない**。最終的には model / max_tokens / リトライ回数をモデルごとの設定として持たせる。
- 検証時のログ推奨：継続ループの**ラウンド数**を出す。0 回（1 発完了）なら入力累積の問題は起きていない。何度も回るなら、そのとき初めて `max_tokens` を上げて分割を減らす価値が出る。

### 2-5. コード生成＋サンドボックス方式は「特殊経路」に降格
- 主経路から外す。反復的な出力・既存データ整形など「機械的に膨らむ」ケース専用の道具として残す。
- 効くのは「データを生成するロジック（ループ）」を書かせるとき。**HTML 全文を文字列リテラルに埋めるのはアンチパターン**（出力トークンを全く節約できない）。

---

## 3. 廃止対象（propose で明示的に modify / remove する）

以下は今回捨てる旧方針。confirmed な capability に残っていれば削除・変更対象として提案に含める。

- **JSON での成果物受け取り**：廃止。素のテキスト継続生成に置換。
- **スクリプト探索 → 直接生成フォールバックの多重分岐**：廃止。経路は「成果物の性質」で一意に決める。
- **サンドボックス実行を主経路にする設計**：主経路から外し、特殊経路に降格。
- **`run_script` に `code`/`script_path` を渡す前提の生成フロー**：廃止（`code` 欠落で失敗していた原因）。
- **文字数指定による分割（「1万文字ずつ」等）**：採用しない。`max_tokens`＋`stop_reason` に置換。

## 5. 移行の進め方（低コスト・低リスク）

作り直しに見えるが、旧方式は「引き算」で消える部分が多く、コアは `generateLargeFile` 1 関数に集約されるため、実質は差し替え。

1. `feature/generate-v2`（作成済み）で作業。
2. 既存 `/api/generate` は**消さず**、`/api/generate-v2` を**新規追加**して継続生成関数だけをつなぐ（この段階は削除ゼロ＝既存変更が失われる余地なし）。
3. HTML 生成を 1 本通して動作確認。
4. UI の向き先を新ルートへ切り替え。
5. **最後に**旧ルートと死んだ分岐を削除。
6. 過去実装を参照したいときは `git show <commit>:path` / `git diff` で覗くだけ（今のコードは変えない）。

---

## 6. 受け入れ基準（提案に含めたい確認項目）

- HTML（素のテキスト）が `max_tokens` を超える規模でも、途中で壊れず 1 ファイルとして完成する。
- JSON パース失敗・`{` 未閉じ由来のエラーが発生しない。
- スクリプト有無による分岐・`run_script` の `code` 欠落エラーが発生しない。
- 軽量モデル（例：GPT-5 nano 相当）でも「続きを書く」だけで完了率が保たれる。
- 成果物タイプ（html / markdown / code / svg / jsonl-records など）で経路が一意に決まる。

## 7. 次にやること（アクション順）

1. `openspec spec list` / `openspec list` で確定仕様と進行中提案を確認。
2. 廃止対象が confirmed capability に残っているか特定。
3. 本ドキュメントを入力に `openspec` の `explore` を実行し、「既存仕様のどれを置換する提案か」を明示。
4. `propose` で、新経路の追加＋廃止対象の modify/remove を含む変更を起票。
5. `feature/generate-v2` 上で `/api/generate-v2` を追加実装し、動作確認。
6. UI 切り替え → 旧経路削除 → `apply` / `archive`。
