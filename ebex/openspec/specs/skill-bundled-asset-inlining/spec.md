# skill-bundled-asset-inlining Specification

## Purpose

ホスト機能によるオンデマンドの CSS・アイコンのインライン化と、その適用範囲の規約。生成物が単体で開けることを、事前に用意した素材ではなく実物からのコンパイルで保証する。
## Requirements
### Requirement: インライン化はホスト機能として提供する

CSS・アイコンのインライン化はホスト（EBEX）の機能として提供しなければならない（SHALL）。実装はサーバ側の実行時コードとして `lib/agent/tools/` 配下に置かなければならない（SHALL）。開発用の道具箱である `scripts/` 配下へ置いてはならない（MUST NOT）。

インライン化は 1 回のツール呼び出しと 1 回のユーザー確認で完結しなければならない（SHALL）。差し込み・不足素材の取得・再差し込みを複数の呼び出しへ分割してはならない（MUST NOT）。

スキルは、インライン化の手段としてホスト機能の名称・物理パス・ツール名を SKILL.md に記述してはならない（MUST NOT）。目的のみを記述し、手段はホストが解決しなければならない（SHALL）。

#### Scenario: 1 回の呼び出しで完了する

- **WHEN** ユーザーがインライン化に同意する
- **THEN** CDN の除去・CSS の差し込み・アイコンの展開がすべて完了し、追加の呼び出しを必要としない

#### Scenario: スキルがホスト固有の記述を持たない

- **WHEN** 対象スキルの SKILL.md をレビューする
- **THEN** インライン化の記述に EBEX 固有のツール名・物理パス・スクリプト名が存在しない

#### Scenario: 同梱スクリプトと同梱素材が存在しない

- **WHEN** 対象スキルのフォルダを確認する
- **THEN** `assets/` および インライン化用の `scripts/` が存在しない

### Requirement: スタイルはオンデマンドでコンパイルする

インライン化で差し込む CSS は、対象 HTML の実物を入力として、その場でコンパイルして生成しなければならない（SHALL）。事前に生成したサブセットや safelist を用いてはならない（MUST NOT）。

コンパイルには Tailwind CSS v3 を用いなければならない（SHALL）。スキルの額縁が読み込む Play CDN が v3 であり、v4 でコンパイルすると既存の成果物と見た目がずれるため、EBEX 本体の Tailwind のバージョンに追随してはならない（MUST NOT）。

コンパイルはプロセス内の API 呼び出しで行わなければならない（SHALL）。外部コマンド（npm / npx / シェル）を子プロセスとして起動してはならない（MUST NOT）。

対象 HTML が `tailwind.config` による設定拡張（色トークン・フォント等）を持つ場合、その設定をコンパイルへ反映しなければならない（SHALL）。設定の取り込みは任意のコードを評価せずに行わなければならない（SHALL）。データとして解釈できない記述に出会った場合は、設定を取り込まずに処理を継続しなければならない（SHALL）。

#### Scenario: 模範回答の語彙外のクラスも当たる

- **WHEN** 成果物が `bg-gradient-to-br` `md:grid-cols-3` `hover:shadow-lg` `space-y-8` など模範回答に無いクラスを使っている
- **THEN** これらのクラスに対応する CSS が生成され、インライン化後も見た目が変わらない

#### Scenario: 任意値クラスが当たる

- **WHEN** 成果物が `w-[137px]` のような任意値クラスを使っている
- **THEN** 当該クラスに対応する CSS が生成される

#### Scenario: 額縁の設定拡張が反映される

- **WHEN** 額縁が `tailwind.config` で `bosch-*` の色トークンを定義している
- **THEN** インライン化後も `bg-bosch-bg` 等が定義された色で表示される

#### Scenario: 設定にコードが書かれていても評価しない

- **WHEN** `tailwind.config` に関数呼び出しなどデータでない記述が含まれる
- **THEN** その記述は評価されず、設定を取り込まないまま既定のテーマでコンパイルが完了する

#### Scenario: 子プロセスを起動しない

- **WHEN** インライン化を実行する
- **THEN** `npx` などの子プロセスは起動されず、実行時のネットワークアクセスも発生しない

### Requirement: 生成物の自己完結

インライン化後の HTML は、**ネットワークへ到達できない環境でもレイアウトとアイコンが正しく表示されなければならない**（SHALL）。Tailwind および Lucide の CDN 読み込みは除去されなければならず（SHALL）、`lucide.createIcons()` の呼び出しも除去されなければならない（SHALL）。額縁が `tailwind.config` を定義する `<script>` を持つ場合、それも除去されなければならない（SHALL）。

web フォントの `<link>` は除去してはならない（MUST NOT）。到達できる環境では意図した字形で表示し、到達できない環境では額縁の `font-family` に並ぶローカルフォントへ倒れる。倒れても失われるのは字形のみで、レイアウトは保たれる。日本語フォントはサブセット化しても数百 KB〜MB 級になり、埋め込むとインライン化で抑えたサイズの意味が失われるため、埋め込みは行わない。

生成した `<style>` は、文書中に最初に現れる `<head>` へ挿入しなければならない（SHALL）。

#### Scenario: ネットワーク無しで表示できる

- **WHEN** インライン化後の HTML をネットワークに接続していない環境で開く
- **THEN** スタイルとアイコンが正しく表示され、フォントはローカルフォントへ倒れる

#### Scenario: web フォントの読み込みは残る

- **WHEN** 額縁が web フォントの `<link>` を持つ HTML をインライン化する
- **THEN** 当該 `<link>` は除去されず、到達できる環境では意図した字形で表示される

#### Scenario: head が複数あっても最初へ挿入する

- **WHEN** 対象 HTML が入れ子の文書を含み `<head>` が複数存在する
- **THEN** 生成した `<style>` は最初の `<head>` に挿入される

### Requirement: アイコンは inline SVG へ直接置換する

アイコンの展開は `<i data-lucide="X">` を inline `<svg>` へ直接置換する方式でなければならない（SHALL）。SVG スプライトと `<use>` 参照による方式を用いてはならない（MUST NOT）。元の要素の `class` と `style` は生成された `<svg>` へ引き継がなければならない（SHALL）。

アイコンのパスデータはスキルへ同梱せず、ホスト側の依存から解決しなければならない（SHALL）。旧名が新名への再エクスポートになっている場合は、再エクスポートを辿って実体のパスデータを取得しなければならない（SHALL）。

#### Scenario: サイズ指定が引き継がれる

- **WHEN** `<i data-lucide="file-text" class="w-6 h-6" style="color:var(--gray-40)">` を展開する
- **THEN** 生成された `<svg>` は同じ `class` と `style` を持ち、既定サイズによる巨大化が起きない

#### Scenario: 旧名のアイコンが解決される

- **WHEN** 成果物が `<i data-lucide="circle-help">` のように旧名を使っている
- **THEN** 再エクスポート先（`circle-question-mark`）のパスデータが取得されて展開される

### Requirement: 不足アイコンの取得と代替

ホスト側の依存に存在しないアイコン名を検出した場合、代替アイコンへ差し替え、処理を継続しなければならない（SHALL）。検出を理由に処理を中断してはならない（MUST NOT）。差し替えた件数は報告しなければならない（SHALL）。

アイコン解決処理（ホスト側の依存の動的解決）自体が失敗した場合、アイコン名不明による代替差し替えと区別できる形で、開発時に原因を診断できるログを残さなければならない（SHALL）。この失敗を「不足アイコンの代替」と同一の経路で無言に握りつぶしてはならない（MUST NOT）。

インライン化の実行中に外部ネットワークへアクセスしてはならない（MUST NOT）。

#### Scenario: 未知のアイコン名でも完走する

- **WHEN** 生成された HTML が存在しないアイコン名を含む
- **THEN** 当該アイコンは代替アイコンへ差し替えられ、代替件数が報告され、処理は最後まで進む

#### Scenario: アイコン解決処理自体の失敗が診断可能になる

- **WHEN** ホスト側の依存解決（例: 実行時のモジュール解決）が何らかの理由で失敗し、本来解決できるはずのアイコン名が解決できない
- **THEN** 当該失敗の原因を特定できるログが開発時に残る

### Requirement: 処理結果の報告

インライン化は実行結果として、展開したアイコン数・代替へ差し替えたアイコン数・生成した CSS のサイズを報告しなければならない（SHALL）。

コンパイルが実物を入力とするため「同梱 CSS に存在しなかったクラス」という概念は存在しない。未収録クラスの列挙を報告に含めてはならない（MUST NOT）。

#### Scenario: 結果が報告される

- **WHEN** インライン化が完了する
- **THEN** 展開したアイコン数・代替件数・生成した CSS のサイズが報告される

#### Scenario: 未収録クラスの報告が存在しない

- **WHEN** インライン化が完了する
- **THEN** 「未収録クラス」に相当する報告項目は出力されない
