## 2. 次にやること

### 2.0 順序（決定済み）

**「先にスキルを磨く」ではなく「まず1回動かす」。** ただし純粋な後者ではなく、**実物を見なくても正しいと分かるものだけ先に足してから回す**。

```
① lesson-template.md に「マークダウンの運用」を足す   ← 貼るだけ（→ 2.3.1）
② Git / 概念 を1コース回す（L05・L06）              ← 観測（→ 2.1）
③ 昇格基準4項目で判定 → 模範解答に昇格              （→ 3.3・2.2）
④ 観測結果をもとにスキルを磨く                       （→ 2.3）
```

**先に磨く材料が実は溜まっていない。** 4章の発見はすべて「実行時に知るべき事実」で、SKILL.md に反映済み。未反映の改善は 2.3.1 の1件だけで、それも貼れば終わる。フェーズを1つ立てるほどの残作業がない。

**2.3 の大半はそもそも前倒しできない。** 模範解答を読む手順は模範解答が無いと書けず、完了条件の置き場所は草稿が無いと決まらない。

**観測なしの改善は的を外す。** design.md の「レビューは根本的なやり直しを提案しない」がここにも効く——鮭弁当に「野菜を増やしては」は出るが「そもそもサンドイッチでは」は出ない。いちばん知りたい「フェーズを飛ばさないか」は、動かさないと分からない。

#### 何を先に足し、何を実行後に回すか

迷ったらこの1問で振り分ける。

> **実物を見なくても正しいと分かるか？**

| 項目 | 判定 | 扱い |
|---|---|---|
| マークダウンの運用（太字・箇条書き・目次なし） | 見なくても分かる（慣習であって仮説ではない） | **先に足す** |
| 完了条件をどこに置くか | 草稿の形を見ないと決まらない | 実行後 |
| 模範解答を読む手順 | 模範解答がまだ無い | 実行後 |
| フェーズの強化 | 飛ばすかどうか未観測 | 実行後 |

#### 「初回が無駄になるのでは」への答え

ならない。**初回実行は成果物を作る回ではなく、観測装置。** 昇格基準を4項目にしてあるのは、出来の悪い草稿を誤って模範に据えないため。**1本も通らなければ昇格させず、直して回し直す。** それが設計されたループであって、失敗ではない。

### 2.1 初回実行

`dx-training-create` を**コース単位**（既定）で1本回す。

**推奨は `Git / 概念`**（L05・L06 の2本）。理由:

- 社内情報への依存が薄く、**穴だらけにならない**。初回に穴の海を見ると、スキルの出来と社内制約の区別がつかない
- 2本あるので「次のレッスンが前のレッスンを読む」挙動を確認できる
- L05 は空振り確認で1度通してあるので、比較対象がある

避けたほうがよいもの: `はじめに / 環境準備`（L02・L03）と `GitHub / 入門`（L11・L12）。申請系で穴が本文を埋め尽くし、初回の判断材料にならない。

**トンマナは `docs/work6.md` を主、`ads-lecture/` を従として取る。** 模範解答がまだ無いので、初回だけ外から声を持ってくる。

#### 主: `docs/work6.md`（6ヶ月目の卒業制作課題文）

**媒体が同じ**なのが決定的。受講者に宛てた markdown の読み物で、変換なしに写せる。写す対象:

| 仕掛け | 実例（行） |
|---|---|
| 冒頭に流れの箇条書きを置き、何の話かを言い切る | 5〜13 |
| **ステップ末尾に太字で完了条件を置く** | 74・101・129・190。**「やってみる」にそのまま移植できる** |
| `> **見出し：**` のコラムで、本筋を薄めずに脇に出す | 66・119・168 |
| AI への頼み方をバッククォートで丸ごと渡す | 70・121 |
| 「これは一例です」で考えなくてよい範囲を切る | 47・95 |
| 太字は**段落あたり1箇所以下**。一番効かせたい1文だけ | 全体 |
| 番号付きは手順、中黒は並列。使い分けが一貫している | 全体 |

⚠ **blockquote の用途が衝突する。** work6.md は blockquote を「コツ・注意」に使い、うちは「穴」に使う。穴は公開時に消えるので実害は薄いが、**埋めた後にコラムとして残す場合の書き分けを決めること**。`> **社内**:` と `> **分解のコツ：**` が同じ文書に並ぶと読者が区別できない。

⚠ **work6.md は課題文であってレッスンではない。** 章立て（学習目標→本文→やってみる→まとめ→確認問題）と概念の説明の組み立ては写さない——そこは `lesson-template.md` と `design-principles.md` の担当。

⚠ **work6.md は現在 git 未追跡。** 参照させるならコミットしておくこと。

#### 従: `ads-lecture/` 第3回

姿勢の確認用に**1回だけ**。11回で 93万文字・21,198行あるので全部読ませない。第3回は読者への語りかけ（「〜ですよね」系）が最多で、冒頭が難所予告そのものになっている——「今回の講義から、やや難易度が高いと感じられる方が増えていくでしょう」。

**写すのは姿勢であって逐語の文体ではない。** 文字起こしは1行1文の短文でフィラーと言い直しを含む。レッスンは読み物なので、話し言葉のリズムごと持ち込むと冗長になる。

`design-principles.md` は**同じ文字起こしから判断を抽出したもの**で、そのとき声は落ちている。両者は競合しない——**原則は判断を、`ads-lecture` は声を供給する**。

**この読み込みは初回だけ。** 2回目以降は模範解答が声を運ぶので、どちらも開かない（→ 3章）。

**観察すること**（スキル改善のインプットになる）:

| 観点 | 見るところ |
|---|---|
| フェーズを飛ばさないか | 設計メモのファイルが承認前に作られているか。承認なしに執筆に入らないか |
| 穴の粒度 | 社内の穴が「答えるべき問い」になっているか。一般論が混ざっていないか |
| references を読むか | `design-principles.md` と `lesson-template.md` を実際に開いているか。開かないなら参照が弱い |
| 分量 | `estimated_minutes` に対して本文が膨らみすぎていないか |

#### 2.3.1 `lesson-template.md` に「マークダウンの運用」節を足す

work6.md のエッセンスのうち、**規則として簡潔に言い切れるもの**をここに移す。声や密度は言い切れないので書かず、模範解答に運ばせる（→ 3.1）。

`lesson-template.md` の内容を列挙している spec 要件は無いので、**change を立てずに足せる**。

```markdown
## マークダウンの運用

- **太字は段落あたり1箇所まで。** その段落で一番効かせたい1文だけに当てる。
  乱発すると、どれも効かなくなる
- **番号付きリストは手順、中黒は並列。** 順序に意味がないものに番号を振らない
- 並列する情報は文中に並べず箇条書きに開く。ただし**3項目未満なら文のまま**
- 本筋から外れるコツ・注意は `> **見出し：**` のコラムに出す。
  **穴の記法と同じ blockquote なので、穴が埋まるまでは併用しない**
- **目次は置かない。** 学習目標が同じ役割を担う（長い参照文書ではないため）
```

**最後の2行が要。** 前者は blockquote の用途衝突への手当て。後者は**やらないことの明示**で、これが無いと work6.md を見た次のセッションが素直に目次を付ける。

⚠ **work6.md の目次をそのまま真似しない。** work6.md は238行あって「提出物どこだっけ」で戻ってくる参照文書なので目次が効く。レッスンは 10〜15分・2000〜3000字を頭から1回読んで終わりなので、目次を置くと助走が2段になる（目次 → 学習目標 → 本文）。**「冒頭で何の話かを言い切る」の実装が媒体によって違うだけ** — 長い文書では目次、短い読み物では学習目標。

#### 2.3.2 完了条件の置き場所（初回草稿を見てから）

work6.md の**ステップ末尾の太字の完了条件**（74・101・129・190行）は転用価値が高いが、**5章構成のどこに置くかが未定**。「やってみる」の末尾か、まとめか、両方か。初回草稿を見てから決める。

## 3. 模範解答の設計（検討結果）

「模範解答から型やトンマナを抽出する記述をスキルに含める」「模範解答でスキルをスリムにする」という案について。**前者は賛成。後者は条件付き。**

### 3.1 模範解答に担わせるもの

模範解答が**散文の指示より強いのは、規則で書けないもの**に限る。

| 担わせる | なぜ |
|---|---|
| **トンマナ** — 文体、読者への語りかけ方、断定の強さ、専門語を出す間合い | 「親しみやすく」と書いても伝わらない。実物なら1本で伝わる |

初回のトンマナは `docs/work6.md`（主）と `ads-lecture/`（従）から取る（→ 2.1）。**模範解答ができた時点で、その役割は模範解答に移る。** 外部文書を毎回読ませる運用にはしない。

**マークダウンの運用**（太字の当て方、箇条書きの使い分け、コラムの出し方、完了条件の置き方）も模範解答が運ぶ。これらは規則で書くと窮屈になり、実例なら1本で伝わる典型。
| **密度** — 1節あたりの分量、図と文の比率、たとえの長さ | 数値で指定すると機械的になる。実例のほうが速い |
| **穴の書きぶり** — 「答えるべき問い」の具体度 | 抽象的な指示では粒度がばらつく。実例が最も効く |

### 3.2 担わせてはいけないもの

| 担わせない | なぜ |
|---|---|
| **フェーズとゲート** | AI は手順を平気で飛ばす。実例からは「順序を守れ」が読み取れない |
| **出力規約**（パス・`.meta.json`・命名） | 1本の実例からは一般則が導けない。特に `/` を含むレッスン名のような例外は伝わらない |
| **制約**（既存を変更しない等） | 実例には「やらなかったこと」が写らない |

**つまりスリム化できるのは `lesson-template.md` の一部だけ。** 章の役割や分量の目安は模範解答が語れるので削れる。`SKILL.md` のフェーズ・出力規約・制約は削らない——**むしろここを削ると初回実行で観察した「飛ばし」が悪化する。**

### 3.3 昇格基準（提案・前版では未決だった）

**次の4つを全て満たす1本**を昇格させる。

1. 人の手直しが**段落単位で発生していない**（語句の修正だけで済んだ）
2. 社内の穴が、**中身を知らない人でも何を書けばいいか分かる**粒度になっている
3. 「やってみる」が**学習目標を検証している**（演習をこなすこと自体が到達確認になる）
4. 読み返して**冒頭で詰まらない**（時系列レビューで冒頭に指摘が出ていない）

⚠ **「さらっと眺めるといい感じに見える」現象に注意。** 大量の出力は全部それなりに見える。1本ずつ、上の4項目で明示的に判定する。

### 3.4 何本置くか

**まず1本。** ただし**将来2本目が要る可能性が高い**ことを見込んでおく。

29レッスンには構造の異なる型が少なくとも2つある。

| 型 | 例 | 特徴 |
|---|---|---|
| 概念型 | L05・L06・L11・L18 | 穴が少なく、たとえと図で運ぶ |
| 手順型 | L02・L07・L12・L19 | **申請 → 承認待ち → 承認後の実作業**の3段。穴が主役 |

1本目は概念型になる（2.1 の推奨がそこだから）。手順型の出来が悪ければ2本目を足す。**最初から2本作ろうとしない** — 昇格に値するものが2本同時に出る保証がない。

### 3.5 置き場所と形式

```
references/model-answer/
  <レッスン名>.md      ← contents.md をそのままコピー（frontmatter 込み）
  README.md            ← なぜ模範か・どこを写しどこを写さないか（短く）
```

- **本文に注釈を書き込まない。** 注釈を入れると、それ自体が「レッスンの形」として写る
- 写してよいもの／写してはいけないもの（＝内容そのもの）の区別は `README.md` 側に置く
- `model-answer/` が**無い状態は今も正常**（spec で保証済み）。増えても、無い場合の経路を壊さない

## 4. 実行時に効く既知の事実（再調査不要）

2026-08-06 の実装と空振り確認で確かめたもの。

### 4.1 ディレクトリ名の出典は計画書「第5章 コース仕様」

シリーズ名・コース名は第5章の表（`はじめに / DX入門`、`Git / 概念`）。**第2章の全体構造ツリーにある「〜シリーズ」「〜コース」は装飾なので使わない。** レッスン名は第6章の表から取り、`L05` の ID・`【撮】`『【録】』の印・`☆` は落とす。

### 4.2 レッスン名に `/` が含まれるものが2本ある

L13「リポジトリを作る / clone」と L25「ファイル読み書き（CSV / JSON）」。ディレクトリ名では `_` に置換される（`lib/content-filename.ts` の `sanitizeFilename`）。**frontmatter の `lesson` はディレクトリ名のほうに合わせる** — ずれるとディスク側の名前で上書きされる。

### 4.3 `id` は loader が自動で書き足す（実挙動で確認済み）

`order` と `target` だけ書いた `.meta.json` に、Studio が起動していると `id` が追記される。既存キーは保たれ、`cross_series_prev/next` は追加されない。**スキルが `id` を書かないのは正しい。**

### 4.4 新しいシリーズを作ると `contents/.meta.json` が書き換わる

loader が `order` の末尾に新シリーズ名を追記する。**草稿を破棄したときは、このファイルの差分も戻すこと**（`git checkout -- dx-training-studio/contents/.meta.json`）。

### 4.5 `order` は後から直す必要がある

`order` には実在するディレクトリだけを書く。後からコースやレッスンを足したら、**親の `.meta.json` の `order` を計画書の順に直す**。直さないと末尾に追加されて並びが崩れる。

## 5. 守るべき作法

### 5.1 OpenSpec

- planning home は **`dx-training-studio/`**（リポジトリルートではない）。ルートから叩くと `No OpenSpec changes directory found`
- `openspec validate <change> --strict` は**リポジトリルートからだと `Unknown item` になる**。planning home に入ってから叩く
- **`openspec-sync-specs` スキルはこの環境に無い。** archive 時の同期は手作業。本体 spec を直接書き、`npx openspec validate --specs` で**42件**通ることを確認する
- `openspec/changes/` は `.gitignore` されている。**コミットされるのは `openspec/specs/` だけ** — 設計の記録はそこにしか残らない
- アーティファクトは日本語で書く

### 5.2 スキルの SSoT 作法

スキルの作成・更新には **`creating-skills` スキルを使う**。SSoT 監査とハードコード・不整合レビューがゲートになっている。

- `SKILL.md` は 200行が目安・500行が上限。`references/` は各300行以内、100行超なら目次
- **同じ内容を2箇所に書かない。** 特に `SKILL.md` に references の本文を写さない（spec の要件でもある）
- 外部ファイル（`lib/schema.ts` 等）の内容をスキルに写さない。参照先を示す

### 5.3 その他

- 出力は日本語
- `npm run lint` は既存エラーが残っている。増やしていないかだけ見る
